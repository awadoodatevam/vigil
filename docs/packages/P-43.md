## 2. Goal

Build the second half of the primary demo's API layer (PM-M23, CTX-D-077 (1)): the read operations of the incident workspace's AI investigation (AR-I-25), Response (AR-I-27) and Recovery (AR-I-28) sections; the mobile Acknowledge page with its read (AR-I-32) and action (AR-I-33); the mobile Approval page with its read (AR-I-34) and decision (AR-I-35); and the dashboard (AR-I-80). The reads of AR-I-28, AR-I-32 and AR-I-34 are what those screens poll every second (AR-I-05). Each operation checks its permission, asks the owning modules and combines their answers as P-25 does (AR-I-06, AR-I-07, CTX-D-077 (2)); the display reads `vigil-actions` does not have yet (a run's proposal, requests and executions) and the refusal that applies before an acknowledgement or a decision (DM-E35-R1, DM-E59-R1, CTX-D-075 (8)) are added to `vigil-actions` and `vigil-incidents`.

### 6.1 General rules

- P-25 Section 6.1 applies unchanged: composition (CTX-D-077 (2)); answers as snake-case records with every field present; `TeamName`, `UserName`, `ActorName`; component names; times with `ApiTimes.format`; code point order. **Incident guard** (all five incident operations of this package): P-25's `IncidentGuard.workspace` with a `String` path variable (not a UUID in the 8-4-4-4-12 form, unknown, `forming` or `merged`: 404 `not_found`; CTX-D-077 (5), CTX-D-079 (8)). **Approval request guard**: `{request_id}` not a UUID in the same 8-4-4-4-12 form (`IncidentGuard`'s pattern, made package-visible) or no request of the tenant: 404 `not_found`.
- **Owner modules (CTX-D-079 (5)).** Each operation asks the modules of its AR §10.2 row, and also: AR-I-27 `vigil-runner` (parameter order, DM-E-12) and `vigil-incidents` (the executions' result summaries, DC-TX-03); AR-I-28 `vigil-engine` (the run, DC-S03-11 "of the run"); AR-I-33 and AR-I-35 `vigil-identity` (the decider's name, DC-U-06); AR-I-34 `vigil-runner` (parameter order).
- **"The run"** of AR-I-27 and AR-I-28 is the incident's latest live run (by `started_at`, then id), as AR-I-29 finds it; with no live run their answers are the empty forms stated below.
- **Refusals in read answers (AR-I-03, CTX-D-079 (1), (2)).** `refusal` is `null` or `{"key", "message"}` with the module's refusal key and text (times in the outbound format); the page shows times in viewer time from the fields it carries (`acknowledged`, `decided`, `expires_at`). For a caller who does not hold the action's permission (`acknowledge`, `approve_action`), the refusals that depend on the user (`not_notified`; `not_eligible`, `excluded`) are left out: `refusal` is then `null` when only such a refusal applies. `may_act` is whether the caller holds the action's permission.
- **Parameters in the operation's order** (AR-I-27, AR-I-34; DM-E-12): `[{"name", "value"}, …]` in the order of the names in `RunnerService.operation(tenant, operation_key).parametersJson` (the operation's parameter definitions, an array of objects with `name`); each value as stored (any JSON value); names the definitions do not list follow in code point order; with no operation found, all in code point order.
- **Snapshot instants** (`expires_at`, evidence `collected_at`, stored with `Instant.toString()`) are parsed and written with `ApiTimes.format`; every other snapshot value is passed as stored. Decimals written "as text with two decimal places" use `setScale(2, RoundingMode.HALF_UP).toPlainString()`, as P-24's `Snapshots` does.

### 6.2 Module reads and refusal checks (complete list; DC-R-08, PM-R-10)

Reads as P-25 Section 6.2: declared on the service interface, implemented in the service class with SQL in the records class, filtered by `tenant_id`, `null` arguments `IllegalArgumentException`, no audit event, unmodifiable lists.

### 6.4 AR-I-27 `GET /api/v1/incidents/{incident_id}/response` (DC-S03-10)

Permission `view`. Owner modules `vigil-knowledge`, `vigil-actions`, `vigil-engine`, `vigil-identity`, `vigil-runner`, `vigil-incidents`. Answer:

```
{"similar": {"state": "done" or "unavailable", "outcome",
             "past_incident": {"past_incident_key", "title", "record_label", "fix_description"} or null,
             "score", "success_count", "min_similarity"} or null,
 "proposal": {"action_name", "parameters": [{"name", "value"}, …], "target": {"target_key", "name"},
              "policy_outcome"} or null,

                "refusal_reason", "decided": {"user": UserName, "at"} or null, "expires_at"}, …],
 "executions": [{"action_execution_id", "attempt_number", "attempt_limit", "state",
                 "recheck": [{"check", "passed", "detail"}, …], "result_summary",
                 "started_at", "finished_at"}, …]}
```

- `similar` (CTX-D-079 (4)) is `null` until the run's first step execution of an AI task step whose parameters in the run's content have `task` `SL-T-3` (`EngineService.stepExecutions`, the content copy of `EngineService.run`) has state `completed`; the web shows the Response section only when `similar` is not `null` (DC-S03-10); the other parts are answered regardless. With its named output `unavailable`: `{"state": "unavailable"}` with every other field `null`. Otherwise `state` `done` with `KnowledgeService.latestSearchResult` (DM-E66-R2): for `match`, `outcome` `match`, `past_incident` from `KnowledgeService.pastIncident(bestPastIncidentKey)` (`null` when not found), `score`, `success_count` (0 when `null`) and `min_similarity`; for `no_match`, `outcome` `no_match`, `past_incident` `null`, `score` (`null` when none was found), `success_count` `null`, `min_similarity`; scores and the minimum as text with two decimal places (Section 6.1); with no search result, `{"state": "done"}` with every other field `null`.

- `approvals`: `ActionsService.requests(tenant, run)` in `sequence_in_run` order; `eligible_teams` in code point order of the names; `state` and `refusal_reason` keys; `decided` for `approved` and `rejected` (`decided_by`, `decided_at`); `expires_at` (the web shows it while `pending`).
- `executions`: `ActionsService.executions(tenant, run)`; `attempt_limit` from the proposal's action snapshot; `state` the key; `recheck` the stored recheck JSON (`[]` when `null`); `result_summary` the summary of the execution's `action_execution` evidence entry (the entry whose `producerRecordId` is the execution's id, from `IncidentService.evidence`), `null` until the execution's final state.
- With no live run: `{"similar": null, "proposal": null, "no_proposal": false, "approvals": [], "executions": []}`.
