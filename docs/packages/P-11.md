## 2. Goal

Build the seed import of `vigil-setup` (PM-M22-03 to PM-M22-05) and the four installation operations of `vigil-api` that the reset of the control panel uses (AR-I-95 to AR-I-98, AR-B-03), accepted only with the installation token (AR-S-07, PM-M23-06). An installation creates a tenant and uploads a seed bundle file (a ZIP of the data files of `docs/31-demo-data/`, AR-B-05). `vigil-setup` refuses at once a bundle it cannot read or that still contains placeholders (AR-B-05, AR-B-07, BP-A-23); otherwise it records the import (DM-E-82) and imports it part by part in the order of DM-R-56 on its own virtual thread (AR-R-31). A part fails when a file it is the first to read cannot be read or has an unknown section (AR-B-05), or when its module refuses its content (DM-R-57); the first failed part fails the import and the tenant (DM-E82-R1). A successful import writes the one audit event of the import and makes the tenant `ready` (CTX-D-044). The installation then points a host name's alias at the new tenant. Parts 1 to 3 (the import operations of P-08 and P-10) join the part registry now; every later part joins it in the package that builds its module's import, and until then the interim rule BP-R-29 skips its sections. A restart fails every import still running (AR-R-24 step 2).

### 6.3 The bundle at upload (AR-B-05, AR-B-07, BP-A-23)

`SeedBundleReader` (package-private) turns the uploaded bytes into a `SeedBundle` (package-private: the entry bytes by name, the decoded text of each text entry, `bundle_name`, `bundle_version`) or refuses it with `VigilError` `INVALID` (422), a `message` and `details` `{"problems": [texts]}`. The checks run in three stages; a stage with problems refuses the bundle and the later stages do not run. The entry order is that of AR-B-05: `bundle.yaml`, `01-tenant-identity.yaml` … `09-past-incidents.csv`, `logo.png`, `logo.svg`. Within a stage, problems follow the order of the rules, then the entry order (for names that are not allowed: the order they appear in the ZIP), and each distinct text appears once.

**Stage A — the ZIP** (message `The bundle cannot be read: {problems joined by "; "}.`), complete list of rules:

1. The bytes are read with `java.util.zip.ZipInputStream` entry by entry; a read failure, or no entry at all: `the file is not a ZIP file` — then no other rule of stage A is checked.
2. The entries unpack to at most 52,428,800 bytes in total (50 MiB, BP-A-23): else `the bundle is larger than 50 MiB unpacked` — reading stops at the limit and no other rule of stage A is checked.
3. Every entry name is one of the ten required names, `logo.png` or `logo.svg` (so no directory and no path with `/`): else `entry {name} is not allowed`.
4. No name appears twice: `entry {name} appears more than once`.
5. Each of the ten required entries is present: `entry {name} is missing`.
6. Each logo entry has at most 524,288 bytes (512 KB, AR-B-05, BP-A-23): else `entry {name} is larger than 512 KB`.
7. Each allowed text entry (the ten required names) is strict UTF-8 (as P-10 Section 6.6; BP-A-23): else `{name} is not UTF-8`.

**Stage B — placeholders (AR-B-07).** A text entry that contains `${` refuses the bundle with exactly the message `The bundle still contains placeholders: {names}.`, where `{names}` are, for each `${`, the text from it to the next `}` on the same line (to the line's end, without a final `\r`, when there is none), distinct, in order of first appearance across the text entries in entry order, joined by `, `; an empty name is written `""`. `details` `{"problems": [that message]}`.

**Stage C — `bundle.yaml`** (message `The bundle has problems: {problems joined by "; "}.`): it is read as Section 6.4 says; it MUST be a mapping with exactly the keys `bundle_name` (a string of 1 to 100 characters) and `bundle_version` (a string of 1 to 40 characters). Problems (complete list): `bundle.yaml could not be read: {parser message}`; `bundle.yaml: not a mapping`; `bundle.yaml: bundle_name: 1 to 100 characters` (also when absent or not a string); `bundle.yaml: bundle_version: 1 to 40 characters` (also when absent or not a string, so `bundle_version: 1.5` unquoted is refused); `bundle.yaml: unknown field {key}`.

The data files are not parsed as YAML at upload: their YAML problems refuse a part during the import (Section 6.4, AR-B-05).

### 6.5 The registry and the adapters of parts 1 to 3 (PM-M22-03, AR-B-11)

`SeedPartImporter` (package-private interface): `int part()`; `PartResult importPart(TenantId tenantId, SeedBundle bundle, Map<String, JsonNode> files, Instant importStartedAt, Map<String, UUID> handles)`, where `files` holds the checked trees by entry name and `PartResult` is `(Map<String, Integer> counts, Map<String, UUID> handles)`; it throws `VigilError` `INVALID` (message `Part {part name} refused.`, details `problems`) for a refused part; and `default void afterCommit(TenantId tenantId, Map<String, UUID> handles)` (called with the handles this part returned; does nothing by default; the hook of AR-B-11, used from P-13). `SeedPartRegistry` collects every `SeedPartImporter` bean; at construction it throws `IllegalStateException` with "two importers for part {n}" or "no part {n} in the catalogue". Exactly parts 1, 2 and 3 are registered by this package. A part is "registered" when the registry has an importer for it.

**Adapter rules (common).** An adapter reads its sections from the checked trees, checks their shape, maps them to its module's part record and calls the module's import interface. Shape problems (complete list, collected, in section order, then entry order, then the order of the keys in the YAML entry as written): `{s}: missing` (the section is absent); `{s}: not a list` or `{s}: not a mapping` (the section has another form than its row below); `{s}[{i}]: not a mapping`; `{s}[{i}]: unknown field {k}`; `{s}[{i}].{k}: not a single value` (a list or mapping where a single value is expected); for the mapping section `tenant_settings`: `tenant_settings: unknown field {k}`, `tenant_settings.{k}: not a single value`; for `permission_grants` (keys are usernames): `permission_grants.{user}: not a list`, `permission_grants.{user}[{i}]: not a single value`. `{s}` is the section, `{i}` the entry's index from 0, `{k}` a key. A single value becomes its text (a YAML number or boolean as Jackson's `asString()` writes it); YAML `null` and an absent field become `null`. With shape problems the adapter throws `VigilError` `INVALID` `Part {part name} refused.` with them and does not call the module. Counts are, per section, the number of list entries, of mapping keys for `permission_grants`, and 1 for `tenant_settings`.

### 6.7 The import (PM-M22-03, AR-R-31, DM-E-82, DM-E82-R1, DM-E08-R3)

`vigil.setup.api.SeedImports` (requests of `vigil-api` and `RestartProcedure`, complete list):

- `SeedImportView start(TenantId tenantId, byte[] bundle)` — in order: `tenantId` or `bundle` `null` → `IllegalArgumentException`; the tenant does not exist (`TenantService.tenant`) → `VigilError` `NOT_FOUND`; the tenant is not `provisioning`, or has a seed import record → `VigilError` `REFUSED` with the message "A seed bundle can be imported only into a new tenant." and details `{"refusal": "tenant_not_new"}` (DM-E82-R1, BP-A-23); the checks of Section 6.3 (a refusal stores nothing and leaves the tenant `provisioning`). Then one transaction inserts the record: state `running`, `bundle_name` and `bundle_version` from `bundle.yaml`, `started_by` = `Actor.module("vigil-setup")` (AR-S-07), `created_at` = `updated_at` = now (the import start time T), `parts` the 17 entries `not_started` with counts `{}` and error `null`; a unique violation on `tenant_id` (two imports started at once) gives the same `REFUSED`. After the commit it starts the worker on a new virtual thread `Thread.ofVirtual().name("seed-import-" + record id)` (AR-R-31) and returns the record's view.
- `Optional<SeedImportView> seedImport(UUID seedImportId)` — the record (installation-level).
- `void failInterrupted()` — restart step (2), below.

`SeedImportView` — record `(UUID id, TenantId tenantId, String bundleName, String bundleVersion, SeedImportState state, Instant startedAt, Instant finishedAt, List<PartView> parts)`, with `SeedImportState` `RUNNING`, `SUCCEEDED`, `FAILED` and `PartView(String module, PartOutcome outcome, Map<String, Integer> counts, String error)`, `PartOutcome` `SUCCEEDED`, `FAILED`, `NOT_STARTED`; each enum has `key()` (lower case, as stored).

**The worker**, in order, with no transaction around module calls; any exception (not an `Error`) thrown by a step goes to step 3 with the error `unexpected error` on the part being worked on (the last registered part when it is thrown in step 2 or 4), logged at `ERROR`:

1. For each part 1 to 17 in order: (a) the file checks of Section 6.4 for the files whose turn it is; a problem fails the part (step 3); (b) when the part is not registered, its entry stays `not_started` (BP-R-29); (c) when it is registered, call its importer with T and the handle map so far. On success: one transaction sets the entry `succeeded` with its counts; the returned handles are added to the map (a handle already in the map is an `IllegalStateException`); then `afterCommit` runs. On a `VigilError` `INVALID`: the entry's error is its message, a space, and its problems joined by `; ` (Example: `Part identity refused. users: no password for admin`); any other `VigilError`: its message, or its code's wire text (`VigilError.Code.wireText()`) when it has none. The import fails (step 3); no later part runs. Every part error (file check, adapter, module, key check, restart) is cut to its first 500 code points (DM-E-82 `error` is Text(500)).
2. The key checks of Section 6.6; problems fail the import (step 3).
3. **Failure:** one transaction sets the failing entry (and, for key checks, every referring part with problems) `failed` with its error, the record `failed` with `finished_at` = now, and the tenant `failed` (`TenantService.markFailed`, DM-SM01-T3). No audit event (CTX-D-044). If this transaction itself fails, it is logged at `ERROR` and the record stays `running` until the next restart (step (2) of AR-R-24 fails it).
4. **Success:** one transaction sets the record `succeeded` with `finished_at` = now, appends the one audit event (DM-E08-R3, DM-C-07) and makes the tenant `ready` (`TenantService.markReady`, DM-SM01-T2). The event: `tenantId` the tenant; `occurredAt` now; actor `Actor.module("vigil-setup")`; type `CONFIGURATION_CHANGED`; `subjectType` `SeedImport`; `subjectId` the record id; `incidentId` `null`; summary `Seed bundle {bundle_name} {bundle_version} imported.` (DC-TX-10); `detailsJson` `{"area": "seed_import", "before": null, "after": {"bundle_name": …, "bundle_version": …, "parts": [{"module": …, "outcome": …, "counts": {…}}, … for all 17 in order]}}`.

**Restart step (2)** (`failInterrupted`, called by `RestartProcedure.step2FailInterruptedSeedImports`; AR-R-24): for every record in state `running`, one transaction: the first registered part whose outcome is `not_started` (when there is none, the last registered part) becomes `failed` with the error `interrupted by restart`; the record `failed` with `finished_at` = now; and, when `TenantService.tenant` shows the tenant `provisioning`, the tenant `failed` (`markFailed`; a tenant in another state is left as it is). Logged at `WARN` with the record id.

### 6.8 Installation operations (AR-I-95 to AR-I-98, AR-S-07, PM-M23-06)
