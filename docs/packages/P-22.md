### 6.1 General rules

- Every public type of `vigil-notifications` is in `vigil.notifications.api`, of `vigil-routing` in `vigil.routing.api` (AR-R-04); every other new class is package-private. The `@ApplicationModule` declarations stay as they are (`vigil-notifications`: `shared`, `connectors :: api`, `identity :: api`, `incidents :: api`, `investigation :: api`, `tenancy :: api`, `audit :: api`; `vigil-routing`: `shared`, `incidents :: api`, `servicemap :: api`, `identity :: api`, `notifications :: api`, `ticketing :: api`, `audit :: api`).
- Persistence with `JdbcClient`; transactions with `TransactionTemplate`; ids from `Ids.newId()`; time from the `Clock` bean through `Timestamps.now(clock)`; every statement filtered by `tenant_id`; no `DELETE`. Requests to other modules inside a transaction join it (AR-R-10). JSON with a `static final JsonMapper` (Jackson 3).
- External calls (AR-R-09): `NotificationsStepHandler.start` and `evaluate`, `RoutingStepHandler.start` and `evaluate`, `NotificationsService.notifyEscalation` and `notifyApprovalRequest`, and `NotificationChannelConnector.send` call `TransactionGuard.assertNoTransaction()` first. A message is sent with no transaction open, and its record is stored in a transaction opened after the send returned.
- Lengths are Unicode code points; "cut to n" keeps the first n code points. "Comma-separated" means joined with `, `. Lists of names are alphabetical, which is ascending order of Unicode code points (DC-TX-00 "Lists"; DM-C-01), unless a rule says otherwise. Times in outbound texts use the outbound time format `YYYY-MM-DD HH:MM:SS UTC`; durations DC-U-07 rule (2) (as P-21 Section 6.1).
- `null` arguments of public requests: `IllegalArgumentException("a required argument is missing")`.
- Actors: requests of `vigil-notifications` use `Actor.module("vigil-notifications")`, of `vigil-routing` `Actor.module("vigil-routing")`.
- Logging (complete list at `INFO` or above from `vigil.notifications`, `vigil.routing` and the two connectors): `WARN` `{purpose key} message to {recipient kind} {recipient key} by {channel key} failed for incident {incident id} of tenant {tenant id}: {error}` once per `failed` notification record; `WARN` `escalation of incident {incident id} of tenant {tenant id}: the ticket comment failed` each time `recordEscalation` answers `FAILED` (also for a record that failed earlier, which P-21 answers again with no Jira call); the `WARN` of `vigil-ticketing` stays. The `WARN` of `FileSecrets.readNamed` stays. No message content, webhook address or secret is logged.
- Every list returned is unmodifiable. Texts named in this spec are exact.

### 6.2 The channel connectors (`vigil-connectors`; AR-K-00d, AR-K-05, AR-K-06, AR-K-17 to AR-K-20, AR-T-14, AR-R-32)

**Public types added to `vigil.connectors.api` (complete list):**

- `record MessageLine(String text, String link)`: one line of a message; `link` `null`, or the address the line ends with. Compact constructor as `TicketLine` of P-21 (`IllegalArgumentException("message line: text ending with its link")`); static `of(String text)`.
- `sealed interface Delivery permits Delivery.Sent, Delivery.Failed` with `record Sent()` and `record Failed(String reason)` (`reason` cut to 500).
- `interface NotificationChannelConnector` (AR-K-00d; one bean per channel kind; `vigil-notifications` calls it): `ConnectorKind kind()`; `Delivery send(TenantId tenantId, ConnectorInstanceView instance, String address, UUID credentialRefId, String senderName, List<MessageLine> lines)` (external call, not inside a transaction; `credentialRefId` the delivery address's credential reference, `null` for email; `senderName` the product display name, used by email only; `lines` at least one; line 1 is the subject of an email).

`ConnectorTimings` (a positional record: `connect, monitoringTest, chat, localChat, embedOne, embedBatch, jira`) gains `Duration teams` and `Duration smtp` (15 s each, AR-TM-01) after `jira`, in that order, set in `ConnectorConfiguration`; `AiTimeoutsIT`, `ConnectionTestIT` and `FailureReasonsTest` add `Duration.ofSeconds(15), Duration.ofSeconds(15)` after their `jira` argument. Every `send` starts with `TransactionGuard.assertNoTransaction()`, the `null` checks (except `credentialRefId` and `senderName` where this section allows `null`), and an instance of another kind: `IllegalArgumentException("connector instance {id} is not {kind key}")`. A `Failed` reason never holds a secret, a webhook address or its query.

**`TeamsConnector`** (bean, kind `MS_TEAMS`; AR-K-05, AR-K-17, AR-K-18):

1. The webhook (AR-K-17): `credentialRefId` `null` or not a credential reference of purpose `webhook_url` (`ConnectorRecords.credential`): `Failed` `No credential is set.`; its secret not readable: `Secret {name} is not available.`; a secret that is not an `http` or `https` address with a host and no white space (`HttpSourceConnector.address`): `Secret {name} is not a valid webhook address.` The instance's own `address` is informational and not used.
2. The payload (AR-K-18), exactly, key order as written: `{"type":"message","attachments":[{"contentType":"application/vnd.microsoft.card.adaptive","content":{"$schema":"http://adaptivecards.io/schemas/adaptive-card.json","type":"AdaptiveCard","version":"1.4","body":[…]}}]}`; `body` one `TextBlock` per line in order, line 1 `{"type":"TextBlock","text": text,"wrap":true,"weight":"Bolder"}`, the others `{"type":"TextBlock","text": text,"wrap":true}`; a line with a link has `text` = the text before the link followed by `[{link}]({link})` (the visible text is unchanged). Serialized with Jackson as UTF-8 (the P-07 recordings `teams/*.json` hold this payload).
3. The post: `POST` to the webhook address with `Content-Type: application/json`, timeout `timings.teams()` (connect 5 s through `ConnectorHttp`), through the **sender** (AR-K-19, AR-R-32): one per installation, a fair lock held from the wait to the answer; a post starts at least 300 ms after the previous post's answer or failure, waiting the rest with `Thread.sleep` on the caller's thread (no transaction is open, Section 6.1). 200 to 299: `Sent`. Any other status: `Failed` `HTTP {status}`. No answer: `FailureReasons.of(failure, uri, timings, timings.teams(), hidden)` with `uri` the webhook's scheme, host and port only and `hidden` the webhook address, its path and its query, so no reason names any of them.

**`EmailConnector`** (bean, kind `EMAIL`; AR-K-06, AR-K-20, AR-T-14):

1. The server: the instance's `address` must be `smtp://{host}:{port}` (port 1 to 65535), else `Failed` `The address is not a valid smtp address.`; the settings `from_address` (string) and `starttls` (boolean).
2. The credential: the instance's credential reference (purpose `smtp`) as `JiraConnector` reads its own (no reference: `No credential is set.`; not readable: `Secret {name} is not available.`; not a JSON object with the non-empty strings `username` and `password`: `Secret {name} is not valid.`).
3. The message (AR-K-20) with Jakarta Mail (`jakarta.mail`, from `spring-boot-starter-mail`, AR-T-14): a `Session` per send with `mail.smtp.host`, `mail.smtp.port`, `mail.smtp.auth=true`, `mail.smtp.starttls.enable` and `mail.smtp.starttls.required` both equal to `starttls`, `mail.smtp.connectiontimeout=5000`, `mail.smtp.timeout` and `mail.smtp.writetimeout` = `timings.smtp()` in ms; a `MimeMessage` with `From` `InternetAddress(from_address, senderName, "UTF-8")`, `To` the address, `Subject` line 1 (`setSubject(…, "UTF-8")`), `Date` now, the body the lines' texts joined by CRLF and ended by CRLF, `setText(body, "UTF-8", "plain")`, then the header `Content-Transfer-Encoding: 8bit` (so no line, and no link, is wrapped; P-07 report Section 11 item 2); `Transport.send(message, username, password)`.
4. Outcomes: sent: `Sent`. A refusal or failure (complete list, the first that applies): an `AuthenticationFailedException`: `SMTP authentication failed.`; a `MessagingException` whose cause chain holds a `SocketTimeoutException` while connecting (a `MailConnectException`): `No connection to {host}:{port} within 5 s.`; any other `SocketTimeoutException`: `No answer within 15 s.`; an `UnknownHostException`: `Host {host} not found.`; a `ConnectException`: `Could not connect to {host}:{port}.`; a `SendFailedException` or another `MessagingException`: `The SMTP server refused the message: {message}` (the exception's message, cut to 400; a message holding the username or password is replaced by its class name).

### 6.5 The instances

### 6.6 Delivering one request (`Deliveries`; PM-M20-02, PM-M20-04, DM-R-65, DM-E37-R1)

A request has an origin, a purpose, the incident, its recipients (each a recipient kind and key, and for a user the team through which it was chosen), the lines of Section 6.7 and the link. For each recipient in the order given, for each of its active delivery addresses by channel (`teams` before `email`), one message:

1. DM-R-65: a `sent` record of the same origin, recipient (kind and key) and channel exists → nothing is sent and no record is made; it counts as delivered.
2. Otherwise `send` (no transaction open); then one transaction: the record (`content` the lines' texts joined by `\n` and cut to 4,000; `link`; `status`; `error` the reason; `at` now), the audit event (Section 6.13) and, when it was sent and the incident is `open` or `resolved` (read in that transaction; `recordNotifiedTeam` refuses other states, and the record MUST be stored anyway so DM-R-65 holds), `IncidentService.recordNotifiedTeam(…, team, purpose)` for the team (the recipient team, or the user's `via_team_key`), which records the team once (DM-E37-R1; `vigil-incidents` ignores later requests). A unique violation of the `sent` index (a concurrent send) is not possible: one evaluation at a time per run (DM-R-67) and one request per escalation or approval request.
- A recipient with no active address makes no record. The request's outcome is `SENT` when at least one message is delivered (sent now or earlier), else `FAILED`.
- Recipients (DM-E77-R1): a team's addresses are those with `subject_kind` `team` and its key; a user's are those with `user` and the username.

### 6.7 The texts (`MessageTexts`; DC-OUT-00, DC-OUT-05 to DC-OUT-07, DM-E02-R2, DC-TX-01)

`{prefix}` is `{environment label} - ` when the tenant's `environmentLabel` is neither `null` nor empty, else empty (DM-E02-R2). `{number}` `INC-` and the number padded to 4 digits; `{severity}` the incident's severity key (`P1` to `P4`); team names from `IdentityService.team` (the key when the team is not found); `{owner team}` the owner team's name (`none` when the incident has no owner team); `{informed team names}` the names of `informed_team_keys`, alphabetical, comma-separated, `none` when empty; `{service names}` the names of `affected_services`, alphabetical, comma-separated, `none identified` when empty; `{summary}` the text of `InvestigationService.summaryForMessage` (DM-E69-R2, in its own transaction before any send); the evidence lines one `- {summary}` per entry of `IncidentService.evidenceSummary`. Links (AR-I-101, AR-I-102): `{base}/m/acknowledge/{incident id}` and `{base}/m/approve/{approval request id}` with `{base}` = `TenantService.publicBaseAddress`; when it is absent, every message of the request not already `sent` (the DM-R-65 check comes first) is a `failed` record with the error `the tenant has no public address for links` and the link `""`.

- **DC-OUT-05** (incident notification), lines: `{prefix}[{severity}] {number} {title}`; `Owner: {owner team}. Informed: {informed team names}.`; `Customer impact: {service names}.`; `Summary: {summary}`; `Acknowledge: {Acknowledge link}` (the link as the line's `link`).
- **DC-OUT-06** (escalation), lines: `{prefix}Escalation level {n}: [{severity}] {number} {title}`; `Escalated to {team names} ({escalation cause}).` (the level's team names, alphabetical; the cause by DC-TX-01: `acknowledgement_timeout` gives `not acknowledged within {timer}`, `escalate_now` gives `workflow escalation step`; the timer by DC-U-07 rule (2): `{s} s` under 120 s, else `{m} min` or `{m} min {s} s`; `MessageTexts` holds its own copies of these helpers and of the incident number, because `vigil.ticketing.TicketTexts` is package-private and is not used); `Owner: {owner team}. Informed: {informed team names}.`; `Summary: {summary}`; `Evidence:`; one line per evidence entry (none when there is none, as P-21 reads DC-OUT-02, CTX-D-069 (7)); `Acknowledge: {Acknowledge link}`.
- **DC-OUT-07** (approval request), lines: `{prefix}Approval needed: {action name} on {target name} for {number}`; `[{severity}] {number} {title}`; `Expires: {expires_at}` (outbound time); `Summary: {summary}`; `Approve or reject: {Approval link}`.

An incident without a `number` or `severity` cannot be messaged: `IllegalStateException("incident {id} has no number or severity")` (a failed call).

### 6.8 The Notification step (`NotificationStep`; DM-S-09, PM-M20-01 to PM-M20-05)

The engine calls `start` and `evaluate` on the run's virtual thread with no transaction open; a throw is a failed call, retried after 5 s, 15 s and 45 s (AR-TM-05). `start` and `evaluate` do the same (the step never answers `Waiting`); `cancel` does nothing, every time.

1. `TransactionGuard.assertNoTransaction()`. A step type other than `NOTIFICATION`, or parameters that are not an object with `recipients` a non-empty array of `owner_team`, `informed_parties`, `named_teams` (and `named_teams` an array of keys when `recipients` holds `named_teams`): `IllegalArgumentException("notification step parameters: recipients")`.
2. The incident; none: `IllegalStateException("incident {id} not found")`.
3. The recipient teams (PM-M20-05), in this order and without repeats: `owner_team` the incident's owner team (none when not set); `informed_parties` its `informed_team_keys`, alphabetical by key; `named_teams` the parameter's keys in the order written.
4. Deliver (Section 6.6) with the origin (`vigil-engine`, `StepExecution`, the step execution id), purpose `incident_notification`, the lines of DC-OUT-05.
5. `Completed(sent or failed, resultRef)` with `resultRef` `ResultRef("vigil-notifications", "NotificationRecord", the first record id of the origin in `at` order)`, or `null` when the origin has no record; `failed` when no message of the origin is delivered (PM-M20-04). Called again after it finished, the step sends only what is not yet `sent` (DM-R-65) and answers by all the origin's records.

### 6.9 The send requests (`Notifications`; PM-M20-01, PM-I-14, DC-A-10)

Both start with `TransactionGuard.assertNoTransaction()` and the `null` checks; the incident must exist (`IllegalStateException`); the outcome is that of Section 6.6.

- **`notifyEscalation(tenant, incident, escalationId, level, teamKeys, cause, timer)`** (from `vigil-routing`): `timer` as P-21's `recordEscalation` (required for `acknowledgement_timeout`, `null` for `escalate_now`); recipients the teams of `teamKeys` in the order given; origin (`vigil-incidents`, `IncidentEscalation`, `escalationId`); purpose `escalation`; the lines of DC-OUT-06 with `level`, the team names and the cause. Called again with the same escalation id it sends only what is not yet `sent`.
- **`notifyApprovalRequest(tenant, incident, approvalRequestId, recipients, actionName, targetName, expiresAt)`** (from `vigil-actions`, P-24): recipients the users in the order given (`recipient_kind` `user`, `via_team_key` the recipient's team); origin (`vigil-actions`, `ApprovalRequest`, `approvalRequestId`); purpose `approval_request`; the lines of DC-OUT-07; the notified team is the `via_team_key`. `recipients` empty: `IllegalArgumentException("recipients: at least one")`.

### 6.10 The Escalation step (`EscalationStep`; DM-S-08, PM-M10-05, PM-D-08, DM-D-09, DM-R-64)

The engine calls `start` and `evaluate` on the run's virtual thread with no transaction open (AR-TM-05 as above); `cancel` does nothing, every time. A step type other than `ESCALATION`, or parameters that are not an object with `mode` `wait_for_acknowledgement` or `escalate_now` and, for `wait_for_acknowledgement`, `timer` an integer number of seconds from 30 to 86,400 (as `WaitStep` reads its durations): `IllegalArgumentException("escalation step parameters: mode and timer")`. The levels are the current escalation policy (`RoutingService.escalationPolicy`, levels in ascending order; `last` the highest level); no policy or no level: `Completed(next, null)` at once, with no escalation (CTX-D-071 (11)). `L` is the incident's `escalation_level` as read at the start of the call.

**The target of a new round** is level `n = min(L + 1, last)` (so at or above the last level the last level is notified again, DM-S-08), with that level's team keys and the policy's revision.

**Recording a round** (round `r` of this step execution): one transaction: `IncidentService.recordEscalation(tenant, Actor.module("vigil-routing"), incident, n, the level's team keys, cause, timer, the policy revision)` and the row `(incident, step execution, r, escalation id, n, now)` of `routing.step_escalation`.

**Sending a round** (with no transaction open, each time the round is reached; both requests send nothing twice, DM-R-65 and P-21 Section 6.8): the escalation is the entry of `IncidentService.escalations` with the row's `escalation_id`, which gives the level, team keys, cause and timer; `NotificationsService.notifyEscalation(…, escalation id, its level, its team keys, its cause, its timer)`; then `TicketingService.recordEscalation(…, escalation id, its level, the names of its teams (`IdentityService.team`, the key when not found), its cause, its timer)` (CTX-D-069 (7); a `FAILED` answer is logged, Section 6.1, and does not change the step).

**A round already recorded comes first** (DM-R-64, CTX-D-071 (2)): at the start of every call, when the row of the next round exists (round 1 for `escalate_now`; round `r + 1` of the state for `wait_for_acknowledgement`, `r` 0 when there is no state), the step does not record a new one: it sends that round, then continues from it as if it had just recorded it (below), whatever the incident's state or acknowledgement now is.

- **`escalate_now`**: round 1 recorded already → send it, `Completed(next, null)`. Otherwise: an incident that is not `open` → `next` (CTX-D-071 (4)); else record round 1 to `n` (cause `escalate_now`, no timer), send it, `next`.
- **`wait_for_acknowledgement`**: the step state is `{"round": r, "wait_started_at": ISO instant, "last_level_at_start": boolean}`; on `start` with no state: `round` 0, `wait_started_at` now, `last_level_at_start` = `L >= last`. Then, in order:
  1. The row of round `r + 1` exists → send it and **continue from round `r + 1`** (below).
  2. The incident is not `open` → `next` (CTX-D-071 (4)).
  3. `IncidentService.acknowledgement` of the current episode exists (whenever it was made, DM-D-09) → `next`.
  4. Now is before `wait_started_at + timer` → `Waiting({INCIDENT_ACKNOWLEDGED}, wait_started_at + timer, the state)`.
  5. The timeout: record round `r + 1` to `n` (cause `acknowledgement_timeout`, timer `timer`), send it, and **continue from round `r + 1`**.
  - **Continue from round `k`** (with its row's `level` and `at`): when `last_level_at_start`, or the row's `level` is `last` or higher → `Completed(next, null)` (the last level has been notified); otherwise `Waiting({INCIDENT_ACKNOWLEDGED}, at + timer, {"round": k, "wait_started_at": at, "last_level_at_start": false})` (after a stop longer than the timer, the next round follows at the next call; CTX-D-071 (11)).
