## 2. Goal

Make the lab produce the real alert storm. Zabbix 7.0 and Prometheus with Alertmanager monitor the five lab hosts of P-03 exactly as DD-F-10 `monitoring_configuration` says and send their webhooks, in the message formats of `50-architecture` Sections 12.3 and 12.4, to `webhook_base_url`; `demo-faults` injects and clears SL-F-1, SL-F-2 and SL-F-3 through the HTTP interface of AR-X-03; while Vigil is not yet built, a recorder stands in for `vigil-app` at `webhook_base_url` and keeps every message it receives. `deploy/local.sh up --lab-only` starts all of it with generated secrets. The storm timing spike (SB-T-01, development run) then proves, against the recorder, every timing target of DD-F-10 that does not need Vigil: 10 storms in a cloud session (`test` profile) and 3 on the owner's Mac (`demo` profile), and measures the development values of DD-F-10. The gate runs one storm with SL-F-2 on every pull request from now on, so later packages cannot break the lab's monitoring unnoticed.

#### 6.2.1 `provision.py` — `lab-zabbix-provision` (AR-X-02)

A one-shot program. Inputs (complete list): environment `ZABBIX_URL` (default `http://lab-zabbix-web:8080`), `WEBHOOK_BASE_URL` (no default; missing or empty: exit 1 with `WEBHOOK_BASE_URL is not set`); secret files `/run/secrets/vigil/webhook-zabbix` and `/run/secrets/vigil/zabbix-admin-password` (a missing file: exit 1 with `missing secret {name}`); output folder `/srv/vigil/generated/`. It calls the Zabbix API (JSON-RPC 2.0, `POST {ZABBIX_URL}/api_jsonrpc.php`, `Content-Type: application/json-rpc`, the session or token in the header `Authorization: Bearer …`), with `urllib`, each call with a 30 s deadline. It never prints a secret, a token or a session identifier. Each step logs one plain-text line (Example: `media type "Vigil webhook": updated`). Any failure exits 1 with the error text; success exits 0.

Steps, in order (complete list):

1. **Wait.** Call `apiinfo.version` (no authorization header) every 2 s until it answers with a `result`, for at most 120 s (AR-H-11); then try step 2 every 2 s, for at most 60 s more, while the error is anything other than a wrong user name or password (the Zabbix database may still be initialising).
2. **Log in as `Admin`.** `user.login` with `username` `Admin` and the password from `zabbix-admin-password`. When Zabbix answers that the user name or password is wrong (an error whose `data` contains `Incorrect user name or password`), log in with the default password `zabbix`, change `Admin`'s password to the secret with `user.update` (with `current_passwd`), and log in again with the secret (AR-X-02: on the first run it changes the default password). When the default password is refused too (the Zabbix database was kept but the secret was made new), exit 1 with `Admin login failed with the secret and the default password: remove the Zabbix database (deploy/local.sh down --volumes) or restore zabbix-admin-password`.
3. **Objects.** For each object of Section 6.2.2, in the order of that section: find it by its key (given in the table); create it when missing; otherwise update it to the values of Section 6.2.2. Nothing is deleted, except in step 4. Values not named in Section 6.2.2 keep Zabbix's defaults on create and are not changed on update.
4. **API token of `vigil`.** When `/srv/vigil/generated/zabbix-api` exists and a `host.get` call (`{"output":["hostid"],"limit":1}`) with that token as `Authorization: Bearer` answers with a `result`, keep it. Otherwise delete every API token named `vigil` of user `vigil` (`token.get`, `token.delete`), create one (`token.create`: name `vigil`, the user `vigil`, no expiry, enabled), generate its value (`token.generate`), write it without a newline to `/srv/vigil/generated/zabbix-api.tmp` with mode 0600, and rename that file to `zabbix-api`.
5. `user.logout`; exit 0.

#### 6.2.3 The media type script (AR §12.3)

JavaScript, run by Zabbix's webhook engine. `provision.py` writes the address `{WEBHOOK_BASE_URL}/api/v1/webhooks/zabbix-lab` (with any trailing `/` of `WEBHOOK_BASE_URL` removed) and the Zabbix webhook token into the script text as JavaScript string literals (JSON-encoded), because DD-F-10's parameter list is complete. The script (complete list of what it does): parses `value` (the parameters object); builds an object with exactly these keys, in this order: `event_id`, `event_value`, `event_name`, `host`, `severity` (each the parameter's string), `tags` (`JSON.parse` of the `tags` parameter), `event_date`, `event_time`, `recovery_date` and `recovery_time` (the parameters when `event_value` is `"0"`, otherwise `""`); sends it with `HttpRequest` as `POST` to the address with exactly the headers `Content-Type: application/json`, `Authorization: Bearer {token}` and `User-Agent: zabbix-webhook`; throws an error naming the HTTP status when the status is not 200 (Zabbix then tries again with its default attempts); otherwise returns `OK`.

#### 6.2.4 `make_secret.py`

Used only by `deploy/local.sh` (Section 6.7), run in the `vigil/lab-zabbix-provision:local` image. Arguments: one or more `{kind}:{output path}[:{input path}]`. Kinds (complete list): `token` writes `secrets.token_urlsafe(32)` (32 random bytes, base64url without padding, 43 characters); `password` writes 20 characters from A–Z, a–z, 0–9 chosen with `secrets.choice`; `web-config` reads the password from the input path and writes the YAML `basic_auth_users:\n  vigil: {hash}\n`, where `{hash}` is `bcrypt.hashpw(password, bcrypt.gensalt(rounds=10))` (AR-S-13 `alertmanager-web-config`). Values are written without a trailing newline (except the YAML's own last newline) to the output path with mode 0600. It prints nothing.

### 6.3 `demo/faults/` — `demo-faults` (AR-U-07, AR-X-03 without SL-F-4)

`faults.py` (Python 3.12, standard library only):

- **Start.** Reads the listen address from `FAULTS_LISTEN` (default `172.31.0.1:8091`), the token from `/run/secrets/vigil/faults-token` (missing: exit 1 with `missing secret faults-token`) and the state file `/var/lib/demo-faults/state.json` (`{"active": [...]}`, a sorted list of fault IDs; missing means none active). Listens with `http.server.ThreadingHTTPServer`; requests are handled one at a time (one lock), so an inject and a clear never overlap.
- **Authorization.** Every request first: header `Authorization: Bearer {faults-token}`, compared with `hmac.compare_digest`; otherwise 401 `{"error":"unauthorized"}`.
- **Operations (complete list, AR-X-03).** `POST /faults/{id}/inject` and `POST /faults/clear` with the JSON body `{"faults": [ids]}`. Every other method or path answers 404 `{"error":"not found"}`. An ID other than `SL-F-1`, `SL-F-2`, `SL-F-3` (SL-F-4 included) answers 500 `{"error":"unknown fault {id}"}`; a clear body that is not a JSON object with a list of strings under `faults` answers 500 `{"error":"invalid body"}`.
- **Inject.** When the fault is already active: 200 `{"active": [...]}` at once, nothing runs (idempotent). Otherwise it runs the fault's inject command (table below); on success it adds the fault to the state and answers 200 `{"active": [...]}`; on failure 500 `{"error": "{id} inject failed (exit {code}): {last 500 characters of the output}"}`, or `{id} inject failed (no exit after 60 s): {output so far}` when the command did not end within its deadline, and the state is unchanged.
- **Clear.** The whole list is checked first: any unknown ID answers 500 `unknown fault {id}` and nothing runs. Then for each fault of the body, in the order SL-F-1, SL-F-2, SL-F-3 (only those named; an empty list answers 200), it runs the fault's clear command, also when the fault is not active (idempotent), then removes it from the state. It stops at the first failure with 500 as above (`… clear failed …`); faults cleared before the failure stay removed. Success: 200 `{"active": [...]}`.
- **State file.** Written to a temporary file in the same folder and renamed after every change.
- **Commands** run inside the lab containers through the Docker Engine API on the mounted socket `/var/run/docker.sock` (what `docker exec` does, AR-X-03): create an exec instance for the container (`User` `root`, standard output and error attached, no TTY), start it attached, read the multiplexed output to its end, and read the exit code; deadline 60 s per command; an exit code other than 0, or no exit code within the deadline, is a failure. The API version is read once at start from the `Api-Version` header of `GET /_ping`, and every call uses the path prefix `/v{that version}/` (unversioned paths are deprecated by Docker).

| Fault | Container | Inject command | Clear command |
| --- | --- | --- | --- |
| SL-F-1 | `lab-db-01` | `bash -c {text of scripts/sl-f-1-inject.sh}` | `bash -c {text of scripts/sl-f-1-clear.sh}` |
| SL-F-2 | `lab-db-01` | `labctl db read-only on` | `labctl db read-only off` |
| SL-F-3 | `lab-rpt-01` | `labctl report fail` | `labctl report succeed` |

- `scripts/sl-f-1-inject.sh`: DD-F-10 `faults.SL-F-1.inject` steps 1 to 4 exactly as `INJECT` in `demo/lab/test_lab.py` does them (files `txlog_000001.arc` to `txlog_{N+1}.arc` in `/data/txlog_archive`, made with `fallocate` as root, modification times from 47 h to 26 h before now); it prints `{N + 1} {bytes}`. `scripts/sl-f-1-clear.sh`: deletes the files `/data/txlog_archive/txlog_*.arc` that still exist (DD-F-10 `clear`). Both start with the line `#!/usr/bin/env bash` followed by `set -euo pipefail` (shellcheck needs the shebang).
- **Logging.** One line per request: method, path, status and duration in milliseconds; for a fault command, its output on the following line. Never the token.

### 6.4 `dev/recorder/` — the webhook recorder

Files (complete list): `Dockerfile`, `recorder.py`, `test_recorder.py`, `README.md`.

`recorder.py` (Python 3.12, standard library only) stands in for `vigil-app`'s webhook operation AR-I-90 while Vigil is not running. It listens on `0.0.0.0:8080` (`ThreadingHTTPServer`, `request_queue_size = 128`). At start it reads `/run/secrets/vigil/webhook-zabbix` and `/run/secrets/vigil/webhook-alertmanager` (missing: exit 1 with `missing secret {name}`) and its output folder from `RECORDER_OUT` (default `/recordings`; not writable: exit 1). It numbers calls from 1, or from one more than the highest number of a file already in the output folder.

Operations (complete list):

| Request | Answer |
| --- | --- |
| `POST /api/v1/webhooks/zabbix-lab` and `POST /api/v1/webhooks/alertmanager-lab` | The body is read (more than 5 MiB, AR-TM-02: 413, recorded with an empty body). `Authorization` equal to `Bearer {token of that source}` (`hmac.compare_digest`): 200 `{"entries": n}` (`n` = 1 for Zabbix; for Alertmanager the length of the body's `alerts` array, 0 when the body is not a JSON object with that array). Otherwise 401 `{"error":"unauthorized"}`. Every such call is recorded, whatever its answer. |
| `GET /_recorder/calls?after={n}` | 200 with the JSON array of recorded calls whose `seq` is greater than `n` (default 0), in `seq` order. |

A recorded call is the JSON object (complete list of keys): `seq` (its number, given under a lock in the order bodies finish arriving); `received_at` (UTC time when the body had been read, RFC 3339 with milliseconds and `Z`); `source_key` (`zabbix-lab` or `alertmanager-lab`); `method`; `path`; `status` (the answer's code); `authorized` (true or false); `headers` (every request header as received, except that the value of `Authorization` is replaced by `Bearer <redacted>`, so no secret is kept); `body` (the body as UTF-8 text, exactly as received). Each call is kept in memory and written to `{output folder}/{seq:06d}-{source_key}.json` (written to a temporary file and renamed). Logging: one line per call (seq, source key, status), never a header value or body.

**Steps of a run (complete list, in order; times are wall-clock seconds; the numbers come from DD-F-10 `timing_targets.numbers` except the 30 s of SL-F-3, DD-F-10 `faults.SL-F-3.expected_effect`):**

1. **Quiet.** Every 2 s, until Zabbix `problem.get` (as `vigil`, tag `vigil` equals `lab`) returns no problem and Alertmanager `GET /api/v2/alerts` returns no alert whose `alertname` is one of the five catalogue names (the reads of AR-B-03 branch A), at most 120 s; then wait `clear_settle_s` (12 s). Not quiet in time: the run's check `quiet_before` fails with `lab not quiet` and the spike stops as "Failure of a step" says. A Zabbix or Alertmanager read that fails (connection error, HTTP status other than 200, or a JSON-RPC error) counts as not quiet; the same holds for step 9.
2. **Baseline.** `fs_used_pct` (DD-F-04, as `vigil-diag`) gives `baseline_used_pct`.
3. **Inject.** `T0` = the time just before the first inject request. `POST /faults/{id}/inject` for each fault of the run; each MUST answer 200.
4. **Arrival.** Read the recorder (`after` = the highest `seq` seen before `T0`) every 1 s until `T0` + 150 s.
5. **Measure.** As `vigil-diag`: `fs_used_pct` (the action's precondition, DD-F-04), the diagnostics `disk_usage`, `largest_folders` and `disk_growth` (their DD-F-04 `summary_template` filled from the parsers' values; GiB as DD-F-04 rounds), and `fs_usage` (`avail_bytes`); and, with the spike's own read-only command `find /data/txlog_archive -maxdepth 1 -type f -name 'txlog_*.arc' -printf '%s\n'` (not a DD-F-04 operation), the number and total size of the injected files (`injected_files`, `injected_bytes`).
6. **Action** (`standard` and `read-only` only). As `vigil-action`: the registered action `purge-archived-txlogs` (operation `purge_old_archives` with DD-F-04's `parameter_values`). `TA` = the time the SSH command returned. Then `fs_used_pct` gives `used_pct_after_action`.
7. **After the action** (`standard`): read the recorder until `TA` + `resolve_after_action_s` (60 s) and then until 300 s (`no_refire_s`) after the last resolved entry of a storm alert. (`read-only`): read the recorder until `TA` + 60 s, then read Zabbix `problem.get` and Alertmanager `/api/v2/alerts` once.
8. **Clear.** `TC` = the time just before `POST /faults/clear` with the run's faults (MUST answer 200). Read the recorder until `TC` + `resolve_after_clear_s` (40 s).
9. **Settle.** As step 1 (quiet within 120 s, then 12 s); the run's observation ends here.

**Failure of a step.** When an inject or clear request does not answer 200, or an SSH command of steps 2, 5 or 6 fails (connection error, exit status other than 0, or output its parser cannot read), the run's check `steps` gets `passed` false and the error as `detail`; the spike then sends `POST /faults/clear` with the run's faults (once, its answer only logged), writes the result file with `finished` true and `passed` false, and exits 1 without starting another run. The same applies when `quiet_before` fails (then no fault was injected, the clear is still sent). A failed check of the table below other than `quiet_before` and `steps`, and a failed connection check, does not stop the spike: the remaining runs still run. For a run that stopped before `T0`, `t0`, `action_end` and `clear_at` are null and every value of `measured`, `timing` and `counts` is null; a run that stopped later keeps the values it reached and has null for the rest. A stopped run's `checks` holds every check of its kind: `quiet_before` and `steps` as defined (`steps` passes when no request or SSH command of the run failed, so it passes when only `quiet_before` failed), the checks whose observation finished before the stop as evaluated, and every other check with `passed` false and `detail` `not evaluated: run stopped at step {n}`.
