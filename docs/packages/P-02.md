## 2. Goal

Give every later package a working base: the shared value types, the PostgreSQL database with its two roles and pgvector, Flyway migrations per schema run by a separate `migrate` start, the event store of Spring Modulith, the start-up rules of a single `vigil-app` process (lock, restart procedure, readiness), JSON logs, the enforcement tests that read the database, and a Testcontainers database that every later `*IT` test uses. After this package, `vigil-migrate` then `vigil-app` start against a real PostgreSQL 17 with pgvector, and nothing product-specific exists yet.

### 6.2 `vigil.shared` (AR-R-06)

All types directly in package `vigil.shared` (no sub-packages, so `ModuleStructureTest`'s check that `shared` has no named interface keeps holding), no dependency on any module. The public top-level types are exactly these 13, one per item of the AR-R-06 list; component types the list needs are nested inside them:

| AR-R-06 item | Type | Content |
| --- | --- | --- |
| identifier | `Ids` | `static UUID newId()`: a UUID version 7 (RFC 9562): 48-bit Unix time in milliseconds from `System.currentTimeMillis()`, version `0111`, variant `10`, a 12-bit counter in `rand_a` and 62 random bits from `SecureRandom` in `rand_b` (RFC 9562 Section 6.2, Method 1). The counter starts at a random value below 2048 in each new millisecond; when the current millisecond is not later than the last one used (same millisecond, or the clock went back), the last millisecond is kept and the counter is increased; when the counter would pass 4095, the millisecond used is increased by 1. So ids made by one process are strictly increasing. No library. |
| key | `Key` | `record Key(String value)`; the constructor rejects `null` and any value not matching `^[A-Za-z0-9._-]{1,64}$` with `IllegalArgumentException`; `toString()` returns `value`; `Comparable<Key>` by Unicode code points (DM-C-01). |
| actor | `Actor` | DM-V-01: `record Actor(Kind kind, UUID userId, String module)` with nested `enum Kind { USER, MODULE }`; for `USER`, `userId` set and `module` `null`; for `MODULE`, `module` 1 to 40 characters and `userId` `null`; factories `Actor.user(UUID)`, `Actor.module(String)`. |
| tenant identifier | `TenantId` | `record TenantId(UUID value)`, `value` not `null`. |
| clock | `Timestamps` | `static Instant now(Clock clock)`: `clock.instant()` truncated to milliseconds (AR-P-01, DM-C-08); nested `@Configuration public static class ClockConfiguration` with one bean `Clock clock()` returning `Clock.systemUTC()`. Tests replace the bean with a fixed clock. |
| canonical JSON and hashing | `CanonicalJson` | `static String canonicalize(String json)` (RFC 8785, with `java-json-canonicalization`); `static String sha256Hex(byte[] bytes)`; `static String sha256HexOfCanonical(String json)`: SHA-256 over the UTF-8 bytes of the canonical form; 64 lowercase hexadecimal characters (AR-P-03). |
| error type | `VigilError` | `class VigilError extends RuntimeException` with nested `enum Code` holding exactly the codes of AR-I-03 with their HTTP status and wire text: `BAD_REQUEST` 400 `bad_request`; `SESSION_ENDED` 401 `session_ended`; `NOT_SIGNED_IN` 401 `not_signed_in`; `BAD_TOKEN` 401 `bad_token`; `FORBIDDEN` 403 `forbidden`; `NOT_FOUND` 404 `not_found`; `UNKNOWN_HOST` 404 `unknown_host`; `CONFLICT` 409 `conflict`; `TOO_LARGE` 413 `too_large`; `REFUSED` 422 `refused`; `INVALID` 422 `invalid`; `DEPENDENCY_FAILED` 503 `dependency_failed`; `STARTING` 503 `starting`. ### 6.3 Configuration and migrations

- `app/src/main/resources/application.properties` adds (complete list): `spring.config.import=optional:configtree:${VIGIL_SECRETS_DIR:/run/secrets/vigil}/`; `spring.datasource.url=jdbc:postgresql://${VIGIL_DB_HOST:vigil-db}:${VIGIL_DB_PORT:5432}/${VIGIL_DB_NAME:vigil}`; `spring.datasource.username=vigil_app`; `spring.datasource.password=${vigil-db-app}`; `spring.datasource.hikari.maximum-pool-size=20`; `spring.flyway.enabled=false`; the four settings of AR-R-13; `server.address=${vigil.http.bind-address:127.0.0.1}`; `server.forward-headers-strategy=native`; `management.endpoints.web.exposure.include=health`; `management.endpoint.health.probes.enabled=true`; `logging.structured.format.console=ecs`; `spring.main.banner-mode=off`.
- `app/src/main/resources/application-migrate.properties` (profile `migrate`, the unit `vigil-migrate`): `spring.main.web-application-type=none`; `spring.datasource.username=vigil_owner`; `spring.datasource.password=${vigil-db-owner}`; `spring.flyway.enabled=true`; `spring.flyway.locations=classpath:db/migration` (Flyway scans the sub-folders); `spring.flyway.schemas=` the 23 schemas of AR-P-04 in AR §7.1 order (`audit`, `tenancy`, `identity`, `connectors`, `runner`, `servicemap`, `intake`, `ai_gateway`, `knowledge`, `incidents`, `investigation`, `notifications`, `ticketing`, `routing`, `correlation`, `recovery`, `diagnostics`, `actions`, `engine`, `workflows`, `reporting`, `setup`, `platform`); `spring.flyway.default-schema=platform` (the history table is `platform.flyway_schema_history`); `spring.flyway.create-schemas=true`; `spring.flyway.connect-retries=30`; `spring.flyway.connect-retries-interval=2s`. In this profile no bean of Sections 6.5 and 6.6 is created (`@Profile("!migrate")`).
- `VigilApplication.main`: runs the application; when the started context has the profile `migrate` active, it calls `System.exit(SpringApplication.exit(context))`, so `vigil-migrate` stops with exit code 0 after the migrations; a failed migration fails the start and the process exits with a non-zero code.
- `vigil-app` (no profile) never holds the owner password: its secret directory holds only `vigil-db-app`; `vigil-migrate`'s holds only `vigil-db-owner` (AR-S-13).
- Migration (AR-P-05): `app/src/main/resources/db/migration/platform/V{yyyyMMddHHmmss}__platform_create_event_publication.sql` (UTC date and time when the file is written): the current, non-archive PostgreSQL DDL that `spring-modulith-events-jdbc` 2.1.1 ships (not the legacy variant, not the archive variant), with every table name and every `ON` target qualified as `platform.{table}` (index names stay unqualified; PostgreSQL creates an index in its table's schema); then `GRANT USAGE ON SCHEMA platform TO vigil_app;` and `GRANT SELECT, INSERT, UPDATE ON platform.event_publication TO vigil_app;` (AR-P-06: technical table).
- **Convention for every later migration** (record it in `README.md` under "Migrations"): a module's first migration grants `USAGE` on its schema to `vigil_app`; every `CREATE TABLE` is followed in the same file by the grant AR-P-06 gives its mutability class; a migration names only its own schema; every tenant-scoped table has `tenant_id uuid NOT NULL` and every secondary index on it starts with `tenant_id`; the table's row is added to the class table of Section 6.7.

### 6.4 `deploy/db/init/`

`deploy/db/init/10-vigil-roles.sh` (bash, `set -euo pipefail`, run by the `pgvector/pgvector` image's entrypoint from `/docker-entrypoint-initdb.d/` at first start, as the superuser `postgres`, with `POSTGRES_DB=vigil`; the superuser's password comes from `POSTGRES_PASSWORD_FILE` = `{secrets}/vigil-db-superuser`):

1. runs one `psql` session on database `vigil` (`ON_ERROR_STOP=1`) whose commands come from a quoted here-document (`<<'SQL'`, so bash expands nothing in it), and that reads the two passwords inside psql with the backquote form of `\set` (`\set owner_pw` followed by the command `cat {secrets}/vigil-db-owner` in backquotes, and `\set app_pw` the same for `vigil-db-app`), where `{secrets}` is `${VIGIL_SECRETS_DIR:-/run/secrets/vigil}`, so no password is on a command line, in the environment or in a log;
2. in that session, first `SET log_min_error_statement = panic;` and `SET log_statement = 'none';` (so a failing statement, which holds a password, is never written to the server log), then: `CREATE ROLE vigil_owner LOGIN PASSWORD :'owner_pw';` and `CREATE ROLE vigil_app LOGIN PASSWORD :'app_pw';`; `GRANT CONNECT, CREATE ON DATABASE vigil TO vigil_owner;` `GRANT CONNECT ON DATABASE vigil TO vigil_app;` `CREATE EXTENSION IF NOT EXISTS vector;`.

Nothing else (schemas are created by Flyway as `vigil_owner`). The file is committed with mode 0755 (`git update-index --chmod=+x`), so the image's entrypoint runs it rather than sourcing it.

### 6.5 Start-up of `vigil-app` (in `vigil.api`, internal, `@Profile("!migrate")`)

These classes live in `vigil.api`, the module that may depend on every other module (AR §7.1), because the restart procedure calls into several modules.

- **Advisory lock (AR-R-01):** during context start-up, one JDBC connection is opened with `DriverManager` using the datasource's URL, user and password (outside the Hikari pool, which keeps its 20 connections) and kept open; `SELECT pg_try_advisory_lock(4835711)` on it; when the answer is `false`, log at `ERROR` exactly `Another vigil-app is running against this database.` and fail the start-up (an exception from the bean's initialisation, so the process exits with a non-zero code). The connection is closed at shutdown. PostgreSQL advisory locks belong to one database.
- **Ready gate (AR-R-24):** a servlet filter that, while the ready flag is not set, answers every request except those to the path `/actuator/health/liveness` (any method) with status 503, `Content-Type: application/json` and exactly the body `{"error":{"code":"starting"}}`.
- **Restart procedure (AR-R-24):** an `ApplicationRunner` that runs, in order, seven methods `step1MarkInterruptedOperationRuns()`, `step2FailInterruptedSeedImports()`, `step3ResubmitIncompletePublications()`, `step4StartRunExecutors()`, `step5StartCorrelationWorkers()`, `step6StartScheduledWork()`, `step7SetReady()`, each logging one `INFO` line `restart step {n} done` (so the order can be checked). In this package: step 3 calls `IncompleteEventPublications.resubmitIncompletePublications(p -> true)`; step 6 registers the per-installation task (Section 6.6); step 7 sets the ready flag; steps 1, 2, 4 and 5 are empty, each with a comment naming the package that fills it (P-18, P-11, P-17, P-16). Later packages add their calls to these methods (through the owning module's `api`).
- **Bind address:** `vigil.http.bind-address` defaults to `127.0.0.1`; the demo installation sets `172.30.0.10` and a local installation `0.0.0.0` (BP-A-09) through their compose files.

### 6.6 Scheduling and the async executor (AR-R-23, AR-R-28, AR-R-14, AR-TM-08)

- One `ThreadPoolTaskScheduler` bean (type `TaskScheduler`) with pool size 4 and thread name prefix `vigil-scheduler-`, in `vigil.api` (internal). Modules inject Spring's `TaskScheduler` interface. No `@Scheduled` and no `@EnableScheduling` anywhere.
- Because a scheduler bean is also an `Executor`, `vigil.api` also declares the executor for `@Async` (and so for `@ApplicationModuleListener`): a bean named `taskExecutor` of type `SimpleAsyncTaskExecutor` with virtual threads (AR-T-01) and thread name prefix `vigil-async-`. Listeners never run on the scheduler's 4 threads.
- The per-installation task: `IncompleteEventPublications.resubmitIncompletePublicationsOlderThan(Duration.ofSeconds(60))`, registered by step (6) with fixed delay 60 s, first run 60 s after registration.
- Per-tenant tasks are registered with the same `TaskScheduler` by the modules that own them (later packages).

### 6.7 Test support (`app/src/test/java/vigil/testsupport/`, used by every later `*IT`)

- `VigilPostgres`: one Testcontainers `GenericContainer` per test JVM (a static singleton, started once) from image `pgvector/pgvector:{tag}@sha256:{digest}`, where `{tag}` is the latest `0.8.x-pg17` tag on the pin date and `{digest}` its multi-architecture index digest (BP-R-04). Environment (complete list): `POSTGRES_USER=postgres`, `POSTGRES_DB=vigil`, `POSTGRES_PASSWORD_FILE=/run/secrets/vigil/vigil-db-superuser` (not `POSTGRES_PASSWORD`; Testcontainers' `PostgreSQLContainer` always sets `POSTGRES_PASSWORD`, which the image refuses together with the file, so it is not used). Copied in before start: `../deploy/db/init/` to `/docker-entrypoint-initdb.d/`, and a temporary secrets folder created at test start with three random 24-character passwords (`vigil-db-superuser`, `vigil-db-owner`, `vigil-db-app`, BP-R-14), file modes as BP-R-26, to `/run/secrets/vigil/`. Wait until the log line `database system is ready to accept connections` has appeared twice (the image restarts once after its init scripts).
- `VigilDatabase`: hands out databases in that container. `VigilDatabase.main()` is database `vigil` (made by the init script); `VigilDatabase.fresh()` creates a new database `vigil_t{n}` as `postgres` with the same grants and extension as Section 6.4 step 2 (n counts up per JVM). Each database is migrated once by running the built JAR as the unit `vigil-migrate` does: a child process `{java} -jar target/vigil-app.jar` (`{java}` is the `java` executable of the running test JVM, from `ProcessHandle.current().info().command()`; test paths are relative to the `app` module directory, the working directory of Surefire and Failsafe) with `SPRING_PROFILES_ACTIVE=migrate`, `VIGIL_SECRETS_DIR` pointing to a folder holding only `vigil-db-owner`, and `VIGIL_DB_HOST`, `VIGIL_DB_PORT`, `VIGIL_DB_NAME` of that database; the child's exit code MUST be 0. It also offers a `postgres` `JdbcClient` per database for tests that read the catalogue.
- `VigilTestApp`: starts `vigil-app` in the test JVM (`SpringApplication` with `VigilApplication`, `server.port=0`, `VIGIL_SECRETS_DIR` of a folder holding only `vigil-db-app`, the database's host, port and name, and extra configuration classes the test passes) on its own thread, gives the port as soon as the web server is up (before the restart procedure has finished) and the `ConfigurableApplicationContext` once it exists (`context()`), and closes the application when the test class ends. **Every `*IT` that starts `vigil-app` uses `VigilTestApp` on its own `VigilDatabase.fresh()` database** (the one exception is `JsonLogIT`, which runs the JAR as a child process, also on its own fresh database) and does not use `@SpringBootTest` for the whole application, so no two applications share a database (AR-R-01) and no test leaves data for another.
- `DoubleDelivery` (AR-Q-05 helper): `assertSameResult(JdbcClient db, String schema, TransactionTemplate tx, Runnable deliverOnce)`: reads every row of every table of `schema` (ordered by all columns), runs `deliverOnce` in a new transaction (`tx`), reads again, runs it a second time in a new transaction, reads again, and asserts that the rows after the second delivery equal the rows after the first. `deliverOnce` calls the listener method on the target object (`AopTestUtils.getUltimateTargetObject(bean)`), so the call is synchronous and runs in the helper's transaction, as the listener's own transaction would.
- `app/src/test/resources/db/table-classes.csv`: the class table of AR-Q-06 and AR-Q-08. Header `table,class,tenant_scoped`; `class` is one of `immutable`, `stateful`, `configuration`, `revisioned`, `technical_rw`, `technical_none`. Rows in this package (complete list): `platform.event_publication,technical_rw,no`; `platform.flyway_schema_history,technical_none,no`.
- Existing test `WebAppServingIT` (P-01): rewritten to use `VigilTestApp` on a fresh database; it waits until a request no longer answers 503 (at most 30 s) before its checks, which stay the same.
