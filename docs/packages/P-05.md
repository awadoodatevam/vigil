## 2. Goal

Build everything the demo installation needs on AWS before the Vigil units exist (they follow in P-32), and prove the riskiest part of the hosting: live updates through the load balancer. `deploy/edge.sh` creates, idempotently with the AWS CLI from the owner's Mac, the network, security groups, roles, the two hosts with their bootstrap, the deployment bucket, the ECR repositories, the GitHub push role, the Route 53 zone of `vigil.solviclabs.com`, the certificate, the load balancer with its rules and the SES identity. `deploy/new-installation.sh` generates the installation's secrets into Parameter Store; `deploy/secrets.sh` writes them on the host per `deploy/units.yaml`; `deploy/build.sh` builds and pushes images; `deploy/deploy.sh` runs the deployment sequence of AR-H-11 on the main host through Systems Manager; `deploy/status.sh`, `deploy/gpu.sh` and `deploy/models.sh` operate the hosts and the Ollama models. In this package the main host runs only `vigil-embed` and an SSE test probe that stands at `vigil-app`'s address and port, so the owner can run AR-SP-01 from a browser in Pakistan.

### 6.1 General rules for the scripts

- Every script is bash with `set -euo pipefail`, passes `shellcheck`, and starts with a comment naming its purpose and this spec's section. Scripts run on the owner's Mac (`edge.sh`, `new-installation.sh`, `build.sh`, `deploy.sh`, `status.sh`, `gpu.sh`, `models.sh`, `tests/acceptance/p05_aws_check.sh`) use only what macOS's bash 3.2 offers (no associative arrays, no `mapfile`, no `${x,,}`, no empty arrays under `set -u`) and no GNU-only option of a command (`base64`, `sed -i`, `date`, `stat`, `mktemp` differ on macOS); they do text, JSON, encoding and time work with `python3` (standard library only, code that runs on Python 3.9 or later, the version of macOS's Command Line Tools). No script uses the AWS CLI's `--query`: they read `--output json` with `python3`. Scripts run on a host (`secrets.sh`, `deploy/main/host-deploy.sh`, `deploy/gpu/host-gpu.sh`, the user data) use Ubuntu 24.04's bash, `python3` and the packages the bootstrap installs.
- Mac scripts run from the repository root (they `cd` there from their own location, as `deploy/local.sh` does), export `AWS_REGION=us-east-1` (AR-T-23) and `AWS_PAGER=""` (no pager on a terminal), and use the AWS CLI's normal credentials (`AWS_PROFILE` chosen by the operator, CTX-D-041). Each first runs `aws sts get-caller-identity`; when it fails, the script prints "Sign in first: aws login --profile vigil, then export AWS_PROFILE=vigil (deploy/edge.md)." and exits 1. They need the AWS CLI 2.32 or later, `python3` (from the Command Line Tools), `dig` and `ssh-keygen` (macOS has these two) and, for `build.sh`, Docker with `buildx`.
- For the scripts of Section 6.15: an installation argument MUST match `^[a-z][a-z0-9-]{0,19}$` and, for Mac scripts, have a values file `deploy/values/{installation}.yaml` (host scripts do not check one); a release name MUST match `^[a-z0-9][a-z0-9.-]{0,39}$`; otherwise, and for wrong or missing arguments, the script prints its usage line (Section 6.15) and exits 2. The scripts that `run_on_host` runs are called only by those scripts, with fixed arguments, and do not check them.
- Shared Mac-side functions are in `deploy/lib/aws.sh` (sourced, not executed): the identity check, the region, the account ID, the registry address `{account id}.dkr.ecr.us-east-1.amazonaws.com`, the bucket name `vigil-{installation}-deploy-{account id}` (BP-A-21), finding an instance by its `Name` tag (states `pending`, `running`, `stopping`, `stopped`), and `run_on_host {instance id} {script file} [{file} …] -- [{argument} …]`: runs a script file of the repository on the host as root through Systems Manager (`AWS-RunShellScript`, execution timeout 3,600 s). Before sending, `run_on_host` waits until Systems Manager reports the instance `Online` (`describe-instance-information`, every 5 s, at most 60 attempts; otherwise "The {main|GPU} host is not reachable through Systems Manager." and exit 1; right after a start the agent needs a moment). The command is POSIX `sh` (Systems Manager runs it with `sh`, which is `dash` on Ubuntu: no `pipefail`, arrays or `[[`); it exports `AWS_REGION=us-east-1`, appends `/snap/bin` to `PATH`, writes the script and the listed files, each under its file name (their contents passed inline as base64, each at most 16 KiB; a larger file → "{file} is larger than 16 KiB." and exit 1 before sending) into a new folder `{VIGIL_ROOT}/run/{random name}/` (mode 0700, after `mkdir -p {VIGIL_ROOT}/run`), runs the script there with `bash` and the arguments, and removes the folder. `run_on_host` then waits for the command to end (polling `get-command-invocation` every 5 s, at most 730 attempts; `InvocationDoesNotExist` counts as still pending), prints its standard output and error, and returns its exit code; when the polling ends without a final status, or the status is not `Success` or `Failed` (Example: `TimedOut`, `Cancelled`), it prints "The command on the {main|GPU} host ended with status {status}." (`{status}` `unknown` when the polling ended) and returns 1. A main host that does not exist → "The main host does not exist yet (deploy/edge.sh)." and exit 1 (the GPU host's case: Section 6.10). The scripts that `run_on_host` runs (complete list; host scripts like `deploy/secrets.sh` and the user data, all shellchecked, all exporting `AWS_REGION=us-east-1` except the user data, which calls no AWS service): `deploy/hosts/marker.sh` (prints the bootstrap marker line, exit 1 when it is missing), `deploy/main/host-fetch.sh` (Section 6.8, which runs `deploy/main/host-deploy.sh`), `deploy/main/host-status.sh` (Section 6.9), `deploy/gpu/host-gpu.sh` and `deploy/gpu/host-gpu-status.sh` (Section 6.10), `deploy/hosts/model-update.sh` (Section 6.10), and `tests/acceptance/p05_host_check.sh` (Section 6.12). Systems Manager returns at most 24,000 characters of standard output and 8,000 of standard error, so host scripts keep progress output away from them: `docker compose pull --quiet`, and `ollama pull` writes to `{VIGIL_ROOT}/logs/ollama-pull.log`. A host that is not `running` → the message "The {main|GPU} host is {state}. Start it first (deploy/edge.md, or deploy/gpu.sh start for the GPU host)." and exit 1.
- AWS resources are named `vigil-{installation}-{part}` (Example: `vigil-demo-main`), except the VPC, internet gateway and route table (`vigil-{installation}`), the load balancer `vigil-alb` and the target groups `vigil-app` and `demo-control` (AR-H-05), the ECR repositories `{installation}/{image}`, the bucket (BP-A-21), the hosted zone and SES identity (`{demo_domain}`), and the OIDC provider (its URL). Every resource of Section 6.4 that has its own name in this list and takes tags gets `Name` = that name (the certificate: `vigil-{installation}`) and `vigil:installation={installation}`; listeners, listener rules, CIDR reservations and parameters are not tagged; the root volume and network interface of an instance get the instance's tags at launch (`--tag-specifications` for `instance`, `volume` and `network-interface`). Each inline policy has the name of its role.
- No script prints, logs or writes into the repository a secret value (SL-B-14): secret values exist only in Parameter Store, in memory of the script that makes or copies them, in a temporary folder with mode 0700 that the script removes on exit, and in the host's secret files; the ECR login token is held only by Docker until the logout.
- Host scripts export `AWS_REGION=us-east-1` themselves too (AR-T-23).
- Registry logins end with `docker logout {registry}` once the push or pull is done (the ECR token is valid 12 hours; it is kept only in Docker's credential store meanwhile).
- Tests replace the AWS CLI, Docker, `curl` and, where the machine has none, `ssh-keygen` with fakes on `PATH` (Section 7); scripts call them as `aws`, `docker`, `curl` and `ssh-keygen`. Two environment variables exist for tests (complete list; the non-root fallback of Section 6.7 is the third difference): host scripts take their base folder from `VIGIL_ROOT` (default `/srv/vigil`); and every wait goes through one function, `pause {seconds}` (in `deploy/lib/aws.sh` for Mac scripts, and defined the same way in each host script), which sleeps that long, or not at all when `VIGIL_TEST_FAST=1`. Every time limit is counted in attempts of a fixed interval (Example: 20 minutes = 240 attempts 5 s apart), so a fast test still ends.

### 6.4 `deploy/edge.sh {installation}` and `deploy/edge.md` (AR-H-03 to AR-H-06, AR-H-08, BP-A-06, BP-A-21)

`edge.sh` creates what is missing and sets what can drift, in this order (complete list). These parts of a resource are always reconciled with it, printing `{kind} {name}: set` when one was added or changed (complete list): the internet gateway's attachment, the route table's `0.0.0.0/0` route and its two subnet associations, the subnets' public-IPv4-on-launch attribute, the VPC's two DNS attributes, the role inside each instance profile. ### 6.11 The SSE probe (`spikes/sse-probe/`; AR-SP-01)

`probe.py` (Python 3.12, standard library only, a `BaseHTTPRequestHandler` with `protocol_version = "HTTP/1.1"` on a `ThreadingHTTPServer`, one thread per connection; fixed answers carry `Content-Length`, streams use `Transfer-Encoding: chunked`, one chunk per write, as `vigil-app`'s servlet stream does), listening on `PROBE_ADDRESS` (default `127.0.0.1`) and `PROBE_PORT` (default 8080). Timings from the environment, for tests (defaults): `PROBE_PING_SECONDS` 15, `PROBE_CLOSE_SECONDS` 300, `PROBE_NOTICE_SECONDS` 3. Paths (complete list; anything else 404 with no body):

- `GET /` → `index.html` (`text/html; charset=utf-8`, `Cache-Control: no-cache`).
- `GET /actuator/health/liveness` and `GET /actuator/health` → 200 `{"status":"UP"}` (the target group's health check and `status.sh`; the load balancer answers 404 for `/actuator*` from outside).
- `GET /probe/time` → 200 `{"server_ms": {milliseconds since the epoch, with fractions}}`, `Cache-Control: no-store`.
- `GET /probe/info` → 200 `{"local_address": "{the local address of the request's socket}", "forwarded_for": {the X-Forwarded-For header as a JSON string, or JSON null}}`; the result file copies both.
- `GET /probe/stream?mode=notices|idle` → a stream as AR-I-04: status 200, `Content-Type: text/event-stream;charset=UTF-8`, `Cache-Control: no-cache`; first `retry: 1000\n\n`; `: ping\n\n` every `PROBE_PING_SECONDS`; in mode `notices` also, at n × `PROBE_NOTICE_SECONDS` after the open while that time is less than `PROBE_CLOSE_SECONDS` (99 per connection with the defaults), `event: change\ndata: {"seq":{n},"sent_ms":{server_ms}}\n\n` with `n` from 1 per connection; the stream ends at `PROBE_CLOSE_SECONDS` after the open. A missing or other `mode` → 400 with no body. Each write is flushed; a failed write ends the stream.

`index.html` (one file, plain JavaScript, no external resource): a "Start" button and a result area. The test, started by "Start", in order: (1) `GET /probe/info`; (2) clock offset: 20 requests of `/probe/time`, each timed with `performance.timeOrigin + performance.now()`; of the request with the smallest round trip, `offset_ms = server_ms − (t_send + t_receive) / 2`; (3) at the same time two `EventSource`s, `notices` and `idle`; for each `change` event, `delay_ms = t_receive + offset_ms − sent_ms`; the test ends when 200 notices have arrived and the `idle` stream has been reopened once (or after 15 minutes); when the end condition is met while a stream is between an `error` and its next `open`, the page waits up to 5 s for that `open` before ending; (4) the offset is measured again the same way; (5) the page shows PASS or FAIL with each criterion, and a "Download result" link that saves `P-05-AR-SP-01.json`. The page does not reopen a stream that `EventSource` has closed for good (after a non-200 answer); such an `error` without a later `open` (also a stream still in error when the test ends) goes into `reconnects` with `gap_ms` null and `at_s` the `error` event's time since "Start", and makes `reconnect_5000` false. Pass criteria (complete list, AR-SP-01, with their keys in `criteria`): `local_address` — `local_address` is `172.30.0.10`; `https_origin` — the page was loaded with `https:` from `demo.vigil.solviclabs.com`; `notices_200` — 200 notices arrived; `max_delay_1000` — the largest `delay_ms` is at most 1,000; `idle_open_295` — the `idle` stream had no `error` event earlier than 295 s after its first `open` (no closing by the load balancer while idle for 5 minutes with heartbeats); `reconnect_5000` — every reconnection of either stream (from an `error` event to the next `open`) took at most 5,000 ms. Result file (JSON, complete list of keys): `started_at` and `finished_at` (UTC ISO 8601), `page_url`, `user_agent`, `local_address`, `forwarded_for`, `offset_ms_start`, `offset_ms_end`, `rtt_min_ms` (of the start measurement), `notices` (`count`, `max_delay_ms`, `delays_ms` list; every `delay_ms` uses `offset_ms_start`), `idle` (`first_error_after_s`, counted from the idle stream's first `open`; null when it had none), `reconnects` (list of `{stream, at_s, gap_ms}`: the stream's name, the `open` event's time since "Start", the gap from the `error` event), `criteria` (one boolean per criterion above), `passed`.

`Dockerfile`: as `demo/faults/Dockerfile` (the same `ubuntu:24.04` digest, the optional CA secret, `python3`, `ca-certificates`, `tzdata`), copying `probe.py` and `index.html` to `/opt/probe/`, `USER 10001`, `ENTRYPOINT ["/usr/bin/python3", "/opt/probe/probe.py"]`. `deploy/build.sh` builds it for the demo installation; `deploy/images.sh --test` also builds it as `vigil/sse-probe:local` for the image test of `test_probe.py` (BP-R-04). `README.md` describes the test, its criteria and the result file. `spikes/README.md` and `spikes/results/README.md` add the probe's rows.
