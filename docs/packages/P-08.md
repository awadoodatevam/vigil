## 2. Goal

Build the three platform modules every other module stands on, as module cores (no HTTP operation): `vigil-audit` keeps the append-only audit log with a sequence per tenant and answers filtered, paged queries; `vigil-tenancy` keeps tenants with their state machine, tenant settings, and the installation-level tenant aliases that decide which tenants are active, and announces each alias change (AR-E-14); `vigil-identity` keeps users, teams, memberships and permission grants, logs users in with Argon2id-hashed passwords, keeps login sessions with their lifetime and idle limit, answers permission and membership questions, and runs the session expiry sweep for active tenants only. The seed import operations of parts 1 and 2 (DM-R-56) import the content of DD-F-01; their registration in the import registry is P-11. The gate's Docker daemon gets a registry mirror (BP-O-04, CTX-D-037).

### 6.1 General rules for the three modules

- Every public type of a module is in its `api` package (AR-R-04): the service interfaces, the request and result records, enums, the event records and the import interface. Every other class is package-private or in the module's root package and is not referenced from another module. The `@ApplicationModule(allowedDependencies = …)` declarations of P-01 stay unchanged.
- Writing operations are `@Transactional(propagation = REQUIRED)`; reads are `@Transactional(readOnly = true)`. No operation of this package makes an external call.
- Time comes from the `Clock` bean through `Timestamps.now(clock)` (P-02); identifiers from `Ids.newId()`.
- Persistence: Spring Data JDBC entities or `JdbcClient` SQL (AR-T-04), each naming only its module's schema (AR-R-07). Every query of a tenant-scoped table filters by `tenant_id` (DM-C-10).
- A caller's programming error (a `null` where a value is required, a value outside its type) throws `IllegalArgumentException` with a message naming the field. A domain refusal throws `VigilError` with the code this section names. A request about a tenant, user or team that does not exist answers as the method's text says (an empty result or `VigilError` `NOT_FOUND`).
- Logging: nothing at `INFO` or above per request; never a password, token, token hash or password hash.

### 6.2 Migrations and the class table

Three migration files, each with its own UTC date and time in the name (AR-P-05), following the conventions of `README.md` "Migrations": `audit/V{ts}__audit_create_audit_event.sql`, `tenancy/V{ts}__tenancy_create_tenancy_tables.sql`, `identity/V{ts}__identity_create_identity_tables.sql`, under `app/src/main/resources/db/migration/`. Each starts with `GRANT USAGE ON SCHEMA {schema} TO vigil_app;` and grants after every `CREATE TABLE` the privileges of the table's class (AR-P-06). Column types follow AR-P-01: `Key` → `varchar(64)` with the `CHECK` of AR-P-01; `Text(n)` → `varchar(n)`; `Timestamp` → `timestamptz`; `Enum` → `varchar(40)` with a `CHECK (… IN (…))` of exactly the listed values; `Actor` → three columns `{f}_kind varchar(40) NOT NULL CHECK ({f}_kind IN ('user','module'))`, `{f}_user_id uuid`, `{f}_module varchar(40)`, with `CHECK (({f}_kind = 'user' AND {f}_user_id IS NOT NULL AND {f}_module IS NULL) OR ({f}_kind = 'module' AND {f}_module IS NOT NULL AND {f}_user_id IS NULL))`. Required fields are `NOT NULL`. Foreign keys only within the schema.

### 6.3 `vigil.audit` (PM-M03, DM-E-08)

#### 6.3.1 Public types (`vigil.audit.api`, complete list)

- `AuditEventType` — enum of the 18 types of DM-E08-R1 in its order, each with `key()` returning the lower-case key (Example: `INCIDENT_CREATED` → `incident_created`).
- `ConfigurationArea` — enum of the 10 values of DM-V-11 in its order, with `key()`.
- `AuditEntry` — record `(TenantId tenantId, Instant occurredAt, Actor actor, AuditEventType eventType, String subjectType, UUID subjectId, UUID incidentId, String summary, String detailsJson)`; `incidentId` and `detailsJson` may be `null`.
- `AuditRecorded` — record `(UUID id, long sequence)`.
- `AuditActorFilter` — record `(Kind kind, UUID userId)` with nested `enum Kind { USER, AUTOMATIC }`; `USER` needs `userId`; `AUTOMATIC` matches every module actor (DC-S11-02 "{product} (automatic)").
- `AuditPosition` — record `(Instant occurredAt, long sequence)`: the position after which the next page starts.
- `AuditQuery` — record `(Instant from, Instant to, AuditActorFilter actor, Set<AuditEventType> eventTypes, Set<UUID> incidentIds, String subjectType, UUID subjectId, int limit, AuditPosition after)`; every filter may be `null` or empty (no filter); `subjectType` and `subjectId` are both set or both `null`; `limit` from 1 to 50.
- `AuditEventView` — record `(UUID id, long sequence, Instant occurredAt, Actor actor, AuditEventType eventType, String subjectType, UUID subjectId, UUID incidentId, String summary, String detailsJson)`.
- `AuditPage` — record `(List<AuditEventView> items, long total, AuditPosition next)`; `next` is `null` when no further row exists.
- `AuditService` — interface with exactly two methods: `AuditRecorded append(AuditEntry entry)` and `AuditPage query(TenantId tenantId, AuditQuery query)`. No other method (PM-M03-02, DM-E08-R2).

#### 6.3.2 Behaviour

- `append` (PM-M03-01, AR-R-11): `@Transactional(propagation = REQUIRED)`, so a call inside the caller's transaction commits or rolls back with it. Checks (each failure `IllegalArgumentException`): every non-nullable component set; `subjectType` 1 to 40 characters; `summary` 1 to 300 characters; `detailsJson`, when set, a JSON object (parsed with the application's Jackson 3 `tools.jackson.databind.json.JsonMapper` bean, which Spring Boot 4 provides); for `CONFIGURATION_CHANGED` it MUST be set and have exactly the keys `area` (the `key()` of a `ConfigurationArea`), `before` and `after` (any JSON values, DM-C-07). It stores the event with `occurred_at` = `occurredAt` truncated to milliseconds, `created_at` = now, the sequence from the identity column (strictly increasing per tenant, DM-E-08; gaps are allowed), and returns its id and sequence.
- `query` (PM-M03-03): the tenant's events that match every given filter: `occurred_at` ≥ `from` and ≤ `to`; actor (a user id, or every module actor); event type in `eventTypes`; `incident_id` in `incidentIds`; subject type and id. Ordered newest first: `occurred_at` descending, then `sequence` descending (DC-S11-03). It returns at most `limit` rows after the position `after` (rows strictly after it in that order), the number of all matching rows in `total` (independent of `after` and `limit`), and `next` = the position of the last returned row when more rows follow.

#### 6.4.2 Behaviour

- **Transitions (DM-SM-01).** `markReady` and `markFailed` lock the tenant row (`SELECT … FOR UPDATE`, AR-R-12), then check in this order: unknown tenant → `VigilError` `NOT_FOUND`; not `provisioning` → `VigilError` `CONFLICT` with message `Tenant {id} is {state}.` (`{state}` the `key()` of its state, Example: `Tenant 0199… is ready.`); for `markReady` only, no settings → `VigilError` `CONFLICT` with message `Tenant {id} has no settings.`. No other transition exists; `ready` and `failed` are final.
- **Aliases (DM-E-83, AR-B-01).** `setAlias`: `hostName` is lower-cased (`Locale.ROOT`) and MUST then be 1 to 253 characters, each one of `a`–`z`, `0`–`9`, `.` and `-` (otherwise `VigilError` `BAD_REQUEST` with message `host name: 1 to 253 characters of a-z, 0-9, . and -`); `setBy` 1 to 40 characters; the tenant MUST exist (`NOT_FOUND`) and be `ready`, otherwise `VigilError` `REFUSED` with message `The tenant is not ready.` and details `{"refusal": "tenant_not_ready"}` (AR-I-98 answers 422). In its transaction it first runs, as a statement of its own, `SELECT pg_advisory_xact_lock(hashtext('tenancy.tenant_alias'), hashtext(:host_name))` (the two-key form, whose keys never meet the one-key lock of AR-R-01), then reads the host's highest revision in a new statement, so two calls for one host get consecutive revisions; it inserts the next revision (1 for a new host) with `set_at` = now, publishes `TenantAliasChanged(hostName, tenantId, previous tenant of the host or null)` in the same transaction (AR-R-13), and returns the revision. Setting a host to the tenant it already points to still creates a revision and publishes the event.
- **Resolution.** `resolveHost` lower-cases its argument and returns the tenant of the host's highest revision, or empty (also for a name that `setAlias` would refuse). `activeTenants` returns every tenant that the highest revision of some host points to (Section 3 "Active tenant"); `isActive` answers the same for one tenant. `publicHostName` returns the host name of the alias revision with the latest `set_at` among the revisions whose tenant is this tenant (on equal `set_at`, the higher `revision`, then the smaller `host_name`), or empty.
- **Import of part 1 (AR-B-11, DM-R-57).** `importPart` checks, collecting every problem before it refuses (complete list, each problem one text as written here): the tenant exists and is `provisioning` (`tenant is not provisioning`); the tenant has no settings yet (`tenant settings already exist`); `customer_name` 1 to 100 characters (`customer_name: 1 to 100 characters`); `environment_label` at most 100 characters (`environment_label: at most 100 characters`); `product_display_name` 1 to 60 characters (`product_display_name: 1 to 60 characters`); when `logo` is set, `mediaType` is `image/png` or `image/svg+xml` (`customer_logo: media type image/png or image/svg+xml`) and the bytes are 1 to 524,288 bytes (512 KB read as 512 × 1024 bytes; `customer_logo: 1 byte to 512 KB`). A `null` `customerName` or `productDisplayName` is reported as its length problem; a `null` part is an `IllegalArgumentException`. With one or more problems it throws `VigilError` `INVALID` with message `Part tenant settings refused.` and details `{"problems": [texts in the order above]}` and stores nothing. Otherwise it stores the settings record (an empty `environment_label` is stored as `null`; `updated_by` = `Actor.module("vigil-setup")`, the actor of installation operations, AR-S-07; `created_at` = `updated_at` = now) and returns an empty map (part 1 creates no handles; `handles` is not read). It writes no audit event (the import's one event is `vigil-setup`'s, DM-E08-R3) and publishes no event.

### 6.5 `vigil.identity` (PM-M02, DM-E-03 to DM-E-07)

#### 6.5.1 Public types (`vigil.identity.api`, complete list)

- `Permission` — enum of the 10 permissions of DM-E06-R1 in its order, with `key()` (Example: `APPROVE_ACTION` → `approve_action`).
- `UserView` — record `(UUID id, Key username, String displayName, boolean active, Set<Permission> permissions, Set<Key> teamKeys)`: `permissions` are the user's active grants; `teamKeys` the keys of the active teams in which the user has an active membership.
- `TeamView` — record `(UUID id, Key teamKey, String name, boolean active)`.
- `NewSession` — record `(UUID sessionId, String token, Instant expiresAt, UserView user)`; `token` is the session token base64url-encoded without padding (43 characters), returned only here.
- `SessionCheck` — record `(Status status, UUID sessionId, UserView user)` with nested `enum Status { ACTIVE, ENDED, UNKNOWN }`; `sessionId` and `user` are set only for `ACTIVE`.
- `IdentityPart` — record `(List<TeamPart> teams, List<UserPart> users, List<MembershipPart> memberships, List<GrantPart> grants)`, the content of seed part 2 (DM-R-56 (2)), with nested records `TeamPart(String teamKey, String name)`, `UserPart(String username, String displayName, String password)`, `MembershipPart(String teamKey, String username)`, `GrantPart(String username, List<String> permissions)`. Keys and permissions arrive as text, so the import reports every bad value as a problem.
- `IdentityService` — interface (complete list of methods):
  - `Optional<NewSession> login(TenantId tenantId, String username, String password)` (PM-M02-02, DM-SM02-T1).
  - `SessionCheck authenticate(TenantId tenantId, String token)`.
  - `void logout(TenantId tenantId, UUID sessionId)` (DM-SM02-T2).
  - `boolean hasPermission(TenantId tenantId, UUID userId, Permission permission)` (PM-M02-03).
  - `boolean isMember(TenantId tenantId, UUID userId, Key teamKey)` (PM-M02-03).

#### 6.5.2 Passwords and tokens

- **Hashing (AR-S-01).** Spring Security's `Argon2PasswordEncoder` constructed as `new Argon2PasswordEncoder(16, 32, 1, 19456, 2)` (salt 16 bytes, hash 32 bytes, parallelism 1, memory 19,456 KiB, 2 iterations), with Bouncy Castle; `password_hash` holds its encoded form, which begins `$argon2id$v=19$m=19456,t=2,p=1$`. `app/pom.xml` adds (complete list): `org.springframework.security:spring-security-crypto` (version from the Spring Boot BOM; not the security starter, which P-09 adds with its filter chain) and `org.bouncycastle:bcprov-jdk18on` (the Spring Boot BOM does not manage it: the latest release on the pin date).
- **Session token (AR-S-02, AR-P-03).** 32 bytes from one `SecureRandom` instance; given to the caller base64url-encoded without padding; `token_hash` = SHA-256 of the 32 bytes as 64 lowercase hexadecimal characters (`CanonicalJson.sha256Hex`). `authenticate` decodes the token; text that is not base64url or not 32 bytes is `UNKNOWN`.

#### 6.5.3 Behaviour

- **Login (DM-SM02-T1, DM-E01-R1, DM-E06-R2).** Empty result, and nothing stored, when `username` is not a valid `Key`, when the tenant is not `ready` (asked of `vigil-tenancy`, PM-I-02), when no user has that username in the tenant, when the user is not active, or when the password does not match its hash. Otherwise a session with `state` `active`, `expires_at` = now + 12 h, `last_activity_at` = now (AR-TM-03), and the result with the token and the user. No permission is needed (DM-E06-R2). A login writes no audit event (DM-E08-R1 has no type for it).
- **Authenticate (DM-SM02-T3, AR-S-02).** Finds the session by `(tenant_id, token_hash)` and locks it (`SELECT … FOR UPDATE`); none → `UNKNOWN` (also a session of another tenant, SL-B-01). `ended` → `ENDED`. `active` but now ≥ `expires_at`, or now − `last_activity_at` > 2 h → moves it to `ended` with `end_reason` `expired` and `ended_at` = now, then `ENDED`. Otherwise `ACTIVE` with the session id and the user; `last_activity_at` is set to now only when it is at least 60 s old.
- **Logout (DM-SM02-T2).** An `active` session of the tenant → `ended` with `end_reason` `logout`, `ended_at` = now. An `ended` or unknown session: nothing changes.
- **Questions.** `hasPermission`: true only for an active user with an active grant of that permission. `isMember`: true only for an active user with an active membership in an active team with that key. `teamMembers`: the active users with an active membership in the active team with that key, ordered by username in Unicode code-point order (`Key`'s order, DM-C-01; sorted in Java, not by the database collation); empty when the team does not exist or is not active. `user`, `userByUsername` and `team`: by id, username or key within the tenant, active or not.
- **Import of part 2 (AR-B-11, DM-R-57, AR-S-06).** `importPart` checks, collecting every problem before it refuses (complete list; `{x}` is the value concerned): the tenant exists and is `provisioning` (`tenant is not provisioning`); the tenant has no team, user, membership or grant yet (`identity records already exist`); every `teamKey` and `username` is a valid `Key` (`teams: {x} is not a valid key`, `users: {x} is not a valid key`); team keys unique (`teams: {x} appears more than once`); usernames unique (`users: {x} appears more than once`); team names 1 to 100 characters (`teams: name of {x}: 1 to 100 characters`); display names 1 to 100 characters (`users: display_name of {x}: 1 to 100 characters`); every user has a non-empty password (`users: no password for {x}`); every membership names a team and a user of the part (`memberships: unknown team {x}`, `memberships: unknown user {x}`) and no (team, user) pair appears twice (`memberships: {team} {user} appears more than once`, DM-E05-R1); every grant names a user of the part (`permission_grants: unknown user {x}`) and only permissions of DM-E06-R1 (`permission_grants: unknown permission {x}`), and no (user, permission) pair appears twice (`permission_grants: {user} {permission} appears more than once`, DM-E06-R3). Within one kind, problems follow the first appearance of their value in the part, and each distinct problem text appears once (so a value that appears three or more times gives one "appears more than once" problem, and the same unknown team, user or permission named twice gives one problem). A `null` key, username, name, display name or permission is reported as the problem its rule names, with `{x}` written `null`; a `null` part or list is an `IllegalArgumentException`. With one or more problems it throws `VigilError` `INVALID` with message `Part identity refused.` and details `{"problems": [texts in the order above, within one kind in the order of the part]}`, and stores nothing. Otherwise it stores every team, user (password hashed as Section 6.5.2; the password itself is not kept), membership and grant with `active = true` (DD-R-07 (3)) and `created_at` = `updated_at` = now, and returns an empty map (part 2 creates no handles). It writes no audit event and publishes no event.

#### 6.5.4 Scheduled work and the AR-E-14 listener (AR-R-19, AR-R-23, DM-R-70, PM-R-11)

- The class that holds the sweep registrations (the implementation of `SessionExpiry`) and the listener are `@Profile("!migrate")`, like P-02's start-up classes, because the `migrate` profile has no `TaskScheduler`.
- The sweep of a tenant is registered with Spring's `TaskScheduler` (P-02) as `scheduleWithFixedDelay(task, taskScheduler.getClock().instant(), Duration.ofSeconds(60))` (first run at once, then every 60 s) and runs in its own transaction: every `active` session of that tenant with now ≥ `expires_at` or now − `last_activity_at` > 2 h moves to `ended` with `end_reason` `expired` and `ended_at` = now (DM-SM02-T3).
- `matchActiveTenants()` (synchronized) reads `TenantService.activeTenants()`, registers the sweep of each active tenant that has none, and cancels (`ScheduledFuture.cancel(false)`) the sweep of each tenant that is no longer active. The internal class that holds the registrations offers, package-private for tests, `Set<TenantId> scheduledTenants()` and `void sweep(TenantId tenantId)` (one sweep run now).
- The listener: an `@ApplicationModuleListener` method in `vigil.identity` that receives `TenantAliasChanged` and calls `matchActiveTenants()`; it makes no tenant check (AR-R-14, installation-level event) and writes no record, so a second delivery gives the same result (AR-Q-05).
- `vigil.api.RestartProcedure.step6StartScheduledWork()` calls `SessionExpiry.matchActiveTenants()` after it registers the per-installation task (AR-R-24 (6)).
