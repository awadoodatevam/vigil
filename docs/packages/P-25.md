### 6.1 General rules

- **Composition (AR-I-06, CTX-D-077 (2)).** `vigil-api` holds no record and no business rule and reads no table. An answer combines module reads. Ordering, grouping, reversing, counting and finding a position over the whole result of a module read that returns a bounded set (an incident's runs, step executions, timeline entries, memberships, notified teams, escalations, evidence; a run's timers; a tenant's sources; one hypothesis computation's keys) are done by `vigil-api` while combining. A count, sum, limit or page over a set that grows with alert or incident volume (a tenant's alerts or incidents) is a module read (Section 6.2).
- **Owner modules (CTX-D-077 (7)).** Each operation asks the modules of its AR §10.2 row, read with DC-U-06: AR-I-22 also asks `vigil-servicemap` (via component names); AR-I-29 also asks `vigil-identity` (team names of the canvas cards); AR-I-30 also asks `vigil-identity` (actor display names) and `vigil-correlation` (the grouping's hypothesis); AR-I-24 asks `vigil-runner` nothing (CTX-D-077 (4)).
- **Access.** Every operation of this package is `@RequiresPermission(Permission.VIEW)` (AR-I-07): 401 without a session, 403 `forbidden` without `view`, checked before any module is asked.
- **Answers** are Java records in `vigil.api` with `@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy.class)`, as P-09 Section 6 writes them; every listed field is always present, empty values as `null`, empty lists as `[]`; instants with `ApiTimes.format`; durations as whole seconds; ids as UUID text; enumerations as their lower-case keys. Every list in an answer is in the order this spec states.
- **Incidents of the workspace.** The handlers of AR-I-22 to AR-I-24 and AR-I-29 to AR-I-31 take `@PathVariable("incident_id") String`; a text that is not a UUID in the 8-4-4-4-12 form, an id of no incident of the request's tenant, or an incident in state `forming`: `VigilError` `NOT_FOUND` (404 `not_found`; DC-S03-01, DM-E32-R3; CTX-D-077 (5)). A `merged` incident: AR-I-22 answers `{"merged_into_incident_id"}` (Section 6.6); the other five answer 404 `not_found` (the web opens the survivor, DC-S03-01).
- **Names (DC-U-06).** Three shared answer types (complete list): `TeamName` `{"team_key", "name"}`, the name from `IdentityService.team` (the key when the team does not exist); `UserName` `{"user_id", "display_name"}`, the display name from `IdentityService.user` (the id as text when the user does not exist); `ActorName` `{"kind": "user" or "module", "user_id" (`null` for a module), "display_name" (the user's, or the id as text when the user does not exist; `null` for a module)}` from a `vigil.shared.Actor` (DM-V-01; a module actor is shown as "{product} (automatic)" by the web). The Java names `TeamName`, `UserName` and `ActorName` are also the schema names in the OpenAPI file (the existing `User` is the session user). One answer asks for each team, user and component name once. Component names come from `ServiceMapService.component` (current generation): the name, or the key when the component is not in the current service map.
- **Times.** `Timestamps.now(clock)` with the `Clock` bean wherever "now" is used.
- "Code point order" is `String` order by Unicode code point, as `ActionTexts.CODE_POINTS` (P-24) compares; ties of names are broken by the key.

### 6.2 Module reads (complete list; DC-R-08, PM-R-10)

Each is a read declared on the module's service interface (`api` package) and implemented in the module's service class, with its SQL in the module's records class (`IntakeRecords`, `IncidentRecords`, `EngineRecords`): one query of its own schema (at most two for `stages`), filtered by `tenant_id`, without `@Transactional`, as the module's existing reads are; `null` arguments: `IllegalArgumentException` as the module's other reads; no audit event; returned lists unmodifiable.

**`vigil-intake` (`IntakeService`):**

- `long alertsReceivedSince(TenantId tenantId, Instant from)` — the number of the tenant's alerts with `first_received_at >= from` (DM-E-21).
- `List<AlertView> latestAlerts(TenantId tenantId, int limit)` — the tenant's alerts by `first_received_at` descending, then `sequence` descending, at most `limit`; `limit` from 1 to 50, else `IllegalArgumentException`.

**`vigil-incidents` (`IncidentService`):**

- `List<IncidentView> incidentPage(TenantId tenantId, Set<IncidentState> states, Long beforeNumber, int limit)` — the incidents in one of `states` that have a `number`, with `number < beforeNumber` when `beforeNumber` is not `null`, by `number` descending, at most `limit`; `states` non-empty and `limit` from 1 to 51, else `IllegalArgumentException`.
- `FormingSummary formingSummary(TenantId tenantId)` with the new `record FormingSummary(long incidents, long alerts)` in `vigil.incidents.api`: the number of the tenant's `forming` incidents and the sum of their `alert_count` (0 and 0 when none).

**`vigil-engine` (`EngineService`):**

- The new `enum Stage { INVESTIGATION("investigation"), RESPONSE("response"), RECOVERY("recovery") }` in `vigil.engine.api`, with `key()` and `fromKey(String)` as the module's other enums.
- `Map<UUID, Stage> stages(TenantId tenantId, Collection<UUID> incidentIds)` — for each given incident that has a live run: its latest live run (by `started_at`, then id); of that run's step executions in state `running` or `waiting`, the latest by `started_at`, then id; its step type `DIAGNOSTIC` or `AI_TASK` → `INVESTIGATION`, `APPROVAL` or `ACTION` → `RESPONSE`, `RECOVERY_CHECK` → `RECOVERY` (DC-TX-01 "Stage", DM-SM-05 note; CTX-D-077 (3)). An incident with no live run, with no running or waiting step execution in its latest live run, or with another step type there, has no entry. An empty collection gives an empty map.
- `List<TimerView> pendingTimers(TenantId tenantId, UUID runId)` with the new `record TimerView(UUID id, UUID stepExecutionId, Instant dueAt)` in `vigil.engine.api`: the run's durable timers in state `pending` (DM-E-52), by `due_at`, then id.

### 6.3 Live update producers (`LiveProducers`; AR-I-04, AR-R-14, AR-R-19, PM-M23-04)

A new package-private class `vigil.api.LiveProducers` (`@Component`, `@Profile("!migrate")`) with one public `@ApplicationModuleListener` method per event (complete list). Each method first checks `TenantService.isActive(event.tenantId())` and does nothing for a tenant that is not active (AR-R-14, AR-R-19); it then calls `LiveHub.publish(tenant, topic, id, Timestamps.now(clock))` for each topic of its row, in order:

| Event | Topics (in order) | Notice `id` |
| --- | --- | --- |
| `AlertReceived` (AR-E-01) | `alerts` | the alert id |
| `AlertStateChanged` (AR-E-02) | `alerts` | the alert id |
| `SourceHealthChanged` (AR-E-03) | `sources` | the source id |
| `IncidentChanged` (AR-E-08) | `incidents`; `incident:{incident id}` | the incident id |
| `RunStarted`, `StepChanged`, `RunFinished` (AR-E-10) with mode `LIVE` | `run:{run id}`; `incident:{incident id}`; `incidents` | the run id |
| `RunStarted`, `StepChanged`, `RunFinished` with mode `TEST` | none in this package (`test-replay`: P-36) | — |
| `ApprovalDecided` (AR-E-09) | `approval:{approval request id}` | the approval request id |
| `TenantSettingsChanged` (AR-E-13) | `tenant` | the tenant id |

The listeners ask nothing else, write nothing and make no external call; a second delivery sends the same notices again, which a screen answers by reading again (AR-Q-05: no record changes). `vigil-api`'s `@ApplicationModule` declaration does not change (it already allows the `api` packages of `intake`, `incidents`, `engine`, `actions` and `tenancy`).

### 6.4 AR-I-20 `GET /api/v1/alerts/strip` (DC-S02-02, AR-I-05)

Owner modules `vigil-intake`, `vigil-incidents`. Answer `AlertStrip`:

```
{"received_last_10_minutes": n,
 "forming": {"incidents": k, "alerts": m},
 "sources": {"healthy": h, "total": s, "not_healthy": [{"source_key", "name", "health"}, …]},
 "latest": [{"alert_id", "first_received_at", "source_kind", "alert_type_name", "title"}, …]}
```

- `received_last_10_minutes`: `IntakeService.alertsReceivedSince(tenant, now − 600 s)`.
- `forming`: `IncidentService.formingSummary` (the web shows item 2 only while `incidents` > 0).
- `sources`: of `IntakeService.sources`, the active ones: `total` their number, `healthy` those with health `healthy`, `not_healthy` the others in code point order of `name`, each with its health key (`stale` or `disconnected`).
- `latest`: `IntakeService.latestAlerts(tenant, 10)` in that order; `source_kind` the alert's `MonitoringKind` key; `alert_type_name` the display name from `IntakeService.alertTypes` (the alert type key when it has none). The list holds the latest ten whether or not they arrived in the last 10 minutes; the web shows "No alerts in the last 10 minutes." when `received_last_10_minutes` is 0 (DC-S02-02 item 4).

### 6.5 AR-I-21 `GET /api/v1/incidents` (DC-S02-04, AR-I-01, DC-U-12)

Owner modules `vigil-incidents`, `vigil-identity`, `vigil-ticketing`, `vigil-engine`. Query parameters (complete list): `limit` (absent: 50) and `after` (absent: the first page). A valid `limit` is the ASCII text of a whole number from 1 to 50 without sign or leading zeros; a valid `after` is base64url text without padding that decodes to ASCII `[1-9][0-9]{0,17}` and encodes back to the same text; anything else, including an empty value: 400 `bad_request`. The cursor is the decimal `number` of a page's last row, encoded that way (opaque to clients; AR-I-01).

`IncidentService.incidentPage(tenant, {open, resolved, closed}, after's number or null, limit + 1)`: the first `limit` incidents are the rows; `next_cursor` is the cursor of the last row when the read returned `limit + 1` incidents, else `null`. Answer `{"items": [IncidentRow, …], "next_cursor"}`, each `IncidentRow`:

```
{"incident_id", "number", "title", "severity", "state", "stage", "owner": TeamName or null,
 "acknowledged": {"user": UserName, "at"} or null, "alert_count", "first_alert_fired_at",
 "ticket": {"key", "url"} or null}
```

`severity` the key (`P1` to `P4`) or `null`; `stage` the key of `EngineService.stages(tenant, ids of the page's open incidents)` for an `open` incident, else `null` (DC-TX-01 "Stage"; CTX-D-077 (3)); `owner` from `owner_team_key` (`null` when none); `acknowledged` from `acknowledged_by` and `acknowledged_at` (the current episode's, DM-E-32); `ticket` from `TicketingService.ticketLink` (`external_key`, `url`) when there is one. The empty state's source count (DC-S02-05) is AR-I-20's `sources.total`.

### 6.6 AR-I-22 `GET /api/v1/incidents/{incident_id}` (DC-S03-02 to DC-S03-04)

Owner modules `vigil-incidents`, `vigil-correlation`, `vigil-routing`, `vigil-identity`, `vigil-ticketing`, `vigil-engine`, `vigil-servicemap`. For a `merged` incident the answer is exactly `{"merged_into_incident_id"}`. Otherwise `IncidentHeader`:

```
{"incident_id", "number", "title", "state", "stage", "severity", "owner": TeamName or null,
 "informed": [TeamName, …], "rule_name", "acknowledged": {"user": UserName, "at"} or null,
 "escalation": {"level", "teams": [TeamName, …]} or null, "first_alert_fired_at", "resolved_at",
 "ticket": {"key", "url"} or null, "reopen_count", "alert_count",
 "hypothesis": {"component_key", "name", "kind", "criticality", "other_affected_count",
                "dependent_count", "tie_break"} or null,
 "affected_services": [{"service_key", "name", "criticality", "via": [{"component_key", "name"}, …]}, …]}
```

- `stage` as AR-I-21 (one incident); `informed` from `informed_team_keys`, in code point order of the names; `rule_name` the `matched_rule_name` of `RoutingService.evaluation(tenant, assignment_evaluation_id)` (DM-E-43), `null` when the incident has no assignment evaluation, it is not found or it matched no rule; `escalation` only when `escalation_level` > 0: the level and the teams of the incident's latest record of `IncidentService.escalations` (by `at`, then id) whose level equals it, in code point order of the names (`[]` when there is no such record); `resolved_at` as stored (the web shows it only for a `resolved` incident); `ticket` as AR-I-21; `alert_count` for the heading "Alerts ({alert_count})".
- `hypothesis` (`null` when the incident has none): `component_key`, `name`, `kind`, `criticality` from the incident's hypothesis copy (DM-E-32; `criticality` `null` when not set); from `CorrelationService.latestHypothesisComputation`: `other_affected_count` the number of its `affectedComponentKeys` other than its `resultComponentKey` (DC-TX-02's m), `dependent_count` its `dependentCounts` value of the result component (DC-TX-02's n; 0 when absent), `tie_break` its key; with no computation, 0, 0 and `none`.
- `affected_services` from the incident's affected service copies, in code point order of `service_key`: `name`, `criticality` (`null` when not set), `via` each via component key with its name (Section 6.1), in code point order of the names.

### 6.7 AR-I-23 `GET /api/v1/incidents/{incident_id}/alerts` (DC-S03-05, DC-TX-02)

Owner modules `vigil-incidents`, `vigil-intake`, `vigil-correlation`, `vigil-servicemap`. The members are `IncidentService.members` (active memberships); their alerts and the related alerts of their reasons come from one `IntakeService.alerts` call. Answer `IncidentAlerts`:

```
{"firing": f, "resolved": r, "grouping_window_seconds": w,
 "groups": [{"alert_type", "alert_type_name", "count",
             "alerts": [{"alert_id", "fired_at", "source_kind", "title", "component_name",
                         "status", "reason": Reason}, …]}, …]}
```

- `firing` and `resolved`: the members whose alert status from `vigil-intake` is `firing` or `resolved`; `grouping_window_seconds`: `CorrelationService.settings` `groupingWindow` in whole seconds (DC-TX-02's W; `null` when the tenant has no settings).
- `groups`: one per alert type of the members' alert copies, in code point order of `alert_type_name` (the copy's `alertTypeName`); `count` its members; `alerts` in `fired_at` order, then `source_kind`, then `alert_key` of the copies (DC-S03-05); `fired_at`, `source_kind`, `title` from the copy; `component_name` `null` when the copy has no `component_key` ("Unknown component"), else its name (Section 6.1); `status` the alert's status key from `vigil-intake`, `null` when `vigil-intake` does not return the alert.
