## 2. Goal

Build the five lab hosts as containers of one `demo-lab` image, with every mock of DD-F-10 `mock_behaviour`, the lab DB server `lab-db-01` with its own XFS `/data` in the size profile asked for, its two SSH users and its keys from secret files, and the local tooling that builds the image and starts and stops the lab (`deploy/images.sh --test`, `deploy/local.sh up --lab-only` and `down`, the lab part of `deploy/local/compose.yaml`). After this package the lab runs on its own, without monitoring and without Vigil, in a cloud session, on a GitHub Actions runner and on the owner's Mac; the five command templates of DD-F-04 have been run on `lab-db-01` before and after an injection like SL-F-1; and P-04 can configure Zabbix and Prometheus against the interfaces of Section 6.4. The gate command also starts the Docker daemon in a cloud session when it is not running (BP-R-12 step (0), CTX-D-032). Zabbix agent 2 comes from the official `zabbix/zabbix-agent2` image (BP-A-17, CTX-D-034).

### 6.1 `demo/lab/` — the `demo-lab` image

Files (complete list): `Dockerfile`; `requirements.txt` (exactly one line, `prometheus-client=={version}`, the latest release on the pin date); `entrypoint.sh`; `labctl.sh`; `sshd_config` (drop-in); `labmocks/` (Python package); `test_labmocks.py` and `test_lab.py` (Section 7); `README.md` (Section 6.4).

`Dockerfile`, two stages (BP-R-04 as amended by BP-A-17):

- Stage `agent`: `FROM zabbix/zabbix-agent2:{tag}@sha256:{digest} AS agent`, where `{tag}` is, on the pin date, the newest `ubuntu-7.0.{patch}` tag whose image is built on Ubuntu 24.04 (`noble`; later 7.0 patches are built on a newer Ubuntu, whose binaries need a newer C library than `ubuntu:24.04` has), with patch 12 or later (AR-T-22), and `{digest}` its multi-architecture index digest. The report records which tags were checked and why the chosen one is the newest noble-based one (Example: from the `FROM` line of the official `zabbix-docker` Dockerfile at that tag). Nothing runs in this stage; only its `/usr/sbin/zabbix_agent2` is copied.
- Final stage, in this order:
  1. `FROM ubuntu:24.04@sha256:{digest}` (the `24.04` tag's multi-architecture index digest on the pin date).
  2. The proxy build arguments (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` and their lower-case forms) are Docker's predefined arguments; they are not declared and not stored in the image.
  3. One `RUN` with `--mount=type=secret,id=ca_bundle,required=false`: when `/run/secrets/ca_bundle` exists (the build host had `/etc/ssl/certs/ca-certificates.crt`: cloud sessions and GitHub runners, not macOS), it writes `Acquire::https::CAInfo "/run/secrets/ca_bundle";` to `/etc/apt/apt.conf.d/99vigil-build-ca` and changes every `http://` to `https://` in `/etc/apt/sources.list.d/ubuntu.sources`; then `apt-get update` and `DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends` of exactly (complete list): `python3`, `python3-venv`, `openssh-server`, `openssh-client`, `prometheus-node-exporter`, `libcurl4t64` (a library of Zabbix agent 2), `xfsprogs`, `util-linux`, `iproute2`, `procps`, `ca-certificates`, `tzdata`; then it removes `/etc/apt/apt.conf.d/99vigil-build-ca`, changes the sources back to `http://`, and deletes `/var/lib/apt/lists/*`. No other package source is added (`repo.zabbix.com` is not reachable, CLAUDE.md).
  4. `COPY --from=agent /usr/sbin/zabbix_agent2 /usr/sbin/zabbix_agent2`, then a `RUN` that fails the build when `ldd /usr/sbin/zabbix_agent2` prints `not found`. When it does, the Ubuntu packages that provide the missing libraries MAY be added to the list of step 3; the report names them.
  5. `python3 -m venv /opt/venv` and `/opt/venv/bin/pip install --no-cache-dir -r requirements.txt` (with `--cert /run/secrets/ca_bundle` when that file exists, same secret mount).
  6. `rm -f /etc/ssh/ssh_host_*` (the image holds no host key; AR-S-04).
  7. Groups and users (complete list): group `zabbix` (GID 1997) and user `zabbix` (UID 1997, no login shell, AR-S-04's Zabbix user); group `vigil-diag` (GID 2001); user `vigil-diag` (UID 2001, primary group `vigil-diag`, home `/home/vigil-diag`, shell `/bin/bash`); group `vigil-action` (GID 2002); user `vigil-action` (UID 2002, primary group `vigil-action`, supplementary group `vigil-diag`, home `/home/vigil-action`, shell `/bin/bash`). The password fields of `vigil-diag` and `vigil-action` are `*` (no password works and the account is not locked, so public-key login works).
  8. Copies `labmocks/` to `/opt/labmocks/labmocks/`, `labctl.sh` to `/usr/local/bin/labctl` (0755), `entrypoint.sh` to `/usr/local/bin/lab-entrypoint` (0755), `sshd_config` to `/etc/ssh/sshd_config.d/10-vigil.conf`.
  9. `ENV TZ=UTC PYTHONPATH=/opt/labmocks`; `WORKDIR /opt/labmocks`; `ENTRYPOINT ["/usr/local/bin/lab-entrypoint"]`. No `USER` line: every lab container runs as user 0 and starts its services under their own users (Section 6.3).

`sshd_config` (complete list): `HostKey /etc/ssh/ssh_host_ed25519_key`; `PasswordAuthentication no`; `KbdInteractiveAuthentication no`; `PermitRootLogin no`; `PubkeyAuthentication yes`; `AuthorizedKeysFile .ssh/authorized_keys`; `AllowUsers vigil-diag vigil-action`.

### 6.2 `labmocks` — the mocks (Python 3.12)

General rules (complete list):

- The modules that hold behaviour import only the standard library, so their unit tests run in the gate's Python (`/opt/vigil-tools`), which has no `prometheus_client`. Only `labmocks/metrics.py` imports `prometheus_client`; it is imported only by the processes started in the containers. Code runs on Python 3.12 (containers) and on the gate's Python.
- Every component takes its clock, its sleep function and its HTTP client for the database or gateway as arguments, so unit tests run it with fakes and a simulated clock.
- Entry point: `/opt/venv/bin/python -m labmocks {role}` with role `db`, `api`, `vas`, `probe` or `rpt` (`PYTHONPATH` and working directory `/opt/labmocks` come from the image).
- HTTP between mocks on `lab-net`, JSON bodies, `http.server.ThreadingHTTPServer` with `request_queue_size = 128` and `daemon_threads = True`, and `urllib.request`. Every call has a deadline for the whole call (connect, send and read together); a call that has not finished by its deadline counts as failed with error `timeout`. Unknown paths answer 404; a body that is not the JSON object of the path, or names an unknown schema, node or menu, answers 400.
- Ports (complete list): `lab-db-01:7000` (database); `lab-api-01:8101` to `8104` (balance-check instances `api-balance-1` to `api-balance-4`) and `8201` to `8204` (bundle-purchase instances `api-bundle-1` to `api-bundle-4`); `lab-vas-01:7100` (USSD gateway sessions); metrics on port `9200` of `lab-api-01`, `lab-vas-01` and `lab-probe-01`.
- Streams are fixed-rate: a stream that runs "one per second" starts one call at every whole second from its start, each in its own thread, whether or not earlier calls have finished; the probe rounds start every 10 s the same way.
- Every counter and gauge of this section is created at start for every one of its label combinations, counters at 0 (so a rate is defined from the first scrape); the probe gauge is created with value 1.
- Logging, to standard output, one plain-text line per event (complete list of events): a component started (with its role and ports); a write, request, session or delivery outcome of one schema, instance and endpoint, node and menu, route, or city and journey changed from success to failure (with the error text) or from failure to success; the read-only flag or the report mode changed; a report run finished (with its result). Nothing is logged per successful call.

| Component | Role | Behaviour (DD-F-10 `mock_behaviour`, made exact) |
| --- | --- | --- |
| Subscriber database | `db` | `POST /write` `{"schema": s}` and `POST /read` `{"schema": s}`, `s` one of the 6 schemas of DD-F-10 (complete list: `subscriber_profile`, `balance_ledger`, `bundle_catalog`, `bundle_orders`, `ussd_sessions`, `sms_delivery`). A read always answers 200 `{"ok": true}`. A write answers 200 `{"ok": true}`, or 409 `{"ok": false, "error": e}` where `e` is, checked in this order: `database is read-only` while the read-only flag (Section 6.4) exists; `No space left on device` while `/data` has less than 256 MiB available (`os.statvfs("/data")`: `f_bavail * f_frsize < 268435456`), checked at every write. It keeps, per schema, the number of writes and of failed writes since it started, and writes them to its status files (Section 6.4) at start and then once per second. It never creates, changes or deletes a file under `/data`. |
| API instances | `api` | 8 instances (4 balance-check, 4 bundle-purchase), each an HTTP server on its own port with its 4 endpoints of DD-F-03 LA-05 or LA-06; a request is `POST {endpoint}` with an empty body or `{}`. Writes per request (complete list): balance-check, every endpoint: `write balance_ledger`, then `write subscriber_profile`; bundle-purchase, every endpoint: `write bundle_orders`, and for `/v1/bundles/offers` then also `write bundle_catalog`. Answer: 200 `{"ok": true}` or 502 `{"ok": false, "error": e}` (the database's error text, or `timeout`). Each instance also runs its own stream: one request per second on each of its 4 endpoints (32 per second in total), made by calling its request handler in-process, not over HTTP. Counters `lab_api_requests_total` and `lab_api_errors_total` with labels `api` (`balance` or `bundle`), `instance` (Example: `api-balance-1`) and `endpoint` (Example: `/v1/balance`) count every request, own stream and received. |
| USSD gateway | `vas` | Two nodes, `ussd-gw-a` and `ussd-gw-b`, each with the 6 menus of DD-F-03 LA-07. A session on (node, menu) has a 2 s deadline as a whole. It calls one API instance, the next one in round-robin order of its API kind for that node (deadline 1.5 s, and not past the session's deadline): menu `balance` → balance-check `/v1/balance`; `data-bundles` → bundle-purchase `/v1/bundles/offers`; `voice-bundles` → `/v1/bundles/purchase`; `sms-bundles` → `/v1/bundles/purchase`; `my-bundles` → `/v1/bundles/active`; `bundle-status` → `/v1/bundles/active`; then `write ussd_sessions` (deadline: what is left of the session's 2 s), also when the API call failed (CTX-D-035). Every-writer rate (DD-F-10 `every_writer_rate`): with the streams above each of the 6 schemas receives at least one write per second; a unit test checks it from the configured rates.

### 6.3 `entrypoint.sh` — the roles

`lab-entrypoint` (bash, `set -euo pipefail`) reads `LAB_ROLE` (one host name of DD-F-10 `lab_hosts`; any other value: print `unknown LAB_ROLE` and exit 1). It first removes `/run/lab/ready` and old pid files (they survive a container restart), creates `/run/lab`, `/var/lib/lab/status` and `/var/lib/lab/control` (all 0755), then starts the processes of its role in the background in the order below. It creates `/run/lab/ready` when each process is up: each process that has a port answers a TCP connect on it (ports 22, 7000, 7100, 8101 to 8104, 8201 to 8204, 9100, 9200, 10050 as they belong to the role); a process without a port is still running 1 s after its start; checked every 0.5 s for at most 60 s, otherwise it stops its processes and exits 1. Then it waits with `wait -n`: when any process exits, it stops the others and exits with that process's code, so a failed mock stops the container. On `SIGTERM` it stops its processes and, in `lab-db-01`, unmounts `/data` (a failed unmount is logged and the exit code is 0).

| Host | Processes, in start order (complete list) |
| --- | --- |
| `lab-db-01` | (1) `/data` set-up (below), before anything else; (2) keys from secret files (below); (3) `/usr/sbin/sshd -D -e`; (4) `prometheus-node-exporter --web.listen-address=:9100` as user `nobody`; (5) `zabbix_agent2 -f -c /etc/zabbix/zabbix_agent2.conf` as user `zabbix`; (6) `labmocks db`. |
| `lab-api-01` | `labmocks api`. |
| `lab-vas-01` | `zabbix_agent2` as user `zabbix`; `labmocks vas`. |
| `lab-probe-01` | `labmocks probe`. |
| `lab-rpt-01` | `zabbix_agent2` as user `zabbix`; `labmocks rpt`. |

**Zabbix agent 2 configuration** (written by the entrypoint to `/etc/zabbix/zabbix_agent2.conf` at every start, complete list of lines): `Hostname={LAB_ROLE}`; `Server=172.31.0.0/24`; `ListenPort=10050`; `ServerActive=` (empty: passive checks only); `LogType=console`; `PidFile=/run/zabbix/zabbix_agent2.pid`; `ControlSocket=/run/zabbix/agent.sock`. The entrypoint creates `/etc/zabbix` (0755) and `/run/zabbix` (owner `zabbix`, 0755). P-04 MAY change this configuration.

**`/data` set-up (`lab-db-01`, AR-X-01, BP-A-05).** `LAB_PROFILE` is `test` or `demo` (any other value: exit 1). Profile sizes (BP-R-30, DD-F-10 `size_profiles`; 1 GiB = 1073741824 bytes): `test` — device 4 GiB, `/data/db` 0.8 GiB, `/data/export` 0.1 GiB; `demo` — device 16 GiB, `/data/db` 6 GiB, `/data/export` 1 GiB. Steps (complete list):

1. The image file is `/var/lib/lab-data/data-{profile}.xfs` on the named volume mounted at `/var/lib/lab-data`. When it does not exist: create it sparse with `truncate -s {device size}`, run `mkfs.xfs -q` on it, and mark it new.
2. Attach and mount: first create a device node for every `/sys/block/loop{N}` that has none in `/dev` (`mknod /dev/loop{N} b 7 {N}`), so that `losetup` can see every attached device; then detach every loop device still attached to the image file from an earlier, abnormal stop (`losetup -j {image file}`, then `losetup -d` each). Then `n=$(losetup -f)`; when the device node `$n` does not exist in the container (Docker copies the host's `/dev` at container creation, so a loop device the kernel added later has no node), create it with `mknod $n b 7 {number}`; then `mount -t xfs -o loop=$n,nouuid {image file} /data` (create `/data` first), so `mount` attaches the device with auto-clear and it is detached when `/data` is unmounted. On failure print the error, detach as above and exit 1 (BP-ASM-06).
3. Owners and modes (every start; `chown` and `chmod` here touch only the four folders, never a file under `/data/db` or `/data/export`): `/data`, `/data/db` and `/data/export` `root:vigil-diag` 0750; `/data/txlog_archive` `vigil-action:vigil-diag` 0750 (no sticky bit).
4. Only when the image file is new: create the baseline content (DD-F-10 `baseline_content`): `/data/db/datafile_01.dbf` to `datafile_08.dbf`, each one eighth of the profile's `/data/db` size rounded down to a multiple of 4096 bytes; `/data/export/export_01.dat` to `export_04.dat`, each one quarter of the profile's `/data/export` size rounded down to a multiple of 4096 bytes; all made with `fallocate -l`, owner `root:vigil-diag`, mode 0640, modification time 30 days before now (`touch -d`); `/data/txlog_archive` empty. Nothing else is created under `/data` (XFS creates no `lost+found`).

### 6.7 `deploy/local.sh` (lab part)

Bash, `set -euo pipefail`, run from any directory (it changes to the repository root). Commands in this package (complete list):

- `deploy/local.sh up --lab-only [--profile test|demo] [--project NAME]`
- `deploy/local.sh down [--volumes] [--project NAME]`

`up` without `--lab-only` prints `The full local installation arrives in package P-26.` and exits 2; any other command or option prints a usage line and exits 2. Defaults: project `vigil-local`; profile `lab_profile` of `deploy/values/local.yaml` (read with `awk`, no YAML tool). `VIGIL_LOCAL_HOME` (default `$HOME/.vigil-local`) is the base folder; the project's folders are `{base}/{project}/secrets/` and `{base}/{project}/values/`. The script needs only `bash`, `docker` with `docker compose`, `awk` and coreutils on the host (macOS and Ubuntu); no OpenSSH and no Python. `ssh-keygen` runs inside the `demo-lab` image as root (`ssh-keygen` refuses a user ID without a passwd entry): `docker run --rm --entrypoint sh -v {temporary folder}:/work vigil/demo-lab:local -c '{ssh-keygen commands} && chown -R {host uid}:{host gid} /work'`, so the files come back owned by the user who runs the script.

`up --lab-only` steps (complete list, in order):

1. `docker info` MUST succeed; otherwise print `Docker is not running.` and exit 1. When a container named like a lab host exists (running or stopped) that does not belong to project `{project}` (`docker ps -a --filter name=^lab- --format …` with the label `com.docker.compose.project`), print `Lab containers of project {other} exist: run deploy/local.sh down --project {other} first.` and exit 1 (container names are fixed, Section 6.6).
2. **Image.** When `docker image inspect vigil/demo-lab:local` fails, run `deploy/images.sh --test`.
3. **Secrets (BP-R-26, AR-S-13).** Folders `{base}`, `{base}/{project}` and `{base}/{project}/secrets` are created with mode 0700 when missing; each unit folder (`secrets/lab-db-01`, `secrets/vigil-app`) is 0555 (the script makes it writable only while it adds a file); every secret file is 0444. For each `{k}` of `diag` and `action`: when both `secrets/vigil-app/lab-db-01-{k}` and `secrets/lab-db-01/lab-db-01-{k}-pub` are missing, generate an ed25519 key pair (`ssh-keygen -t ed25519 -N "" -C vigil-{k} -f /work/{name}`) and write both: `vigil-app/lab-db-01-{k}` holds the JSON object `{"username":"vigil-{k}","private_key":"{OpenSSH private key}"}` (made with `awk`; the key's line breaks, including its last one, written as `\n`; the file ends with `}`), and `lab-db-01/lab-db-01-{k}-pub` holds the public key line without its newline; when exactly one of the two exists, print `Secret pair incomplete: delete {file} or restore {other file}.` and exit 1. When `secrets/lab-db-01/lab-db-01-host-key` is missing, generate an ed25519 key (`-C lab-db-01`) and write its private key without its last newline. Existing files are never changed. Temporary files are created in a folder made by `mktemp -d` (mode 0700) and removed on exit; no key is printed.
4. **Derived value (AR-B-07).** Folder `{base}/{project}/values` (0755). Write `values/derived.yaml` (0644) with exactly one line `lab_db_host_key_sha256: "SHA256:{base64}"`, the fingerprint (`ssh-keygen -l -E sha256`) of the host key's public key, computed from a temporary 0600 copy of the host key with its newline added, every time `up` runs.
5. **Start.** `VIGIL_LOCAL_SECRETS={base}/{project}/secrets VIGIL_LAB_PROFILE={profile} docker compose -f deploy/local/compose.yaml -p {project} up -d lab-db-01 lab-api-01 lab-vas-01 lab-probe-01 lab-rpt-01`.
6. **Wait.** Until every lab service is `healthy`, checking every 2 s for at most 180 s; on time-out print `docker compose ps` and the last 50 log lines of each lab service and exit 1. Then print `Lab is up (profile {profile}, project {project}).`

`down` runs `docker compose -f deploy/local/compose.yaml -p {project} down` (with `--volumes` when given; the lab's `/data` image is then removed). Secrets and values stay; the owner deletes `{base}/{project}` to start from new keys.
