Run `demo-control` in the local installation at `http://control.vigil.test:8090`, make `deploy/local.sh reset` the control panel's reset, and prove SB-T-05 on the local installation with a Playwright suite: "Clear all faults" after a storm, and five resets in a row, the first after SL-F-1 with SL-F-2.

### 6.1 General rules

- `demo-control` is the module `demo/control` (Java 25, Spring Boot 4.1.1 as today; package `democontrol`; AR-T-21). It reaches Vigil only through `vigil-api` (AR-I-10, AR-I-95 to AR-I-98; SL-A3-03) and knows nothing of Vigil's code (no dependency on `app`). It logs JSON lines on standard output (AR-S-11, ECS as today), one line per operation start and end with its times, and never logs a secret, a password or a token.
- New dependencies of `demo/control` (complete list, versions managed by Spring Boot's parent where it manages them): `spring-boot-starter-webmvc`; `spring-security-crypto` (Argon2id) with `org.bouncycastle:bcprov-jdk18on` 1.86 (the pin of `app`); test scope `org.wiremock:wiremock-standalone` at the pin of `app`, `tools.jackson.dataformat:jackson-dataformat-yaml` (managed). The report lists them. No other new dependency anywhere (the Ubuntu packages `iptables` and `conntrack` of `demo-faults`' image are system packages, BP-R-04).
- Secrets (AR-S-04): `demo-control` reads `control-password`, `installation-token`, `faults-token`, `zabbix-api` and `alertmanager-password` from `{demo-control.secrets}/{name}` at each use (complete list; `deploy/units.yaml` lists them already).
- Wording: every visible text of the page is the exact text of DC-S12 and DC-U-11 (row Reset), with `{product}` the control panel's own value `product_display_name` (CTX-D-093 (6)); the texts this spec adds are the error texts of Section 6.4 item 6 (complete list) and the page title "Demo control panel".
- The control panel's look is not bound by `45-visual-design` (CTX-D-088 (6)); its only layout requirement is DC-S12-01's "usable at 640 px wide" (no horizontal scrolling at a 640 px window).

### 6.3 Login, session and the JSON interface (AR-S-12, DC-S12-01; CTX-D-093 (1), (2))

1. **Login**: one user `operator`; at start `demo-control` reads `control-password`, keeps only its Argon2id hash (AR-S-01 parameters: `new Argon2PasswordEncoder(16, 32, 1, 19456, 2)`, as `vigil.identity.Passwords`) and verifies each sign-in against it; the username is compared in constant time. When the file is missing or empty, every sign-in is refused (SL-B-14: no default password). A wrong username or password answers 401 `{"message": "Username or password is incorrect."}`.
2. **Session**: 32 random bytes from a `SecureRandom`, base64url without padding, in cookie `control_session` (`HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` when `vigil.security.secure-cookies` is true, no `Max-Age`); only its SHA-256 is kept, in memory; it lasts 12 h from sign-in and ends when `demo-control` restarts. There is no sign-out (DC-S12 has none).
3. **Interface** (complete list; every `POST` MUST have `Content-Type: application/json`, else 415 with nothing done, so a cross-site form cannot call it):

   | Request | Login | Answer |
   | --- | --- | --- |
   | `GET /health` | no | 200, no body (AR-U-06; the load balancer's check in P-32) |
   | `GET /` | no | the page `index.html` (Section 6.5) |
   | `POST /api/session` `{"username", "password"}` | no | 204 and the cookie; 401 as item 1; 400 for any other body |
   | `GET /api/state` | yes | 200 the state (item 4); without a valid session 401 `{"product": "{product}"}` (the login screen's top line needs it) |
   | `POST /api/buttons/{key}` with body `{}`, `key` one of `storm`, `storm-rerun`, `storm-read-only`, `cut-cloud-ai`, `clear`, `reset` | yes | 202 `{}` when the operation starts; 409 `{"reason": "{guard text}"}` when a guard refuses it (Section 6.4 item 2) or the panel is not yet connected (reason "Connecting…"); 404 for another key; 401 |

4. **State** (`GET /api/state`; complete list of members; every text composed by `demo-control` except the times of the active faults): `product`; `vigil_url`; `connected` (true once both reachability checks of item 5 have answered since `demo-control` started); `active` — `[{"fault", "name", "since"}]` in fault ID order (`since` an ISO 8601 UTC instant); `buttons` — the six in DC-S12-02's order, `[{"key", "label", "description", "refused"}]` (`refused` the guard text or `null`); `status` — the line of DC-S12-05 (Section 6.4 item 5); `storm_clock` — the line of DC-S12-06 or `null`; `last_result` — `null` or `{"operation", "outcome" ("completed" or "failed"), "finished_at" (ISO 8601 UTC), "seconds", "branch_a_seconds", "quiet_seconds", "branch_b_seconds", "error"}` (seconds with three decimals; the branch and quiet times only for a reset, the quiet time also for "Clear all faults"; CTX-D-093 (11): measured values of SB-T-05 and CTX-D-068 (3), not shown on the page).
5. **Reachability** (CTX-D-093 (3)): every 5 s while no operation runs, `demo-control` checks the lab — Zabbix `problem.get` (filtered by tag `vigil=lab`) and Alertmanager `/api/v2/alerts` both readable (as AR-B-03 branch A reads them) and a TCP connection to `demo-faults` within 2 s — and Vigil — AR-I-10 `GET {vigil-url}/api/v1/public/branding` answering any HTTP status within 5 s. A failed check keeps its error text (complete list of forms: "Zabbix: {text}", "Alertmanager: {text}", "demo-faults: {text}" for the lab, the first that failed; "{text}" for Vigil), where `{text}` is "answered HTTP {status}" for an unreadable answer and otherwise the exception's message (its class's simple name when the message is empty). The counts of the latest successful lab read are kept for the status line.

### 6.4 Faults, guards, operations and status (DC-S12-02 to DC-S12-06, AR-B-03, DD-F-10 `control_panel`)

1. **Buttons** (DC-S12-02, complete list; label — description — faults): `storm` "Storm: SL-F-1 + SL-F-3" — "Fills /data on the Subscriber DB server and fails the report export job." — SL-F-1, SL-F-3; `storm-rerun` "Storm re-run: SL-F-1" — "Fills /data on the Subscriber DB server again." — SL-F-1; `storm-read-only` "Storm with read-only DB: SL-F-1 + SL-F-2" — "Fills /data and sets the database read-only." — SL-F-1, SL-F-2; `cut-cloud-ai` "Cut cloud AI: SL-F-4" — "Blocks {product}'s calls to the Claude and OpenAI APIs." — SL-F-4; `clear` "Clear all faults" — "Ends every active fault and waits until every lab alert is resolved."; `reset` "Reset" — "Clears the lab and brings {product} to the starting state.". The fault names are DD-F-10's (`faults.{id}.name`), constants of the code checked by a test against `10-lab-and-faults.yaml`.
2. **Guards** (DC-S12-03, complete list, in this order): while "Clear all faults" or "Reset" runs, every button is refused with "Wait: Clear all faults is running." or "Wait: Reset is running."; otherwise the three storm buttons are refused while SL-F-1, SL-F-2 or SL-F-3 is in the record, with "Clear all faults first (active: {every recorded fault ID in ID order, comma-separated})."; "Cut cloud AI: SL-F-4" while SL-F-4 is in the record, with "Already active."; "Clear all faults" when the record is empty, with "No active faults."; "Reset" is never refused otherwise. The server applies the same guards to `POST /api/buttons/{key}`.
3. **Fault buttons** (`storm`, `storm-rerun`, `storm-read-only`, `cut-cloud-ai`; CTX-D-093 (4)): the faults are added to the record (each with `since` = the press) when the button is accepted, then injected one after the other in fault ID order (`POST /faults/{id}/inject`, 65 s timeout each); a storm button starts the storm clock at the press. A failure stops at that fault and becomes the last result "{label} failed after {s} s: {error text}"; the record keeps the button's faults. A success changes no last result.
4. **"Clear all faults" and "Reset"** (AR-B-03; `Operations.java`):
   - **Lab clear** (the whole of "Clear all faults", and branch A of "Reset"): `POST /faults/clear` `{"faults": ["SL-F-1", "SL-F-2", "SL-F-3", "SL-F-4"]}` (all four, so the lab reaches its starting state whatever the record holds; CTX-D-093 (4)) with the time left to the limit as timeout; then, every 2 s, Zabbix `problem.get` (tag `vigil=lab`) and Alertmanager `/api/v2/alerts` filtered to the five catalogue alert names of `03-monitoring.yaml` (`NodeFilesystemFull`, `BalanceApiErrors`, `BundleApiErrors`, `UssdGatewayTimeouts`, `SyntheticUssdSessionFailed`) until both return none (a read that fails is retried at the next turn); the quiet time is measured from the clear's answer to the first quiet read; then 12 s (DD-F-10 `clear_settle_s`). Limit: 58 s from its start (AR-B-03; for "Clear all faults" alone the same limit, CTX-D-093 (4)).
   - **Vigil prepare** (branch B): AR-I-95 with the name `jazz-demo {UTC time as YYYY-MM-DDTHH:MM:SSZ}` (expects 200 with `tenant_id`); the bundle (Section 6.2 item 4); AR-I-96 with the multipart field `bundle` (file name `bundle.zip`, `application/zip`; expects 202 with `seed_import_id`); AR-I-97 every 1 s until `state` is `succeeded` or `failed` (a read that fails is retried); `failed`, or `succeeded` with a part whose outcome is not `succeeded`, fails the branch. Limit 58 s from its start.
   - **Reset**: the storm clock ends; both branches start at once on their own threads; when one fails, the reset fails at once: the other branch stops at its next call or wait, and AR-I-98 is not called (the alias stays; the earlier tenant stays active). When both succeed, `PUT /api/v1/installation/aliases/demo.{demo_domain}` `{"tenant_id"}` (expects 200); the reset is complete when it answers. Calls to Vigil carry `Authorization: Bearer {installation-token}` (AR-S-07).
   - **The record**: emptied when the operation completes; after a failed operation, emptied when `demo-faults` answered the clear with 200, else kept (AR-B-03, DD-F-10 `fault_state`).
   - Calls to `demo-faults` are made one at a time, in the order they are asked for (a fault button's injects and a later clear do not overlap).
5. **Status** (DC-S12-05, exactly one, in this order): while "Clear all faults" runs: "Clearing faults… {s} s — firing lab alerts: Zabbix {z}, Alertmanager {a}" ({z}, {a} the counts of the latest successful lab read); while "Reset" runs: "Resetting… {s} s — lab: {Clearing or Clear}, {product}: {Resetting or Ready}" (Clear once branch A has succeeded; Ready once branch B has succeeded); otherwise, while the latest lab check failed: "Cannot reach the lab: {error text}."; while the latest Vigil check failed: "Cannot reach {product}: {error text}."; otherwise the last result — "Clear all faults completed in {s} s", "Reset completed in {s} s", "{operation} failed after {s} s: {error text}" (`{operation}` "Clear all faults", "Reset" or a button's label) — or "Idle" when there is none. `{s}` is the operation's whole seconds, rounded down.
6. **Error texts** (complete list, CTX-D-093 (4)): `demo-faults` answered an error: its `error` text, or "demo-faults answered HTTP {status}" without one; `demo-faults` did not answer: "demo-faults: {error text}"; the lab not quiet at the limit: "Lab alerts were still firing after 58 s: Zabbix {z}, Alertmanager {a}."; the lab not readable at the limit: "The lab could not be read: {error text of the last read}."; Vigil answered an error to AR-I-95, AR-I-96 or AR-I-98: the answer's `error.message` (AR-I-03), or "{product} answered HTTP {status}" without one; Vigil did not answer: "{product}: {error text}"; the import failed: "The seed import failed: {module}: {error}; …" over its parts whose outcome is `failed` (`{error}` "failed" when `null`); the import still `running` at the limit: "The seed import was still running after 58 s."; AR-I-97 not readable at the limit: "The seed import could not be read: {error text}."; and the three texts of Section 6.2 items 3 and 4.
7. **Storm clock** (DC-S12-06): "T+{m}:{ss} since '{label}'" from the storm button's press, while no reset has started since and no later storm button was pressed.
8. **State file** (AR-X-04, DD-F-10 `fault_state`): the record, the storm clock's start and label, and the last result, as JSON in `demo-control.state-file`, written to a temporary file in the same folder and renamed after every change; read at start (a missing file is an empty state). An operation that was running when `demo-control` stopped is not resumed.

### 6.5 The page (`demo/control/src/main/resources/static/index.html`; DC-S12, DC-U-11, AR-T-21)

One HTML file with its CSS and plain JavaScript inline, no library, `<title>` "Demo control panel". At every screen a line across the top: "Demo control panel — demo-only, not part of {product}." (`product` from `/api/state` or its 401 answer).

1. **Login** (DC-S12-01): shown while `/api/state` answers 401: fields "Username" and "Password" (labelled inputs), button "Sign in"; a 401 of `POST /api/session` shows "Username or password is incorrect." under the button; a 204 shows the panel. Any later 401 shows the login again.

### 6.6 SL-F-4 in `demo-faults` (AR-X-03, AR-U-07, DD-F-10 `faults.SL-F-4`; CTX-D-093 (9))

1. `faults.py`: the faults are SL-F-1 to SL-F-4 (`ORDER` with SL-F-4 last); SL-F-1 to SL-F-3 are unchanged. SL-F-4 runs its commands on the host network itself (not through `docker exec`), each with the 60 s deadline.
2. **The `iptables` program**: `iptables-nft` when `iptables-nft -S DOCKER-USER` succeeds, else `iptables-legacy` when `iptables-legacy -S DOCKER-USER` succeeds (Docker's backend on the host decides which one holds the chain), checked at each inject; when neither does, the inject fails with "SL-F-4 inject failed: the DOCKER-USER chain was not found".
3. **Inject**: resolve `api.anthropic.com` and `api.openai.com` to their IPv4 addresses (`socket.getaddrinfo(name, 443, AF_INET, SOCK_STREAM)`; the Docker networks have no IPv6, AR Section 6); a name that does not resolve adds no address and is logged. For each source `172.30.0.10` and `172.31.0.10` and each address A, the rule `-s {source}/32 -d {A}/32 -p tcp -m tcp --dport 443 -j REJECT --reject-with tcp-reset` is inserted at the top of `DOCKER-USER` (`-I DOCKER-USER`) unless `-C` finds it; then `conntrack -D -p tcp -s {source} -d {A} --dport 443` (exit 0, or exit 1 with "0 flow entries have been deleted." in its output, is success). The addresses are stored with the fault in the state file (`{"active": [...], "sl_f_4_addresses": [...]}`). While SL-F-4 is active, every 30 s the names are resolved again and a new address gets its rules and its `conntrack` in the same way (logged; an error is logged and tried again 30 s later).
4. **Clear**: the 30 s loop stops; for every stored address and both sources, `-D` removes the rule while `-C` finds it; the addresses are forgotten. Clearing an inactive SL-F-4 does nothing and succeeds.
5. **Restart**: when the state file holds SL-F-4, `demo-faults` checks the rules of the stored addresses, adds any that is missing, and resumes the 30 s loop.
6. Requests stay one at a time (the 30 s loop takes the same lock). The answers of AR-X-03 are unchanged; an unknown ID is now any ID outside SL-F-1 to SL-F-4.
7. **Image** (`demo/faults/Dockerfile`): adds the Ubuntu packages `iptables` and `conntrack`. **Local compose**: `demo-faults` gets `cap_add: [NET_ADMIN, NET_RAW]` (AR-U-07). In the local installation the rules are added on the Docker host but change nothing, because `vigil-app` calls the AI fakes (`60-build-plan` Section 11.1 as amended by v1.35); `README.md` says so.
