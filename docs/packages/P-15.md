### 6.1 General rules

- Every public type of `vigil-routing` is in `vigil.routing.api` (AR-R-04); every other class is package-private in `vigil.routing`. The `@ApplicationModule(allowedDependencies = {"shared", "incidents :: api", "servicemap :: api", "identity :: api", "notifications :: api", "ticketing :: api", "audit :: api"})` of `vigil.routing` stays unchanged, and so do the declarations of `vigil.setup` and `vigil.api`. The public types of `vigil.routing.api` name, of other modules' types, only `vigil.incidents.api.Severity` (every module whose declaration allows `routing :: api` also allows `incidents :: api`) and the types of `vigil.shared` (`TenantId`, `Key`, `Actor`).
- Records are written with `JdbcClient`; every writing request is `@Transactional` (`REQUIRED`, AR-R-10), so `evaluate` runs in the caller's transaction (AR-R-11: the evaluation record, the assignment and the caller's own records commit or roll back together); reads have no transaction of their own.
- Time from the `Clock` bean through `Timestamps.now(clock)`, read once per request; ids from `Ids.newId()`; lengths in Unicode code points; "cut to n" is the first n code points.
- `null` arguments: `IllegalArgumentException`, except where Section 6.4 allows them. A request for an incident id that the tenant does not have: `VigilError` `NOT_FOUND` (default message).
- "Active team": `IdentityService.team(tenant, key)` is present and `active`. A text that is not a valid `Key` is not the key of an active team.
- Concurrency: `evaluate` reads the incident with `IncidentService.incident` and then calls `setAssignment`, which locks the incident row and checks again that it is `forming` and not frozen (P-14). A concurrent `open` between the two would make `setAssignment` throw `IllegalStateException` and roll back the caller's transaction; it cannot occur while every applied evaluation is made in the tenant's one-at-a-time sequence of `vigil-correlation` (DM-R-62). `vigil-workflows` also evaluates a forming incident before a live run (PM-I-16, applied by DM-R-17): P-17 MUST make that request so that it cannot race with `open` (Section 11). `vigil-routing` does not catch that exception.
- Logging: nothing at `INFO` or above per evaluation; one `INFO` line per saved revision (tenant id, revision).
- Every list returned is unmodifiable; JSON values returned are copies.
- No class has a `@Profile`; `vigil-routing` has no scheduled work, no listener and no restart step.

### 6.5 Seed part 11 (DM-E-41, DM-E-42, DM-R-57, AR-B-11)

`vigil.setup.RoutingAdapter` (package-private, a `SeedPartImporter` for part 11, as `IncidentsAdapter`) reads the two sections of `05-routing-escalation.yaml` (`SeedParts.ROUTING`) into a `RoutingPart` by one walk over this schema (complete): `routing_rule_set_revision_1` is a mapping with the field `rules`, a list of mappings with the fields `rule_key`, `name`, `severity`, `owner_mode`, `owner_team_key`, `inform_affected_service_owners` (single values), `conditions` (a list of mappings with the fields `field`, `operator` (single values) and `value` (a single value or a list of single values)) and `informed_team_keys` (a list of single values); `escalation_policy_revision_1` is a mapping with the field `levels`, a list of mappings with the fields `level` (a single value) and `team_keys` (a list of single values). Each node that does not fit gives one problem, collected in a `SeedShapes` (`section` for a missing section, `add` for the others; a helper MAY be added to `SeedShapes`), with its path written as the section, then `.{field}` and `[i]` (0-based) steps (Example: `routing_rule_set_revision_1.rules[0].conditions[1].value`). Shape problems (complete list of forms): `{section}: missing`; `{path}: not a mapping`; `{path}: not a list` (also for `rules` or `levels` absent); `{path}: not a single value`; `{path}: not a single value or a list of single values` (a condition's `value`); `{path}: unknown field {name}`. Any other absent field is passed as `null` without a problem, and so is a YAML `null` for `value` or for a list field (`conditions`, `informed_team_keys`, `team_keys`); any other single YAML value of `value` becomes a list of one. Problems are in the order the walk reads the nodes: section order, then list order, then the fields of a mapping as the file writes them, and after them an absent `rules` or `levels`. The adapter refuses them with `refuseIfAny` ("Part routing refused.") before calling the module. Single values are read as `SeedShapes` reads them (a YAML number or boolean as its text). The adapter calls `RoutingImport.importPart`, counts `{"rules": n, "escalation_levels": m}` (the list sizes), no handles, no `afterCommit`.

`importPart` (in one transaction, under `pg_advisory_xact_lock(hashtext('routing.rules'), hashtext(tenant id text))`) checks the part, collecting every problem (complete list, in this order), each prefixed by its path as written:

0. `rules` or `levels` of the `RoutingPart` `null`: `IllegalArgumentException` (the adapter never passes it: an absent list is its shape problem).
1. The tenant already has a routing rule set revision or an escalation policy revision: `routing rules already exist` (no other check runs).
2. ## 10. Review list for Abdul (at most 10)

1. The caller check of `evaluate`: `CORRELATION` only from `vigil-correlation`, `WORKFLOWS` and `TEST_REPLAY` only from `vigil-workflows`; a test replay is always a dry run, also on a closed or merged incident (DM-R-28 before DM-R-16).
2. The order of "not applied": dry run, then not active (neither `forming` nor `open`), then frozen; every evaluation is recorded, also one that is not applied.
3. The inputs: an empty set of affected services is a value (so `does not include` is true), while a missing hypothesis or criticality has none (every operator false); `highest_service_criticality` is `null` when no affected service has a criticality (the SL-F-3 case).
4. The owner of the hypothesis component and the owners of affected services are read from the current service map generation when the evaluation is made; a component or service no longer in it counts as having no owner, so "same inputs, same result" holds for an unchanged service map and teams. The rule's own teams are used as stored. Refusals of a save carry `places` so the screen can show each under its rule and field.
5. The validation order and texts (DC-TX-11 with BP-A-28): "complete or remove the empty condition" once per rule; "add at least one condition" for a rule above the last without conditions, and "The last rule must be the only rule without conditions." once for the list. An operator not allowed for its field, two values for a one-value operator and repeated rule keys are refused as wrong requests (400 in P-38), since the screen cannot send them.
6. New rules from the screen get keys `rule-1`, `rule-2`, …; `in` and `is not one of` values are stored sorted, so their order never counts as a change.
7. "position" in the change summary means the rule's place among the rules both revisions hold, so adding a rule above the default rule does not report the default rule as moved.
8. A save checks permission, then `base_revision` (409), then the rules (422); a save that changes nothing is still a revision with its audit event (BP-A-28).
9. Part 11 checks the rules with the save's validation (texts prefixed by the section), which already refuses rule teams that are not active; the key checks of DM-R-60 after the last part check the escalation teams and the comparison keys.
10. The report's line count: the estimate is close to the M limit (P-12 and P-14 came in above their estimates); P15-DC-01 says what happens above 2,000.
