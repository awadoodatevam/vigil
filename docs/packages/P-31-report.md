3. **`deploy/test_images.py`**: `LOCAL_CONTEXTS` lists `vigil/demo-control:local` (BP-R-04 as amended), so "the four images" test expects five builds (its docstring names demo-control); the fixture writes `demo/control/target/demo-control.jar`. `images.sh` keeps "Run ./mvnw -B -pl app -DskipTests package first." for a missing `vigil-app.jar` (the earlier test's text) and adds the spec's text for a missing `demo-control.jar`.
4. **`test_installation.py` `test_reset_makes_a_new_tenant`** read `state/tenant.json`, which only `up` writes now that `reset` is the control panel's (spec 6.7 item 4 writes no state); it is replaced by the spec's "SL-A3-03 deploy/local.sh reset is the control panel's reset" (a `presenter` session refused after the reset, the branding answering, the last result "Reset" completed).
5. **The lab clear's settle time and the 58 s limit**: when the lab becomes quiet less than 12 s before the limit, the branch waits until the limit and fails (AR-B-03). The first build used "Lab alerts were still firing after 58 s: Zabbix 0, Alertmanager 0."; since the review it is "The lab became quiet after {s} s, too late for the 12 s settle time within 58 s." (owner agreement, Section 4 item 1).
6. **Start check** (spec 6.2 item 1): "a values file lacks `product_display_name` or `demo_domain`" is read as the merged values of `demo-control.values` lacking them (`derived.yaml` never holds them); an unreadable values file at start also stops the start, with a line naming `demo-control.values`.
7. **`connected`** is true once both checks have *answered* — succeeded or failed — so a failed check shows "Cannot reach …" rather than "Connecting…" forever (DC-S12: "until its first read").
8. **The state file** holds `record` as `{fault: since}`; `seconds` and the branch times are written with three decimals and read back as decimals.
9. **Waiting for `demo-faults`**: a call waits for the earlier one without a bound (the fair lock); its own timeout is the time left to the limit, at least 0.5 s. A reset's wait for its branches is bounded since the review (limit plus 5 s).
10. **Logging**: `Reachability` logs nothing (not required); operation lines carry the times.
11. **Review item 3, "accepted after its press"**: a counter of accepted "Clear all faults" and "Reset" presses is read just before the fault button's press is accepted, and compared before each later inject. Nothing is missed between the read and the acceptance: a clear or reset accepted there would still be running, so the fault button's press would be refused.
12. **Review item 2, beyond the three named places**: a `RuntimeException` around the alias call of a reset is handled the same way, so that no path leaves the reset running.
