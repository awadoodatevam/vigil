## 2. Goal

Build `vigil-engine` (PM-M12): it runs each workflow run durably on its own copy of the content (DM-E-50 to DM-E-52), one evaluation at a time on the run's executor, with hand-offs, durable wakes, retries, cancellation and timers (AR-R-20 to AR-R-22, AR-R-27); waits while the incident is forming and cancels runs of merged or closed incidents, and on a reopen start cancels the unfinished run (DM-R-16, DM-R-22, PM-M12-11); runs the Trigger, Condition and Wait/timer steps itself (DM-S-01, DM-S-02, DM-S-11) and every other step through the step handler of its module (AR-R-21); guards the Action step (DM-R-31) and starts the reconciliation after a restart (PM-M12-10); and runs the timer poll (AR-R-23) and restart step 4 (AR-R-24). The step handlers of the other modules, and the reads `vigil-actions` gives the engine, are interfaces here, implemented by P-18 to P-24; this package tests the engine with test handlers, on runs it starts directly with the content of workflow version 1 (DD-F-06) and with test content. `vigil-workflows`, which imports the workflow and starts live runs, is P-41 (CTX-D-055 (1)). It also makes the two `vigil-correlation` worker fixes of CTX-D-054 (3).

### 6.1 General rules

- Every public type of `vigil-engine` is in `vigil.engine.api` (AR-R-04); every other class is package-private in `vigil.engine`. The `@ApplicationModule` declarations of every module stay unchanged. No public type of `vigil.engine.api` names a type of another module's `api` package; types of `vigil.shared` are used (`StepCall.StepType`, `Waiting.WakeEvent`, `Completed.ResultRef`, `Key`, `Actor`, `TenantId`).
- `vigil-engine` keeps its own package-private tables of each step type's named outputs (DM Section 9: `trigger` `next`; `condition` the branch labels and `otherwise`; `diagnostic` `done`, `failed`; `ai_task` `done`, `unavailable`; `approval` `approved`, `rejected`, `expired`; `action` `succeeded`, `failed`; `recovery_check` `recovered`, `not_recovered`; `escalation` `next`; `notification` `sent`, `failed`; `ticket` `done`, `failed`; `wait` `event_received`, `timed_out`) and of the Condition fields' value types (DM-R-25); it does not use `vigil-workflows` (CTX-D-055 (1)).
- Records are written with `JdbcClient`; transactions with `TransactionTemplate`; requests to other modules inside a transaction join it (AR-R-10). No step handler is called inside a transaction (AR-R-09, AR-R-22 part (2)).
- Time from the `Clock` bean through `Timestamps.now(clock)`; ids from `Ids.newId()`; lengths in Unicode code points. "Now" is read once per transaction. Durable times (timers, `retry_due_at`) are compared with `Timestamps.now(clock)`; the wait for a scheduled hand-off is real time (Section 6.6).
- The actor of every request to another module: `Actor.module("vigil-engine")`.
- JSON (run content, parameters, `step_state`, `result_ref`, `wake_events`) is read and written with a `static final JsonMapper` as the other modules do (Jackson 3, `tools.jackson.databind`); `wake_events` is written as an array of the wake event keys sorted in code point order (AR-P-01); the content, `step_state` and `result_ref` are stored as `jsonb` (AR-P-01), so JSON read back equals what was stored as a JSON tree, not as text; `StepCall.parameters` is the step's `parameters` object of the run's content and `StepCall.stepState` the stored `step_state`, each written as text with the engine's `JsonMapper`.
- `null` arguments of public requests: `IllegalArgumentException` with the message "a required argument is missing" (as P-14 to P-16).
- Logging (complete list): `INFO` `workflow run {run id} started for incident {incident id} (episode {n})` and `workflow run {run id} ended: {state key} ({end reason key})`; `ERROR` `step {step id} of run {run id} for tenant {tenant id} failed (attempt {n})` with the exception, once per failed call; `ERROR` `run executor of run {run id} for tenant {tenant id} failed` with the exception, when an executor transaction fails; `WARN` `engine timer poll for tenant {tenant id} failed` with the exception. Nothing else at `INFO` or above per step.
- Every list returned is unmodifiable.
- Classes that run work (`RunExecutors`, `EngineWork`, the listeners) have `@Profile("!migrate")`, as P-13 to P-16; no other class has a `@Profile`. A class without a profile that hands runs off (the `EngineService` implementation, the cancellation) obtains `RunExecutors` through `ObjectProvider`; in the `migrate` profile there is none and nothing is handed off.

### 6.5 Starting a live run (`EngineService.startLiveRun`; DM-E50-R1, DM-R-22, DM-SM07-T1)

`@Transactional(REQUIRED)`. Refuses with `IllegalArgumentException`: an actor other than `Actor.module("vigil-workflows")` (DM-E50-R1); an `episode` below 1; content that is not a JSON object whose `steps` is a list holding exactly one step of type `trigger`. When a live run of the tenant with this incident and episode exists in any state: returns `Optional.empty()` and writes nothing (DM-E50-R1). With `reopen` true, it first cancels every unfinished live run of the incident with end reason `incident_reopened` (Section 6.7) in this transaction (DM-R-22); with `reopen` false and an unfinished live run of the incident (another episode): `IllegalStateException("the incident has an unfinished live run")` (DM-E50-R1: at most one unfinished live run per incident). It then stores the run (`mode` `live`, the episode, the version id, the content, `state` `running`, `wake_pending` false, `started_at` now), the Trigger step execution (stored `completed` at once: DM-SM08-T1 and T4 in one transaction, with no `StepChanged` `running`; `named_output` `next`, `visit` 1, `evaluation_count` 1, `failed_attempts` 0, `started_at` = `finished_at` now) as the run's current step execution, and as checkpoint (`next_step_id`) the target of the Trigger's `next` connection; when it has none, the run ends at once (`finished`, `path_ended`, `finished_at` now). It publishes `RunStarted`, one `StepChanged` (`completed`) and, when the run ended, `RunFinished`; logs the `INFO` lines; and hands the run to its executor after commit. Returns the run id.

### 6.6 Run executors and the step call (AR-R-20 to AR-R-22, AR-R-27, AR-TM-05)

`RunExecutors` (package-private, `@Profile("!migrate")`): `void handOff(TenantId tenantId, UUID runId)` puts a signal into the run's queue; a run's queue is processed one signal at a time by one virtual thread named `run-{run id}`, started on the first signal and ending when the queue is empty (a later signal starts a new one; at no time do two threads process one run). Hand-offs before `EngineScheduling.resumeRuns()` has been called are dropped (AR-R-20); after the application context begins to close (`@PreDestroy`), hand-offs are dropped, no hand-off is scheduled (neither a retry nor the 5 s hand-off after a failed transaction) and no new processing starts. Hand-offs are made only as AR-R-20 lists: after a commit that started a run, recorded a wake or stored a run as `waiting` while `wake_pending` was set (`TransactionSynchronization.afterCommit`); at a step's `retry_due_at` (scheduled with the `TaskScheduler` after `retry_due_at − now` of real time); 5 s after an executor transaction failed (with the `ERROR` line of Section 6.1); and at restart or when a tenant becomes active again (Section 6.7).

**Processing a hand-off** — the cases (a) to (h) of AR-R-20, in one transaction that locks the run; "the tenant is active" is read from the engine's set of active tenants (Section 6.7). "Starting a step" is part (1) of AR-R-22 for a new step execution; "re-evaluating" is part (1) for the current one.

**Part (1), starting a step** (the checkpoint step: after a `Completed` answer, from case (c) or from case (h)), in one transaction that locks the run: when the tenant is not active, nothing (the run stays as it is); `wake_pending` is cleared, the run is `running` and `wait_reason` cleared (DM-SM07-T3); for a live run, the incident's state is read (`IncidentService.incident`): `merged` or `closed` — the run is cancelled with `incident_merged` or `incident_closed` (Section 6.7) instead; `forming` — the run becomes `waiting` with `wait_reason` `incident_forming` and no step execution is created (DM-SM07-T2); otherwise a step execution of the checkpoint step is stored (`running`, `visit` = 1 + the run's earlier executions of that step, `evaluation_count` 1, `failed_attempts` 0), the run's `current_step_execution_id` set and `next_step_id` cleared, and `StepChanged` (`running`) published. **Part (1), re-evaluating** (cases (d), (f), (g)): the tenant check as above; the run `running`, `wait_reason` and `wake_pending` cleared; the step execution `running`, `retry_due_at` cleared, `evaluation_count` increased; `StepChanged` (`running`).

**Part (2), the call** (no transaction open). `StepCall` holds the tenant, run, incident, step execution and step ids, the step type, the step's `parameters` JSON from the run's content (`{}` when absent), the new `evaluation_count`, the stored `step_state`, the wake reason (below), for a Recovery check step `ActionRuns.latestRecoveryCheckKey(run)` (or `null`), and for an Approval step `ActionRuns.earlierApprovers(run)` (PM-M12-07, DM-A-15). The operation is `start` when the step execution has never stored a `Waiting` answer, otherwise `evaluate`. Wake reasons (complete list): `start` for the first call of a new step execution; `retry` for a retry; `resume` for case (g); otherwise the run's `wake_reason` as last recorded (`event:{wake event key}`, `timer` or `restart`). Trigger, Condition and Wait steps are answered by the engine itself (below); an Action step is first checked by the guard (below); every other step type is passed to its handler (Section 6.4).

**Part (3), the answer** — in one transaction that locks the run, as AR-R-22 says. A run no longer `running` (cancelled meanwhile) discards the answer, and likewise a call that threw (the `ERROR` line is still logged), and calls the handler's `cancel` (when the bean exists); nothing else is stored. Otherwise the step execution's `pending` timer, if any, becomes `cancelled` (DM-SM09-T3) and its `timer_id` is cleared; then `Completed` stores `named_output`, `result_ref`, `refusal_reason` (guard refusals only), `finished_at`, the step execution `completed` and `failed_attempts` 0, and as checkpoint the target of the output's connection, or ends the run (`finished`, `path_ended`, `RunFinished`, the `INFO` line) when the output has no connection; `Waiting` stores `wake_events`, `step_state`, the step execution `waiting` and `failed_attempts` 0, and, when it has a due time, a new `pending` timer (`purpose` `{step type key} timer`) whose id becomes the step execution's `timer_id`; the run becomes `waiting` with `step_waiting`, and, when `wake_pending` is set, it is handed off after commit. Each publishes `StepChanged` with the new state. After `Completed` the executor goes on with part (1) of the next step in the same processing.

**Retries (AR-R-22, AR-TM-05).** A call that throws: the `ERROR` line; in part (3), `failed_attempts + 1` and `retry_due_at` = now + 5 s, 15 s or 45 s after the 1st, 2nd or 3rd failure, and a hand-off scheduled at that time. When the 4th attempt fails: the run `failed` (DM-SM07-T6) with `end_reason` `step_failed_repeatedly` and `end_detail` `step '{step label}' did not answer after 4 attempts` (the label from the run's content), the step execution `cancelled` with `finished_at` and its `pending` timer `cancelled`, `StepChanged` (`cancelled`), `RunFinished` and the `INFO` line; no handler `cancel` (DM-SM07-T6 names none).

**Case (g)** — an interrupted call: an Action step execution without a named output is not called again; `ActionRuns.reconcile` (wake reason `resume`) is called with no transaction open and its `Completed` is stored as the step's answer (PM-M12-10; a throw is a failed call). Any other step is called again with the reason `resume` (its operation by the rule of part (2)).

**Trigger, Condition, Wait (PM-M12-02).** The Trigger is completed at the run's start (Section 6.5); it never reaches part (2). **Condition (DM-S-02, PM-M12-03;** computed by the package-private `Conditions` from an `IncidentView` and the step's parameters**):** the incident is read; the branches are tested in list order, the first whose comparisons are all true gives its label, none gives `otherwise`; the fields and their values (DM-R-25; "no value" is `null`; a set or integer always has a value): `severity` (ordered P1 > P2 > P3 > P4); `owner_team` (`ownerTeamKey`); `informed_teams` (`informedTeamKeys`); `hypothesis_component` (`hypothesisComponentKey`); `hypothesis_component_kind` (`hypothesis().kind()`, no value without a hypothesis); `hypothesis_criticality` (`hypothesis().criticality()`, ordered critical > high > medium > low); `affected_services` (the `serviceKey`s); `affected_service_count` (their number); `highest_service_criticality` (the highest `criticality` among them, no value when none has one); `alert_count`; `alert_types`; `alert_sources`; `acknowledged` (`acknowledgedAt` set); `escalation_level`; `ai_investigation_available` (`aiStatus` `AVAILABLE`); `reopen_count`. A comparison is `{"field", "operator", "value"}`; for `in` and `not_in` the value is a list. The operators as DM-R-26 and the P-15 spec Section 6.6 (2): `at_least` true when the field's value is equal to or higher than the value, `at_most` when equal or lower; `in`/`not_in` against the list; `contains`/`not_contains` on a set; the six integer comparisons; `is` on a boolean; a field with no value is false for every operator; a comparison whose field or operator is not one of DM-R-25 and DM-R-26, or whose value has the wrong form for the field, is false. Answer `Completed(label)` with no result reference. **Wait (DM-S-11;** computed by the package-private `WaitStep` from an `IncidentView`, the parameters, the stored step state and now**):** `start`: mode `duration` → `Waiting({}, now + duration, {"due_at": "{instant}"})`; mode `until_event` → when the incident's `acknowledgedAt` is set, `Completed(event_received)`, otherwise `Waiting({incident_acknowledged}, now + timeout, {"due_at": "{instant}"})`. `evaluate`: mode `until_event` and acknowledged → `event_received`; now ≥ the stored `due_at` → `timed_out`; otherwise the same `Waiting` again (same due time). The Duration parameters are integers of seconds named `duration` and `timeout` (DD-R-07 (2), CTX-D-055 (6)).

**Action step guard (DM-R-31, PM-M12-06, SL-B-04;** computed by the package-private `ActionGuard` from the run's content, its step executions and the `ActionRuns` answers**).** Before the first call of a new Action step execution (not for a retry of the same step execution and not before `reconcile` in case (g), DM-R-64), the conditions are checked in this order; the first that fails gives `Completed(failed)` with no result reference, no call to `vigil-actions`, and its `refusal_reason` (DC-TX-11, exact): (1) `ActionRuns.proposal(run)` empty: `no action proposal in this run`; (2) no Approval step execution of the run that completed with `approved` and started after the step execution `ActionRuns.lastExecutedStepExecution(run)` (any, when that is empty; order: `started_at`, then `id`): `no approval after the last execution`; (3) the run's latest completed Approval step execution (order: `finished_at`, then `id`) did not leave by `approved`, or has no `result_ref`, or `ActionRuns.proposalOfRequest` of its `result_ref` id is not the run's proposal: `the latest approval is not for this run's proposal`; (4) a path from an output of the Action step does not reach a Recovery check step: `an output of this step does not reach a Recovery check step`. Path rule (on the run's content, with the engine's table of outputs): for each output of the Action step (`succeeded`, `failed`), the output has a connection, and from its target, following every output of every step that is not a Recovery check step, no output without a connection is reached and no step is reached twice on one path (a cycle; the Action step itself counts).

### 6.7 Wakes, timers, cancellation, restart and active tenants (AR-R-20, AR-R-23, AR-R-24)

**Wakes.** `EngineIncidentListener`, `EngineIntakeListener`, `EngineApprovalListener` (package-private, `@Profile("!migrate")`, `@ApplicationModuleListener`; each does nothing for a tenant that is not active, `TenantService.isActive`): `AlertStateChanged` and `SourceHealthChanged` → every unfinished live run of the tenant whose current step execution is of type `recovery_check`, reason `event:alert_state_changed` or `event:source_health_changed`; `IncidentAcknowledged` → every unfinished live run of the incident, `event:incident_acknowledged`; `IncidentStateChanged` to `merged` or `closed` → the cancellation below; to any other state → every unfinished live run of the incident, `event:incident_state_changed`; `ApprovalDecided` → the named run, `event:approval_decided` (a `waiting` run only when its current step execution is the event's `stepExecutionId`, DM-R-67). A run is marked (`wake_pending` true, `wake_reason`, `updated_at`) with one `UPDATE … WHERE state IN ('running', 'waiting') AND (…)` when it is `running`, or `waiting` with `step_waiting` and the event in its current step execution's `wake_events`, or `waiting` with `incident_forming` and the event `incident_state_changed`; each marked run is handed to its executor after commit.

**Timer poll (AR-R-23, DM-SM-09).** One task per active tenant, every 1 s (`TaskScheduler.scheduleWithFixedDelay`, as P-14's `ClosureWork`): in one transaction, the tenant's `pending` timers with `due_at` ≤ now, in `due_at` then `id` order, become `fired`; each one's run is marked with reason `timer` when it is `running`, or `waiting` with `step_waiting` and the timer is its current step execution's `timer_id`; marked runs are handed off after commit. A failure: the `WARN` line; the next tick tries again.

**Cancellation (DM-SM07-T5, AR-R-20).** In the transaction that decides it (the `IncidentStateChanged` listener; `startLiveRun` with `reopen`; part (1) for a merged or closed incident): each unfinished live run of the incident is locked and set `cancelled` with its `end_reason` and `finished_at`; its current step execution, when `running` or `waiting`, becomes `cancelled` with `finished_at`, and its `pending` timer `cancelled`; for a step type with a handler bean, the handler's `cancel(StepCancel)` is called in the same transaction; `StepChanged` (`cancelled`, when a step execution was cancelled), `RunFinished` and the `INFO` line. A run already ended is left as it is.

**Active tenants and restart.** `EngineWork` (package-private, `@Profile("!migrate")`, implements `EngineScheduling`) keeps the timer poll of each active tenant and writes the engine's set of active tenants, which is held by the package-private bean `ActiveTenants` (a `volatile` immutable set, no profile; `RunExecutors` and the executors read it without taking `EngineWork`'s lock, and `EngineWork` uses `RunExecutors`, so neither needs the other at construction). `synchronized matchActiveTenants()`: reads `TenantService.activeTenants()`; cancels the timer poll of each tenant no longer active; starts a timer poll for each active tenant that has none; when `resumeRuns()` has run, does for each active tenant not in the set (active again since the last call) what `resumeRuns()` does for a tenant (CTX-D-055 (7)); then the set is the active tenants. `synchronized resumeRuns()` (restart step 4, once): starts accepting hand-offs, sets the set to the active tenants and, for each, in one transaction: every `pending` timer with `due_at` ≤ now becomes `fired` (DM-E52-R1); every `waiting` run gets `wake_pending` true and `wake_reason` `restart` (DM-R-66); the current step execution of every `running` run gets `retry_due_at` `null` and `failed_attempts` 0; after commit every `running` and `waiting` run of the tenant is handed to its executor. For tests: `synchronized Set<TenantId> scheduledTenants()` (the tenants that have a timer poll; after each `matchActiveTenants()` equal to the engine's set of active tenants). `EngineAliasListener` (package-private, `@Profile("!migrate")`): `@ApplicationModuleListener` on `TenantAliasChanged` calling `matchActiveTenants()`. `RestartProcedure.step4StartRunExecutors()` calls `EngineScheduling.resumeRuns()`; `step6StartScheduledWork()` also calls `EngineScheduling.matchActiveTenants()`; `RestartProcedure` injects `EngineScheduling`.
