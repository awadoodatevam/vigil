## 2. Goal

Prove with the real services, before the connectors that depend on them are built (P-19, P-21, AR §19.3), that: a Jira Cloud issue can be created with a label, found by that label within the lag rule, commented in ADF with a working link, resolved and reopened through the API (SB-T-07); Claude and OpenAI answer the structured-output requests of AR-G-20 to AR-G-22 with the usage fields AR-G-14 reads; the local embedding model on the main host gives the same vectors twice and makes PI-1001 the storm's best match with 1.00 (SB-T-03, runtime part); and the local model on the GPU host answers an SL-T-1 request within 45 s (SB-T-04, local model part; AR-G-32). Every spike keeps the requests and answers it saw, without secrets or personal data, under `dev/fakes/recordings/`, so P-19 and P-21 test their connectors on them. The package also makes the GPU host's first start and records the `gemma4:12b` digest, and makes `deploy/secrets.sh` print the Jira token's expiry date from the secret (AR-H-07, BP-A-29).

## 6. Files and code

This spec, `docs/00-context.md` v1.29, `docs/50-architecture.md` v1.9 and `docs/60-build-plan.md` v1.18 are the branch's first commit, made by the owner (BP-L-3); they are binding for this package. Paths are relative to the repository root.

### 6.1 General rules

- The spikes are one folder, `spikes/providers/`, with a README, the bash entry `run.sh` (Section 6.9), the Python modules of Sections 6.2 to 6.8 and their pytest tests. Python 3.12, the standard library and PyYAML only (PyYAML reads the data files through `check_data.py`; HTTP is `urllib.request`). On the Mac, `run.sh` runs them in the virtual environment `spikes/providers/.venv` (Section 6.9); in the gate, the tests run with `/opt/vigil-tools/bin/python`, which has PyYAML.
- `run.sh` follows the rules of the P-05 spec Section 6.1 for Mac scripts (bash 3.2, `set -euo pipefail`, `shellcheck` clean, `cd` to the repository root, `AWS_REGION=us-east-1`, `AWS_PAGER=""`, the identity check of `deploy/lib/aws.sh`, no `--query`, waits through `pause`).
- Secrets: a spike reads a secret with `aws ssm get-parameter --name /vigil/demo/{name} --with-decryption --output json` (a subprocess; the `aws` found on `PATH`) and keeps the value in memory only. It never prints, logs or writes a secret value. A missing parameter stops the spike with "Missing secret /vigil/demo/{name} (AR-S-13)." and exit 1; any other failure of that call stops it with the call's standard error and exit 1; a value that is not what AR-S-13 names (for `jira` a JSON object with the strings `email`, `api_token` and `expires_on`, the last a valid `YYYY-MM-DD` calendar date; for `claude` and `openai` a non-empty string without whitespace) stops it with "Secret /vigil/demo/{name} is not valid (AR-S-13)." and exit 1. All of this happens before any file changes.
- Every file a spike writes (recording or result) is checked before it is written: when its text contains any secret value the spike read (each API key; the Jira `api_token`; the base64 of `{email}:{api_token}`), the Jira account's `email` (compared without regard to case) or its account ID (the `accountId` of the `myself` answer, literal or as `urllib.parse.quote(account_id, safe="")` encodes it), the spike writes nothing more and stops with "A secret would be written to {path}; nothing written." and exit 1.
- HTTP calls use `urllib.request` with the whole-call value of AR-TM-01 as the `timeout` argument (Claude and OpenAI chat 90 s; local model chat 120 s; embeddings 30 s, both providers; Jira 15 s); `urllib` applies it to the connection and to each read, which is the bound the spikes use (the product's exact connect and whole-call timeouts: P-19, P-21). Every call sends, besides the headers Sections 6.4 to 6.7 list, `User-Agent: vigil-p06-spike` (some providers refuse `urllib`'s default agent). An answer with any HTTP status is a result (an `HTTPError`'s status and body are read and recorded like a success); a connection failure or timeout is recorded with `response` `null` and `error` = the exception's text, and fails the check that needed the answer.
- Every wait goes through one function `pause(seconds)` (in `spikes/providers/common.py`) that sleeps, or not at all when `VIGIL_TEST_FAST=1`. Durations (`duration_ms`) are measured with `common.monotonic()` (which returns `time.monotonic()`; tests replace it) from just before the request is sent until its whole body is read.
- Order of every spike run: read and check its arguments, inputs and secrets; then remove the `*.json` files of its recording folder; then make its calls, writing each recording as soon as the call ends; then write its result file. A missing secret or input therefore changes no file.
- Exit codes of every spike and of `run.sh`: 0 when every check passed, 1 when a check failed or an error stopped the spike (the result file is still written with what was done, except (a) a stop while reading the arguments, inputs and secrets, which changes no file, and (b) a stop by the check that a file would hold a secret (the fourth rule of this section), after which nothing more is written and the files written before stay), 2 for wrong arguments (the usage lines of Section 6.12).
- Locations: results go to the folder in `VIGIL_SPIKE_RESULTS` (default `spikes/results/`), recordings to the subfolders of the folder in `VIGIL_SPIKE_RECORDINGS` (default `dev/fakes/recordings/`); relative defaults are taken from the repository root, found from the script's own location. The tests set both to temporary folders, so the gate never changes the committed files.
- Base addresses: `jira_spike.py` and `ai_spike.py` take an optional `--address {url}` that replaces the real base address in the calls (default: Section 6.4 and 6.5); `similarity_spike.py` and `local_model_spike.py` require it. The recordings write the placeholders of Section 6.2 rule 1 whatever the address. The tests point every spike at their fakes this way.
- After a failed check a spike goes on with the next calls and checks that do not need the failed one's answer; a check that needs an answer that does not exist is listed with `passed` false and `detail` "not run", and its call is not made (Sections 6.4 to 6.7 name the cases where a failure stops the spike). Example: when `past-1` fails, `storm-1`, `past-2` and `storm-2` are still made, and `same-vectors` and `best-match` are "not run".
- A spike prints one line per check, `{check}: passed` or `{check}: FAILED ({detail})`, then `result: {path}`.

### 6.2 Recordings and results (`spikes/providers/common.py`)

**Recording folders** (complete list, each with a `README.md` describing its files as `dev/fakes/recordings/monitoring/README.md` does): `dev/fakes/recordings/jira/` (SB-T-07), `claude/`, `openai/` (Responses and embeddings), `local-embed/` (SB-T-03), `local-llm/` (SB-T-04). A spike run removes the `*.json` files of its folder (the README stays) at the point Section 6.1 names, then writes one file per recorded call, `{n:04d}-{call}.json`, `n` counting the recorded calls from 1 in call order (the calls marked "not recorded" get no file and no number), `{call}` the call name of Sections 6.4 to 6.8.

**Recording file** (a JSON object; complete list of keys): `seq` (n); `call`; `started_at` (UTC, RFC 3339 with milliseconds); `duration_ms` (integer); `request`: `{method, url, headers, body}`; `response`: `{status, headers, body}` or `null`; `error` (`null` or text). Rules (complete list):

1. `url` is the address as the product's connector instance would write it, with the instance's address as written in `07-settings.yaml` in place of the real base address: `${endpoint.jira}`, `${endpoint.claude}`, `${endpoint.openai}`, `${endpoint.local_embedding}`, `http://${gpu_host_ip}:11434`; then the path and query exactly as sent.
2. `request.headers`: the headers the spike set explicitly (the lists of Sections 6.4 to 6.7 and `User-Agent`; not the ones `urllib` adds itself, such as `Host`, `Content-Length`, `Connection` and `Accept-Encoding`), names spelled as those sections spell them (not as `urllib` stores them), with the values of `Authorization` and `x-api-key` replaced by `<redacted>` (Jira: `Basic <redacted>`; OpenAI: `Bearer <redacted>`).
3. `request.body` and `response.body`: the text exactly as sent or received (`""` when none), except: every occurrence of the Jira site's address (`endpoint.jira` of `deploy/values/demo.yaml`) is replaced by `${endpoint.jira}`, and every occurrence of the Jira account's `email`, without regard to case, by `<email>`. Every occurrence of the account's ID (the `accountId` of the `myself` answer), literal and in its percent-encoded form (`urllib.parse.quote(account_id, safe="")`, as in `…/user?accountId=712020%3A…`), is replaced by `<account-id>`. Jira answer bodies that are JSON also have the value of every key named `accountId`, `emailAddress`, `displayName` or `avatarUrls`, at any depth, replaced by `"<redacted>"` and are then written as `json.dumps(value, ensure_ascii=False)` (equal in content to the answer, not in text). Personal data stays out of the repository.
4. `response.headers`: only `Content-Type` (`{}` when the answer has none).
5. The secret check of Section 6.1 runs on the finished text of the file.

**Result file** (`P-06-{name}.json` in the results folder, names in Sections 6.4 to 6.8; a JSON object; complete list of common keys): `spike` (the `{name}` of the file: `SB-T-07`, `claude`, `openai`, `SB-T-03` or `SB-T-04`); `run_id` (the UTC start time `YYYYMMDDTHHMMSSZ`); `started_at`, `finished_at` (RFC 3339, milliseconds); `passed` (true only when every check passed); `checks`: a list of `{name, passed, detail}` in the order run (`detail` `""` for a passed check) (a check not reached because an earlier error stopped the spike is listed with `passed` false and `detail` "not run"); plus the spike's own keys. A new run replaces the file.

### 6.3 The SL-T-1 and SL-T-2 requests (`spikes/providers/request_data.py`)

Built from `docs/31-demo-data/` with the functions of `docs/31-demo-data/tools/check_data.py`, loaded with `importlib` from that path (complete list used: `load`, `Map`, `lab_alerts`, `classify`, `hypothesis`, `impact`, `title`; its `main` is never called). The storm, as `check_data.main` computes it: every lab alert gets its type from `classify` over `alert_type_mappings` and its component from `Map.match`; the storm alerts are those whose `fires_in` holds `SL-F-1`, in the order `lab_alerts` returns them; the storm's components are the sorted set of their components; `hyp, counts = hypothesis(m, components)`; `services = impact(m, components)`; the storm title is `title(m, {alert_type: display_name}, hyp, storm_alerts, services)` (DD-K-06: "Subscriber DB server: Disk full — 3 services affected"). Everywhere in this section, "comma-separated" means joined with `, ` (as `check_data.py` joins).

**Parts of SL-T-1** (complete list, in this order; label, data category of DM-R-43, text):

1. `Member alerts`, `alert_data`: one line per storm alert, `{i}. {alert type key} | {component key} | {source} | {detail}`, `i` from 1; `{source}` is the alert's `source` as `lab_alerts` returns it (`zabbix` or `alertmanager`). `{detail}` for Zabbix: the alert's `event_name`, then ` on {host}` (the `host` value of its identity pairs). For Alertmanager: its `alertname`; then ` on {instance}` when its identity pairs hold an `instance` value that is not `None`; then, when its catalogue row has `dimensions`, ` ({name}={value}, …)` with the alert's dimension values other than `instance`, in the row's dimension order. An alert's dimension values are those of its combination: `request_data.py` walks `lab_alert_catalogue` the way `lab_alerts` does (rows in file order, `itertools.product` over the row's `dimensions` in written order) and pairs the n-th combination with the n-th alert `lab_alerts` returns. (Example: `UssdGatewayTimeouts (node=…, menu=…)`; the exact names are those of `03-monitoring.yaml`.)
2. `Hypothesis`, `service_context`: `{component name} ({component key}), kind {kind}, criticality {criticality}; {n} other affected components depend on it` (`n` = `counts[hyp]`).
3. `Customer impact`, `service_context`: one line per entry of `services`, `{name} ({service_key}), criticality {criticality}, through {via, comma-separated}`.
4. `E1`, `E2`, `E3`, `diagnostic_output`: `{diagnostic name}: {summary}` for `disk_usage`, `largest_folders` and `disk_growth` in that order; the names are the `name` fields of those keys' entries in `diagnostic_definitions` of `04-operations-actions-recovery.yaml`, the summaries `lab_db_server.development_values.disk_usage`, `largest_folders` and `disk_growth` of `10-lab-and-faults.yaml`.
5. `RB-API-01`, `RB-DB-01`, `RB-USSD-01` (the DD-K-08 runbooks, in that order), `runbook_text`: `{title}` (from `load`'s `runbooks`), an empty line, then the runbook's text by DD-R-09, which `request_data.py` reads from `08-runbooks.md` itself: the lines after the last line that starts with `|` below the runbook's `## ` heading, up to the next line that starts with `## ` or the end of the file, joined with newlines and `strip()`ped.

**Parts of SL-T-2** (complete list, in this order), built after that provider's SL-T-1 answer was accepted by Section 6.5's checks: `Title`, `incident_record`: the storm title; `Investigation`, `incident_record`: `Likely cause: {likely_cause}` and `Uncertainty: {uncertainty}` on two lines; `Alerts`, `alert_data`: `{count} alerts of {k} types: {type keys, sorted, comma-separated}`; `Customer impact`, `service_context`: as SL-T-1 part 3; `Hypothesis`, `service_context`: as SL-T-1 part 2; `E1` to `E3`, `diagnostic_output`: the summary only.

**Rendering** (AR-G-10): the user message is the parts joined by one empty line, each part as the line `### {label} ({data category display name})` followed by its text on the next lines; the display names are those of `40-demo-cut` ("Alert data", "Service context", "Diagnostic output", "Runbook text", "Incident record").

**System texts** (exactly; AR-G-12's rules):

- SL-T-1: "You are an IT and service NOC investigator. Use only the information in the supplied parts. Give the most likely cause of the incident in likely_cause. In hypothesis_verdict, say whether the likely cause confirms or disputes the supplied hypothesis, or not_applicable when no hypothesis is supplied. In evidence_labels, list the labels of the evidence entries (E1, E2, ...) the likely cause rests on. In uncertainty, state what remains uncertain. In runbooks_cited, list the key of every supplied runbook whose steps address the likely cause, and no other key. Do not decide severity, owner or any action. Answer only with the JSON object."
- SL-T-2: "Write a summary of at most 600 characters for NOC staff in summary, in plain sentences, using only the supplied parts. Answer only with the JSON object."

**Schemas** (AR-G-11), as JSON objects with keys in this order: SL-T-1 `{"type": "object", "properties": {"likely_cause": {"type": "string"}, "hypothesis_verdict": {"type": "string", "enum": ["confirms", "disputes", "not_applicable"]}, "evidence_labels": {"type": "array", "items": {"type": "string"}}, "uncertainty": {"type": "string"}, "runbooks_cited": {"type": "array", "items": {"type": "string"}}}, "required": ["likely_cause", "hypothesis_verdict", "evidence_labels", "uncertainty", "runbooks_cited"], "additionalProperties": false}`; SL-T-2 `{"type": "object", "properties": {"summary": {"type": "string"}}, "required": ["summary"], "additionalProperties": false}`. Maximum output units: SL-T-1 1,500; SL-T-2 600.

**Output check** (`valid_output(text, schema)`): the text parses as JSON and is an object with exactly the schema's properties, each of the declared type (a string; an array of strings; for `hypothesis_verdict` one of the enum values). It returns the object or the reason it failed (`not JSON`, `not an object`, `missing {name}`, `unexpected {name}`, `{name} has the wrong type`, `{name} is not one of the allowed values`). Whether the answer cites RB-DB-01, and the length of an SL-T-2 summary, are recorded, not checked (P-20, SB-T-02).

**Search texts** (DM-R-51): `alert types: {keys, sorted, comma-separated}; services: {keys, sorted, comma-separated}; component: {key}` for the storm (its alert types, the `service_key`s of `services`, `hyp`) and for each of the 50 past incidents of `09-past-incidents.csv` in file order (its `alert_types`, `affected_service_keys` split at `;`, and `hypothesis_component_key`), as `check_data.py` DD-K-09 builds them.
