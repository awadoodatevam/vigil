## 2. Goal

Build `vigil-correlation` (PM-M08): the per-tenant correlation worker that reads the intake log in `sequence` order from a stored cursor and retries a failed decision without skipping it (AR-R-17, AR-R-18, AR-R-26), the grouping decision of each alert (DM-E-29, DM-R-05, DM-R-06, DM-R-08 to DM-R-11) with the merge of forming incidents (DM-R-12) and the reopen rule (DM-R-21), the hypothesis computation (DM-E-30, DM-R-18) and the customer impact (DM-R-19), the routing evaluations of PM-M08-07, the stability check that opens a forming incident with its final grouping reasons (DM-R-15, DM-R-58), the audit events `alert_grouped` and `hypothesis_changed` (DM-E08-R3), the `correlation` health indicator (AR-H-12), restart step 5 (AR-R-24), the correlation settings (DM-E-31) as seed part 10, and the alerts of a component for `vigil-recovery` (PM-M08-10). Every change of an incident is a request to `vigil-incidents` (P-14) and every assignment a request to `vigil-routing` (P-15). The lab storm of the demo data, fed in 20 random orders, gives one storm incident with the expected hypothesis, impact and title and a separate SL-F-3 incident (PM-M08-06, SL-A1-02).

### 6.1 General rules

- Every public type of `vigil-correlation` is in `vigil.correlation.api` (AR-R-04); every other class is package-private in `vigil.correlation`. The `@ApplicationModule(allowedDependencies = {"shared", "tenancy :: api", "intake :: api", "servicemap :: api", "incidents :: api", "routing :: api", "audit :: api"})` of `vigil.correlation` stays unchanged, and so do the declarations of `vigil.setup` and `vigil.api`. No public type of `vigil.correlation.api` names a type of another module's `api` package (types of `vigil.shared` are used).
- Records are written with `JdbcClient`. Each decision and each stability transition is one transaction (`TransactionTemplate`), in which the requests to `vigil-incidents`, `vigil-routing` and `vigil-audit` take part (AR-R-11); reads have no transaction of their own.
- Time from the `Clock` bean through `Timestamps.now(clock)`, read once per decision or stability transition; ids from `Ids.newId()`; lengths in Unicode code points; "cut to n" is the first n code points. Waiting (the worker's wake interval, the retry delays) is real time, not the `Clock`.
- The actor of every request to another module is `Actor.module("vigil-correlation")`.
- Source kinds are mapped by key: `vigil.intake.api.MonitoringKind` → `vigil.servicemap.api.SourceKind` (`fromKey(kind.key())`); identity pairs `IdentityPair` → `IdentityKey` in the alert's order.
- `null` arguments of the public requests: `IllegalArgumentException`.
- Logging: per tenant worker, one `INFO` line when it starts and when it stops (tenant id); one `ERROR` line per failed decision attempt (Section 6.7); nothing at `INFO` or above per decision.
- Every list returned is unmodifiable.
- Classes that run work or report on it (the worker, the two listeners, the health indicator) have `@Profile("!migrate")`, as P-13 and P-14; no other class has a `@Profile`.

### 6.5 Seed part 10 (DM-E-31, DM-R-57, AR-B-11)

### 6.6 The decision of an alert

The worker (Section 6.7) decides each alert X returned by `IntakeService.alertsAfter(tenant, cursor, 100)`, in that order, in one transaction (DM-R-09):

1. **Repeat (DM-R-61).** When the tenant has a decision for X: only the cursor is set to X's `sequence`; nothing else.
2. **Settings.** The tenant's correlation settings (the worker runs only for a tenant that has them) and incident settings (`IncidentService.settings`; without them no incident is reopened).
3. **Match (DM-R-05, DM-R-06).** `ServiceMapService.match(tenant, kind, pairs)` with X's source kind and identity pairs in order: the decision's `generation` and `component_key` (`null`: unknown component). The member copies of `vigil-incidents` hold the component key decided here; it is never recomputed.
4. **The alert copy** for `vigil-incidents` (P-14 `AlertCopy`): X's id, source kind key, alert key, alert type, the alert type's `displayName` from `IntakeService.alertTypes` (read once per decision), title, the matched component key, the first identity pair (or `null`), `fired_at`.
5. **Alert relation (DM-R-07, DM-R-08)** of X to a member Y (a member's data is its `MembershipView.alert` copy): (a) both components known: `ServiceMapService.relation(tenant, X.component, Y.component)` is not `NONE` — its kind is the relation (`same_component`, `depends_on` = X's component depends on Y's, `depended_on_by`) and its path the `relation_path` (from X's component to Y's, both included, as P-12 returns it); both unknown with the same source kind and the same first identity pair (name and value; neither `null`): `same_unknown_identity` with an empty path; otherwise not related; and (b) `|X.fired_at − Y.fired_at|` ≤ `grouping_window`. `time_delta` = that difference rounded to the nearest whole second, halves up.
6. **Related alert (DM-R-11)** of X among a set of members: among the members related to X, the one with the earliest `fired_at`; ties: the source kind first in code point order, then the alert key first in code point order.
7. **Candidates (DM-R-10)**: the incidents of `IncidentService.incidents(tenant, {FORMING, OPEN})` with an active member (`members`) related to X. Then exactly one of:
   - (a) **No candidate.** The reopen rule (DM-R-21): the `resolved` incidents R (`incidents(tenant, {RESOLVED})`) with `resolved_at` ≤ X's `first_received_at` ≤ `resolved_at + reopen_window` and an active member whose component is related to X's by (5)(a) alone (the time condition (5)(b) does not apply); of these, the lowest `sequence`. It is reopened (`IncidentService.reopen`, decision `reopened`) with the reason of (6) over R's members related by (5)(a), `time_delta` measured to that member. Otherwise a new incident (`IncidentService.create`, decision `created_incident`, the four reason fields `null`). (Edge accepted: when `ClosureWork` of P-14 closes R between the read and the `reopen` request, `reopen` throws `IllegalStateException`, the attempt fails and is retried (Section 6.7), and the retry, which no longer sees R as `resolved`, creates a new incident; the demo never reaches this, DM-R-24 (a).)
   - (b) **At least one `open` candidate.** X joins (`addAlert`, decision `joined`) the `open` candidate with the lowest `sequence`, with the reason of (6) over its members; no merge.
   - (c) **All candidates `forming`.** X joins the candidate with the lowest `sequence` (the survivor), with the reason of (6) over the survivor's members before the merge; then, when there are other candidates, `IncidentService.merge(tenant, actor, survivor, the other candidates in ascending sequence)` (DM-R-12); `merged_incident_ids` = those ids in that order.
8. **Record (DM-E-29).** The decision id is made first and passed with the request as `groupingDecisionId`; the record is stored after the request (its `incident_id` is the incident the alert went to; for `created_incident` the id `create` returned), `decided_at` now.

### 6.7 The worker (AR-R-17, AR-R-18, AR-R-26, DM-R-62, DM-R-70)

`CorrelationWork` (package-private, `@Profile("!migrate")`, implements `CorrelationScheduling`): a map from tenant to its worker; `synchronized matchActiveTenants()` stops the worker of each tenant no longer active (`TenantService.activeTenants()`) and starts one for each active tenant that has correlation settings and no running worker; when that tenant's previous worker is still ending, it first waits for its thread to end (at most 4 s in all per call, over all such tenants, so the listener of AR-E-14 stays within AR-R-14's 5 s; if it is still alive, a `WARN` line and no new worker until a later call), so a tenant never has two worker threads (the worker's own exit path, `runningTenants()`, `workerThread()`, `wake` and the health indicator's state never take the monitor of `matchActiveTenants`: they use concurrent maps); a tenant without settings gets no worker until a later call. For tests: `Set<TenantId> runningTenants()` and `Optional<Thread> workerThread(TenantId)`. When the application context closes, `CorrelationWork` stops every worker and waits for each thread to end (at most 10 s each), so no worker outlives its application (as a `SmartLifecycle` or a `@PreDestroy` method).

A worker is one virtual thread named `correlation-{tenant id}` (AR-R-26), and the only thread that decides, checks stability or reopens for its tenant (AR-R-18, DM-R-62). Its loop, until stopped: (1) read the cursor (0 when absent) and decide each alert of `alertsAfter(tenant, cursor, 100)` in order (Section 6.6), repeating while a batch is full; (2) the stability check of Section 6.6; (3) wait until woken or until `stability_check_interval` has passed. `wake(TenantId)` wakes a waiting worker (a wake while it is busy makes the next wait return at once).

Any other exception in the loop (the cursor read, `alertsAfter`, the settings or incident reads of the stability check): an `ERROR` line `correlation worker of tenant {tenant id} failed` with the exception, a wait of 5 s, and the loop continues; a worker ends only by a stop. This loop is also the correlation check of AR-R-23: no `TaskScheduler` task is registered for correlation (AR-R-17 and AR-R-18 give the worker the stability checks; CTX-D-053). **A failed decision** (any exception from the decision's transaction, which rolls back): an `ERROR` line `correlation decision of alert {alert id} for tenant {tenant id} failed (attempt {n})` with the exception; the same alert is tried again after 1 s, 5 s, 30 s and then every 60 s (attempt n + 1 after the delay for n: 1 → 1 s, 2 → 5 s, 3 → 30 s, ≥ 4 → 60 s); it is never skipped, no later alert of the tenant is decided before it, and no stability check of the tenant runs while the retry is pending; wakes do not shorten the delay. While a retry is pending the tenant is in the health indicator's list (below), updated with the attempt number before the `ERROR` line is written; a success removes it. A failed stability transaction is logged at `ERROR` (`correlation stability check of incident {incident id} for tenant {tenant id} failed`) and tried again at the next check; it does not change the health indicator.

**Stop**: sets the worker's stop flag and wakes it; the worker ends after its current transaction or at once from a wait (the thread is not interrupted inside a transaction); its pending retry is dropped from the health indicator. `matchActiveTenants` does not wait for it to end.

`CorrelationHealthIndicator` (package-private, `@Profile("!migrate")`, a bean named `correlationHealthIndicator`, so its contributor name is `correlation`, AR-H-12): `UP` with no details when no retry is pending; otherwise `DOWN` with details `{"retries": [{"tenant_id": "…", "alert_id": "…", "attempt": n}]}` (one entry per tenant with a pending retry, by tenant id, `attempt` the number of the failed attempts so far).

`CorrelationAliasListener` (package-private, `@Profile("!migrate")`): `@ApplicationModuleListener` on `TenantAliasChanged` calling `matchActiveTenants()` (as P-14). `CorrelationWakeListener` (package-private, `@Profile("!migrate")`): `@ApplicationModuleListener` on `AlertReceived` calling `wake(event.tenantId())` (AR-E-01 only wakes the worker; a tenant without a worker is ignored). Neither checks or writes anything. `RestartProcedure.step5StartCorrelationWorkers()` calls `CorrelationScheduling.matchActiveTenants()` (AR-R-24 (5)); the `@Profile("!migrate")` `RestartProcedure` injects `CorrelationScheduling`.
