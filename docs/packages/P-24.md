This spec, `docs/00-context.md` v1.38 and `docs/60-build-plan.md` v1.26 are the branch's first commit, made by the owner (BP-L-3); they are binding for this package. Paths are relative to `app/src/main/java/vigil/` unless they start with `app/` or `docs/`.

### 6.1 General rules

- Every public type of `vigil-actions` is in `vigil.actions.api` (AR-R-04); every other new class is package-private. The `@ApplicationModule` declaration stays as it is (`shared`, `knowledge :: api`, `runner :: api`, `servicemap :: api`, `incidents :: api`, `identity :: api`, `notifications :: api`, `recovery :: api`, `audit :: api`).
- Persistence with `JdbcClient`; transactions with `TransactionTemplate`; ids from `Ids.newId()`; time from the `Clock` bean through `Timestamps.now(clock)`; every statement filtered by `tenant_id`; no `DELETE`. Requests to other modules inside a transaction join it (AR-R-10). JSON with a `static final JsonMapper` (Jackson 3).
- External calls (AR-R-09): `ActionsStepHandler.start` and `evaluate` and `ActionRuns.reconcile` call `TransactionGuard.assertNoTransaction()` first. A runner request (`RunnerService.run`) and a message request (`NotificationsService.notifyApprovalRequest`) are made with no transaction open; every record they lead to is stored in a transaction opened after they return.
- The beans that implement `ActionsStepHandler` (`ActionSteps`) and `ActionRuns` (`ActionRunReads`) are injected by no other bean of the application, so a test can remove them (Section 6.12).
- Lengths are Unicode code points; "cut to n" keeps the first n code points. Lists of names are joined by `, ` in ascending code point order of the text shown, an empty list is `none` (DC-TX-00 "Lists"), unless a rule says otherwise. Times in stored texts use the outbound time format `YYYY-MM-DD HH:MM:SS UTC`; durations DC-U-07 rule (2). Instants in stored JSON are written with `Instant.toString()`.
- `null` arguments of public requests: `IllegalArgumentException("a required argument is missing")`.
- Actors: requests of `vigil-actions` use `Actor.module("vigil-actions")` (also the evidence entries of a decision, since `addEvidence` accepts only the producer module); only a decision's `approval_decided` audit event has the actor `Actor.user(userId)`, and its decision record holds the user.
- Logging (complete list at `INFO` or above from `vigil.actions`): `WARN` `approval request {request id} of incident {incident id} of tenant {tenant id}: the messages failed` each time `notifyApprovalRequest` answers `FAILED`; `WARN` `action execution {id} of incident {incident id} of tenant {tenant id}: {state key}` when an execution ends `failed`, `not_executed` or `unresolved`. No parameter value, output or secret is logged.
- Every list returned is unmodifiable. Texts named in this spec are exact.

### 6.4 The proposal and the policy check (`Proposals`; DM-R-29, DM-E-57, DM-E56-R2, PM-M14-02, PM-M14-03)

**The run's proposal.** The first Approval step execution of the run (the run has no request and no row in `actions.step_without_proposal`) creates it; every later Approval step execution uses the run's proposal, and when the run has none, it has no proposal either (DM-R-29). The first one, from the incident's latest similarity search result (`KnowledgeService.latestSearchResult`; DM-E66-R2), there is **no proposal** when (complete list, DM-R-29): there is no result; its outcome is `no_match`; it has no `fix_action_key`; the registered action of that key does not exist or is not active; the incident has no `hypothesis_component_key`; or that component has no target (`ServiceMapService.target` empty). Otherwise a proposal is stored (in the transaction of Section 6.6 step 3): the run, the incident, the action key, `action_snapshot` (Section 6.5), `component_key` the hypothesis component, `target_key` its target, the result's id, `past_incident_key` its `bestPastIncidentKey`, `score`, `success_count` (`successCount`, 0 when `null`), `created_at` now.

**The policy check** (DM-E56-R2): the policies of the proposal's action that are active; for each affected service of the incident (`IncidentView.affectedServices`, by `service_key`) the policy of (action, service) when there is one, else the policy with no service; with no affected service, the policy with no service; the result is the most restrictive taken, `blocked` > `approval_required` > `preauthorized`. An action with no default policy cannot be imported (DM-E56-R1); a policy check that finds none anyway: `IllegalStateException("no default policy for action {key}")`.

### 6.5 Snapshots, the hash and state checks (`Snapshots`, `StateChecks`; DM-V-08, DM-V-12, AR-P-03)

- **`action_snapshot`** (DM-E-57): `{"action_key", "name", "operation_key", "parameter_values", "limits", "attempt_limit", "precondition", "recovery_check_key"}` with the registered action's values; a state check as `{"operation_key", "parameters", "result_field", "operator", "value"}`. The `unchanged` recheck compares this object with the one built from the active registered action now, as JSON trees.
- **The approval snapshot** (DM-V-12; every key always present; the order written here is the order of the object built and hashed — the stored `jsonb` does not keep it, and RFC 8785 sorts the keys for the hash): `{"action_key", "action_name", "parameters" (the action snapshot's `parameter_values`), "target_key", "target_name" (the `name` of the `server` component whose `target_key` is the target, from `ServiceMapService.components`; the target key when there is none), "limits" (the action's limits), "attempt_number" (1 + the executions of the action for the incident that reached `executing`), "attempt_limit", "expires_at" (instant), "evidence": [{"evidence_entry_id", "kind", "summary", "collected_at"} for every evidence entry of the incident of kind `diagnostic_result`, `ai_investigation` or `similarity_match`, in `collected_at` order, then id], "based_on": {"past_incident_key", "past_incident_title", "record_label" (from `KnowledgeService.pastIncident`), "score" (text with two decimal places, Example `"1.00"`), "success_count"}, "recovery_checks": {"recovery_check_key", "name", "conditions" (the `requirementTexts` of `RecoveryService.definition`), "observation_window" (integer seconds: `observationWindow().toSeconds()`, DM-C-01)}}` (CTX-D-075 (6)). A recovery check key with no definition: `IllegalStateException("recovery check {key} not found")`.
- **`snapshot_hash`** (AR-P-03): `CanonicalJson.sha256HexOfCanonical` of the snapshot written as JSON text, 64 lowercase hexadecimal characters.
- **A state check** (DM-V-08): the operation run through `RunnerService.run(tenant, Actor.module("vigil-actions"), new RunRequest(requestId, DIAGNOSTIC, operation key, the proposal's target key, parameters))`. Its value: when the run is `succeeded` and its `outputValuesJson` holds an entry whose `name` equals `result_field` with a non-`null` value, that value as text; otherwise none. The comparison (CTX-D-075 (5)): when both the value and the check's `value` parse as `BigDecimal`, they are compared as numbers (`compareTo`); otherwise as texts in code point order; `equals` and `not_equals` with `compareTo == 0` and `!= 0`. A state check with no value is not true and not false: "could not be completed". A run answered `running` (a repeated request id of a run that a restart did not end, CTX-D-058 (9)) counts as no value and is never waited on.

### 6.6 The Approval step (`ApprovalStep`; DM-S-05, DM-R-29, DM-R-30, DM-SM-11, PM-M14-02 to PM-M14-04)

The engine calls `start` and `evaluate` on the run's virtual thread with no transaction open; a throw is a failed call, retried after 5 s, 15 s and 45 s (AR-TM-05). Each call, in order:

1. **Parameters.** A step type other than `APPROVAL`, or parameters that are not an object with `eligible_teams` a non-empty array of distinct keys and `expiry` a JSON integer (as `WorkflowPartCheck` checks a Duration) from 60 to 86,400: `IllegalArgumentException("approval step parameters: eligible_teams and expiry")`.
2. **Earlier calls** (DM-R-64): when the step execution has a request, go to step 4; when it has a row in `actions.step_without_proposal`, answer `Completed(rejected, null)` and write nothing.
3. **First call** (one transaction, in this order; the first that applies decides; DM-R-30):
   1. The proposal (Section 6.4). None: no request, no decision record, no event; a row of `actions.step_without_proposal` (run, incident, step execution, now) and the audit event `approval_decided` "No action was proposed." (Section 6.10) with subject type `StepExecution` and the step execution id; answer `Completed(rejected, null)` (CTX-D-075 (7)).
   2. `sequence_in_run` = the run's requests + 1; `eligible_team_keys` the parameter, sorted; `excluded_user_ids` the call's `earlierApprovers`, sorted; `expires_at` = now + `expiry`; the snapshot and its hash (Section 6.5).
   3. **Refusal** (DM-R-30 (2), DM-E60-R2): the executions of the proposal's action for the incident that reached `executing` number `attempt_limit` or more → `refused` with `attempt_limit_reached`; otherwise one of them is `unresolved` → `refused` with `unresolved_execution` (DM-SM11-T1). No policy check.
   4. Otherwise **the policy check** (Section 6.4): `blocked` → `blocked` (T2); `preauthorized` → `preauthorized` (T3); `approval_required` → `pending` (T4).
   5. The request is stored with its state (`decided_at` now for `refused`, `blocked`, `preauthorized`), and the audit events of Section 6.10 (`policy_check_result` except for `refused`; `approval_requested` for `pending`; `approval_decided` for `refused`, `blocked`, `preauthorized`); for `refused`, `blocked` and `preauthorized` the evidence entry (Section 6.9).
4. **Messages** (only for a `pending` request while now is before `expires_at`, with no transaction open; on the first call and on every later call before the expiry, which sends only what was not sent, DM-R-65): the recipients are every user of `IdentityService.teamMembers` of each eligible team who is `active`, holds `APPROVE_ACTION` and is not in `excluded_user_ids` (PM-M14-04, DM-R-30), once each, by username; each user's `viaTeamKey` the first eligible team, in code point order, of which the user is a member (DM-E-59 `team_key`). With at least one recipient: `NotificationsService.notifyApprovalRequest(tenant, incident, request id, recipients, action name, target name, expires_at)`; `FAILED` is logged (Section 6.1) and changes nothing. With none, no request is sent and the request waits for its expiry (DM-R-30).
5. A request that is not `pending` answers at once (step 6).
6. **The answer by the request's state** (one transaction, the request read `FOR UPDATE`): `pending` and now ≥ `expires_at` → `expired` (DM-SM11-T7), `decided_at` now, with its audit event and evidence entry, then answers `expired`; `pending` otherwise → `Waiting({APPROVAL_DECIDED}, expires_at, null)` (after step 4); `approved` and `preauthorized` → `Completed(approved, ref)`; `rejected`, `blocked`, `refused` → `Completed(rejected, ref)`; `expired` → `Completed(expired, ref)`; `cancelled` → `IllegalStateException("approval request {id} is cancelled")` (the engine logs the failed call of a run it has cancelled; AR-Q-11 (e)). `ref` is `ResultRef("vigil-actions", "ApprovalRequest", request id)` (the engine's guard reads the request's proposal through it, DM-R-31).

**`cancel`** (DM-SM11-T8, DM-SM07-T5; joins the caller's transaction, AR-R-21): the request of the step execution, when it is `pending`, becomes `cancelled` (`decided_at` now; no evidence, no audit event, no event); any other state or none: nothing. A cancel that comes while `start` is still running (AR-Q-11 (e)) finds the request when it was already stored; when it was not, the engine's store of the answer calls `cancel` again after `start` returns (AR-R-22), so the request ends `cancelled` either way; when the cancel comes before the request is stored, the request's messages are still sent by that `start`, and the request ends `cancelled` when the engine stores the answer. An Action step's `cancel` does nothing.

### 6.7 The decision (`Decisions`; DM-E-59, DM-E59-R1, DM-R-63, DM-SM11-T5, DM-SM11-T6, AR-E-09, PM-M14-05)

`decide(tenant, requestId, userId, decision, snapshotHashShown)` — called by `vigil-api` for the signed-in user (P-25). One transaction that locks the request row (DM-R-63), checks in this order (the first failing check refuses; CTX-D-075 (8); the messages are those of DC-S05-06 with times in the outbound format, the details carry the values the page formats itself, as `acknowledge` does in P-14: ids as text, instants as `uuuu-MM-dd'T'HH:mm:ss.SSS'Z'` in UTC):

0. The user does not hold `APPROVE_ACTION` (or is not an active user): `VigilError` `FORBIDDEN` (default message). No request of the tenant with that id: `NOT_FOUND`.
1. `cancelled` → `REFUSED` `This request was cancelled because the incident's workflow run ended.` details `{"refusal": "cancelled"}`.
2. `preauthorized`, `blocked` or `refused` → `REFUSED` with its state text of DC-TX-01 (Example `Preauthorized by policy`), details `{"refusal": "not_pending", "state": key}`.
3. `approved` or `rejected` → `REFUSED` `Already {approved or rejected} by {user display name} at {decided_at}.` details `{"refusal": "already_decided", "state": key, "user_id", "at"}`.
4. `expired`, or `pending` with now ≥ `expires_at` → `REFUSED` `This request expired at {expires_at}.` details `{"refusal": "expired", "at"}` (the request stays `pending` until its step expires it).
5. The user is not an active member of any eligible team (`IdentityService.isMember`) → `REFUSED` `You are not in a team that can approve this action ({eligible team names}).` details `{"refusal": "not_eligible"}`.
6. The user is in `excluded_user_ids` → `REFUSED` `You approved an earlier step of this run. A different approver is needed.` details `{"refusal": "excluded"}`.
7. `snapshotHashShown` differs from `snapshot_hash` → `REFUSED` `This request changed after you opened it. Reload the page to see the current request.` details `{"refusal": "snapshot_changed"}`.

Accepted: the decision record (`team_key` the first eligible team, in code point order, of which the user is a member; `at` now); the request `approved` or `rejected` with `decided_at` now and `decided_by` the user; the audit event `approval_decided` (actor the user); the evidence entry; and `ApprovalDecided(tenant, request id, run id, step execution id)` published in the transaction (AR-E-09; the engine's listener wakes the run). Returns the request.

### 6.8 The Action step (`ActionStep`; DM-S-06, DM-R-32, DM-R-33, DM-E60-R1, DM-E60-R2, DM-SM-12, PM-M14-07, PM-M14-08)

`start`, `evaluate` and `ActionRuns.reconcile(call)` run the same procedure (CTX-D-075 (4)): it continues the execution of the call's step execution from its stored state; a final state answers at once. The step never waits. A step type other than `ACTION`: `IllegalArgumentException("action step parameters")`.

1. **Record** (DM-SM12-T1, DM-E60-R1; only when the step execution has no execution): the run's proposal (none: `IllegalStateException("no action proposal in run {id}")`; the engine's guard does not start the step then, DM-R-31); the requests relied on (DM-R-32): the run's requests for the proposal in state `approved` or `preauthorized` created after the run's latest execution that reached `executing` (`executing_at`), or since the run started when there is none, by creation; stored `recorded` with `attempt_number` (Section 6.2), `started_at` now, `recheck_pass` 0, no recheck. This transaction commits before any runner request.
2. **Rechecks** (from `recorded` or `rechecking`, DM-SM12-T2; after a restart the rechecks start again, DM-SM-12 note): one transaction sets `rechecking` and `recheck_pass` + 1 (= `m`), clearing `recheck`. Then, in order, each stored when done, stopping at the first that fails (CTX-D-075 (3)):
   - `approval_valid`: at least one request relied on, each `approved` or `preauthorized` with now before its `expires_at`. Detail `approved by {names}; valid until {earliest expires_at}` where `{names}` are the display names of the requests' `decided_by` (a `preauthorized` request counts as `policy`), as a list; with no request relied on, `no approval`.
   - `unchanged`: the active registered action of the proposal's key gives the proposal's `action_snapshot` (Section 6.5), the incident's `hypothesis_component_key` equals `component_key`, and its target equals `target_key`. Detail `unchanged since approval`, or `changed: {parts}` with the parts that differ in the order `action`, `hypothesis component`, `target`, joined by `, `.
   - `incident_open`: the incident is `open`. Detail its state text of DC-TX-01 (`Open`, `Resolved`, …).
   - `precondition`: the precondition state check (Section 6.5) with request id `{execution id}:precondition:{m}` (DM-E14-R1), with no transaction open; true passes; false or no value fails. Detail `{operation name} ({parameters as name=value, by name in code point order, joined by ', '}): {value read} {operator symbol} {value}` with the symbols of DC-TX-01 (demo `Used percentage of one filesystem (mount=/data): 100 ≥ 90`); with no value, `{operation name} ({parameters}): no value read` (CTX-D-075 (3)).
   - A failed recheck → `not_executed` (DM-SM12-T3), `finished_at` now, with its evidence entry and audit event (Section 6.10); the answer `failed`.
3. **Execute** (DM-SM12-T4): one transaction sets `executing` and `executing_at` now; it commits before the runner call. Then, with no transaction open, `RunnerService.run(tenant, Actor.module("vigil-actions"), new RunRequest("{execution id}:execute", ACTION, the snapshot's operation key, the proposal's target key, the snapshot's parameter values))`; then one transaction stores `operation_run_id` and: `succeeded` → `succeeded` (T5); `failed` or `refused` → `failed` (T6); `unknown` → `reconciling` (T7). A call that finds the execution `executing` (a retry or a restart after the runner call started) goes to `reconciling` (T7) without calling the runner's `execute` again (a repeated request id would return the earlier run, DM-E14-R1, but the result of an interrupted run is decided by reconciliation, DM-R-33).
4. **Reconcile** (DM-R-33, AR-TM-06): from `reconciling`, attempts `n` = (the stored `reconciliation_run_ids` count) + 1 up to 3: the registered action's (by key, active or not) reconciliation state check with request id `{execution id}:reconcile:{n}`; its run id appended in a transaction after it returns; true → `succeeded` (T8); false → `failed` (T9); no value → wait 10 s (`Thread.sleep` on the run's thread) and try again; after the third attempt with no value → `unresolved` (T10). A call that finds three run ids stored and no decision reads the third run (`RunnerService.operationRun`) and decides from it; with no value, `unresolved`.
5. **End**: a final state stores `finished_at` now, the evidence entry and the audit event (Sections 6.9, 6.10) in the transaction that sets it. (An incident that is `closed` or `merged` cannot get evidence; it cannot have a running Action step either, because closing or merging an incident cancels its run, AR-R-20.) The answer: `succeeded` → `Completed(succeeded, ref)`; `failed`, `not_executed`, `unresolved` → `Completed(failed, ref)`, with `ref` = `ResultRef("vigil-actions", "ActionExecution", id)`.

### 6.8a The reads of `vigil-engine` (`ActionRunReads`; DM-A-15, DM-R-31, DM-R-34, PM-M12-07)

Each read is one query of `vigil-actions`' own tables, joins the caller's transaction and writes nothing (complete list):

- `proposal(tenant, run)`: the id of the run's proposal, or empty.
- `proposalOfRequest(tenant, request)`: the request's `proposal_id`, or empty for an unknown request.
- `lastExecutedStepExecution(tenant, run)`: the `step_execution_id` of the run's execution with the latest `executing_at` (then the greatest id), among those that reached `executing`; empty when none did.
- `earlierApprovers(tenant, run)`: the `decided_by` of the run's requests in state `approved` (a `preauthorized` request has no approver), by `decided_at`, then id, each user once.
- `latestRecoveryCheckKey(tenant, run)`: the `recovery_check_key` of the proposal's `action_snapshot` for the execution that `lastExecutedStepExecution` gives (the action as it was approved and executed, DM-R-34), or empty.
- `reconcile(call)`: Section 6.8.

### 6.9 Texts and evidence (`ActionTexts`; DC-TX-01, DC-TX-03, PM-M14-09)

`{action name}` the snapshot's name; `{target name}` as in Section 6.5; `{user display name}` from `IdentityService.user` (the id as text when not found).

- **Approval evidence** (kind `approval`, producer record the request id, `collected_at` `decided_at`, data category `INCIDENT_RECORD`), one per request that reaches `approved`, `rejected`, `expired`, `preauthorized`, `blocked` or `refused` (DC-TX-03; none for `cancelled` or "no proposal"). Summary by state: `Approved by {user display name}: {action name} on {target name}.`; `Rejected by {user display name}: {action name} on {target name}.`; `Approval expired with no decision: {action name} on {target name}.`; `Preauthorized by policy: {action name} on {target name}.`; `Blocked by policy: {action name} on {target name}.`; `Approval refused ({attempt limit reached or an earlier execution has an unknown result}): {action name} on {target name}.` `source_system` `Approval {sequence_in_run} of the run`. Content `{"approval_request_id", "state", "sequence_in_run", "policy_outcome" (key or null), "decided_by" (id or null), "decided_at", "action_key", "target_key", "snapshot_hash"}`.
- **Execution evidence** (kind `action_execution`, producer record the execution id, `collected_at` `finished_at`, `INCIDENT_RECORD`), one per execution at its final state: `{action name} on {target name}: {state text}.` with `{state text}` of DC-TX-01 (`Succeeded`, `Failed`, `Result unknown`); when the execute run (`RunnerService.operationRun` of `operation_run_id`; none when there is no id) has output values and the operation's parser is `removed_files`, `; {files_removed} {file or files} removed ({gib_removed} GiB)` before the full stop (DC-TX-00 "Counts", CTX-D-075 (3)); for `not_executed`, `{action name} on {target name}: not executed, recheck '{recheck name}' failed.` with the recheck names of DC-TX-01 (`Approval still valid`, `Action, parameters and target unchanged`, `Incident still open`, `Precondition`). `source_system` `{target_key} via runner, operation {operation_key}`. Content `{"action_execution_id", "state", "attempt_number", "action_key", "target_key", "operation_key", "operation_run_id", "output_values" (the execute run's array, or null), "recheck"}`.
- **Recheck JSON** (`recheck`): `[{"check": key, "passed": boolean, "detail": text cut to 300}, …]` in the order run.

### 6.10 Audit (DM-E08-R1, DM-E08-R3, DC-TX-10; CTX-D-075 (2))

Each in the transaction of the change it reports; actor `Actor.module("vigil-actions")` unless named; the incident id set:

- `policy_check_result`: one per request with a policy outcome; subject `ApprovalRequest`; `Policy for {action name}: {policy check result}.` (DC-TX-01: `Approval required`, `Preauthorized`, `Blocked`); details `{"outcome": key}`.
- `approval_requested`: one per `pending` request; subject `ApprovalRequest`; `Approval {sequence_in_run} requested for {action name} on {target name} from {eligible team names}.`; no details.
- `approval_decided`: one per request that reaches `approved`, `rejected` (actor the user), `expired`, `preauthorized`, `blocked` or `refused`; subject `ApprovalRequest`; `Approval {n}: {approval request state text} — {action name} on {target name}.` with ` by {user display name}` after the state text for a human decision (Example `Approval 1: Approved by Usman Tariq (DB Ops) — Purge archived transaction logs on Subscriber DB server.`); details `{"decision": state key}` and, for a human decision, `"user_id"`. "No proposal": subject `StepExecution`, `No action was proposed.`, details `{"decision": "no_proposal", "run_id"}`.
- `action_executed`: one per execution that reaches `succeeded` or `failed` from `executing`, or `not_executed`; subject `ActionExecution`; `{action name} on {target name}, attempt {n}: {action execution state text}.` (`attempt {n}` the execution's attempt number); details `{"attempt_number", "outcome": state key}`.
- `action_reconciled`: one per execution that reaches `succeeded`, `failed` or `unresolved` from `reconciling`; subject `ActionExecution`; `{action name} on {target name}, attempt {n}: result checked, {Succeeded, Failed or Result unknown}.`; details `{"attempt_number", "outcome": state key}`.

### 6.11 Seed part 14 (`ActionsAdapter`, `ActionsImporter`; DM-R-56 (14), DM-R-57, AR-B-11, DD-F-04)
