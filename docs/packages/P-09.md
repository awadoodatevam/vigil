## 2. Goal

Build the foundation of `vigil-api`, the only way into Vigil (PM-M23): every `/api` request except the installation paths is tied to the tenant that its host name's alias points to; errors have one format with a default message per code; users log in, are recognised by the `vigil_session` cookie and log out; state-changing requests carry the CSRF header; every operation declares its access (public, logged in, or a permission) and is refused before any module is called when the caller lacks it; logged-in screens open a live update stream of change notices with heartbeats and a 300 s limit, fed by an in-process hub that later packages publish to. The package builds the seven operations AR-I-10 to AR-I-16, writes them into the OpenAPI 3.1 file, and adds the contract test that keeps the file and the code equal (BP-R-13).

## 6. Files and code

This spec, `docs/00-context.md` v1.14, `docs/50-architecture.md` v1.4 and `docs/60-build-plan.md` v1.6 are the branch's first commit, made by the owner (BP-L-3); they are binding for this package. Paths are relative to the repository root; Java paths are under `app/src/main/java/vigil/`.

### 6.1 General rules

- Every class of this package is in `vigil.api` (the module's root package) and is package-private; `vigil.api.api` stays empty (no module depends on `vigil-api`). The `@ApplicationModule(allowedDependencies = …)` of `vigil.api` stays unchanged; this package uses `shared`, `tenancy :: api` and `identity :: api`.
- Every class of this package that takes part in serving requests (filters, the security configuration, controllers, the interceptor, the hub) is `@Profile("!migrate")`, like `ReadyGate`, because the `migrate` profile has no web server.
- No class of this package opens a database transaction or holds one while it writes to the response: each module request is one call of a P-08 service, which has its own transaction.
- Answer bodies of the operations are Java records in `vigil.api` annotated `@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy.class)` (Jackson 3: `tools.jackson.databind.annotation.JsonNaming`, `tools.jackson.databind.PropertyNamingStrategies`). The application-wide JSON settings stay unchanged (the event publication registry serializes with them). AR-I-12 reads its request as Section 6.7 says; notices and error bodies are written as Sections 6.3 and 6.8 say.
- Logging: nothing at `INFO` or above per request; never a cookie value, token, CSRF value, password or request body (AR-S-11). An `internal_error` is logged at `ERROR` with its exception (Section 6.3). The text of every log message is the builder's choice and contains no value taken from the request.

### 6.3 Error format (AR-I-03 with BP-A-20)

- `vigil.shared.VigilError.Code` adds `INTERNAL_ERROR(500, "internal_error")` between `INVALID` and `DEPENDENCY_FAILED`. `ErrorCodeTest` (AR-R-06) lists it in that place. Nothing else in `VigilError` changes.
- `ApiErrors` maps a `Throwable` to an `Optional<ApiError>`, where `ApiError` is `(int status, String code, String message, Map<String, Object> details)` (complete list, first match wins):

| Thrown | Status and code |
| --- | --- |
| `org.springframework.dao.DataAccessResourceFailureException` (this includes `CannotGetJdbcConnectionException`) or `org.springframework.transaction.CannotCreateTransactionException`, also as the cause of another exception at any depth | 503 `dependency_failed` |
| The response is already committed, and the exception or a cause at any depth is a `java.io.IOException` that is not an `HttpMessageNotReadableException` (the client went away while the answer was written) | empty: nothing is written; logged at `DEBUG` |
| `VigilError` | its code's status and wire text; its message, or the default text of its code when it has none (for `STARTING`, which has none, the `message` key is left out); its details |
| `org.springframework.web.servlet.resource.NoResourceFoundException`, `NoHandlerFoundException`, `HttpRequestMethodNotSupportedException` | 404 `not_found` (BP-A-20) |
| `HttpMessageNotReadableException`, or `org.springframework.beans.TypeMismatchException` (this includes `MethodArgumentTypeMismatchException`) | 400 `bad_request` |
| Any other exception that implements `org.springframework.web.ErrorResponse` with status 413 | 413 `too_large` |
| Any other exception that implements `ErrorResponse` with a 4xx status (Example: `HttpMediaTypeNotSupportedException`, `HttpMediaTypeNotAcceptableException`, `MissingServletRequestParameterException`) | 400 `bad_request` |
| Anything else | 500 `internal_error`, logged at `ERROR` with the exception |

- Default texts (complete list, BP-A-20): `bad_request` "The request is not valid."; `session_ended` "Your session ended. Sign in again."; `not_signed_in` "You are not signed in."; `bad_token` "The token is not valid."; `forbidden` "You do not have permission to do this."; `not_found` "Not found."; `unknown_host` "This address is not set up."; `conflict` "This was changed meanwhile. Reload and try again."; `too_large` "The request is too large."; `refused` "The request was refused."; `invalid` "The request has problems."; `internal_error` "Something went wrong. Try again."; `dependency_failed` "A service is not available. Try again later.". `starting` stays as `ReadyGate` writes it (`{"error":{"code":"starting"}}`, no message); `ReadyGate` does not change.
- Body: `{"error":{"code":…,"message":…,"details":{…}}}` in UTF-8 with `Content-Type: application/json`; `details` is left out when empty. The body is written by one shared writer directly to the response (no content negotiation, so the request's `Accept` header does not matter), both by a `@RestControllerAdvice` (exceptions of handlers and interceptors) and by the filters of Sections 6.4 and 6.5; each filter catches every exception of its own module calls and answers with its mapping.
- The advice applies to every handler, so an unknown path outside `/api` that is not answered by `index.html` (Example: `/actuator/anything`, a missing file under `/assets/`) also answers 404 `not_found` in this format; this is intended.
- `HEAD` and `OPTIONS` requests are answered as Spring MVC answers them by default (a `HEAD` of `/api/v1/live` runs the stream without a body; accepted); `TRACE` is answered 405 by Tomcat before any filter (BP-A-20). None of them is an operation of the OpenAPI file. On paths that need a session, the security chain of Section 6.5 answers first.
- A request that Spring Security's `StrictHttpFirewall` rejects (Example: a path with `;` or `//`, or a method such as `PROPFIND`; BP-A-20) answers 400 `bad_request` in this format, after `ReadyGate` and `HostTenantFilter` (so on an `/api/` path of a host with no alias it answers 404 `unknown_host`; BP-A-20): `SecurityConfiguration` defines a `RequestRejectedHandler` bean that writes it with the shared writer, except on an `ERROR` dispatch (`request.getDispatcherType() == DispatcherType.ERROR`), where it writes nothing: Tomcat's refusal of `TRACE` (405) is forwarded to the error page through the security filter chain, whose firewall would otherwise turn it into 400; so `TRACE` keeps its 405 with an empty body.

### 6.4 Tenant of a request (AR-I-02, BP-A-03)

- `HostTenantFilter`: a servlet filter bean ordered `Ordered.HIGHEST_PRECEDENCE + 10` (after `ReadyGate`, before Spring Security's filter chain, whose order is −100). Every path decision of this package's filters and of the CSRF matcher uses `request.getServletPath()` (decoded and normalised by Tomcat; the dispatcher servlet is mapped to `/`), so it matches what Spring Security and Spring MVC match. `HostTenantFilter` acts only on paths starting with `/api/` (the path `/api` itself is a web application path and answers `index.html`, AR-W-01), and not on `/api/v1/installation` or paths starting with `/api/v1/installation/`.
- Host name: the `Host` request header (`request.getHeader("Host")`, not `getServerName()`); when it starts with `[`, the text up to and including the first `]` (no `]`: the whole text); otherwise the text before the first `:`; lower-cased with `Locale.ROOT`. A missing or empty header gives the empty host name.
- `TenantService.resolveHost(host name)`; empty (also for the empty host name, without calling the service) → 404 `{"error":{"code":"unknown_host","message":"This address is not set up."}}`, nothing else runs. Otherwise the `TenantId` is stored in a request attribute, and handlers receive it as a `TenantId` method parameter through a `HandlerMethodArgumentResolver`, which throws `VigilError` `UNKNOWN_HOST` when the attribute is missing.
- Paths outside `/api` (the web application, `/actuator`) are not tied to a tenant.

### 6.5 Sessions, CSRF and access (AR-S-02, AR-S-03, AR-T-11, AR-I-07)

**Security filter chain.** One `SecurityFilterChain` bean (in `SecurityConfiguration`) whose security matcher matches exactly the requests whose servlet path starts with `/api/` (so `/api` itself, like every web application path, passes no Spring Security filter), with (complete list): session management `STATELESS`, so no `HttpSession` is ever created and no `JSESSIONID` cookie is ever sent; form login, HTTP basic, logout and the request cache disabled; Spring Security's response headers disabled (no header that no document requires, AR-S-10 withdrawn); CSRF as below, with `sessionAuthenticationStrategy(new NullAuthenticatedSessionStrategy())` on the CSRF configurer (otherwise Spring Security's session management, seeing each request the session filter authenticates as a new login, clears the `vigil_csrf` cookie on every logged-in request); the session filter added before `CsrfFilter`; authorization (complete list, in this order): every method on `/api/v1/public/**`, `POST /api/v1/session`, every method on `/api/v1/installation/**` and `/api/v1/webhooks/**` are permitted; every other request needs an authenticated session. No `UserDetailsService`, `AuthenticationManager` or password encoder bean is defined by this package.

**Session filter** (`SessionAuthenticationFilter`, created in `SecurityConfiguration`, not a bean, so it is not registered twice). It does nothing on `/api/v1/installation/**` and `/api/v1/webhooks/**`, nor when the request has no tenant attribute. Otherwise it reads the first cookie named `vigil_session`:

- no such cookie: the request stays unauthenticated;
- a cookie: `IdentityService.authenticate(tenant of Section 6.4, value)`; `ACTIVE` → the security context holds an `ApiAuthentication` (authenticated, no authorities) whose principal is `ApiCaller(TenantId tenantId, UUID sessionId, UserView user)`; `ENDED` or `UNKNOWN` (this includes a session of another tenant, SL-B-01, AR-S-02) → the request stays unauthenticated.

**401 and 403.** The authentication entry point answers 401 `session_ended` when the request carries a `vigil_session` cookie, otherwise 401 `not_signed_in`, each with its default text. The access-denied handler (a missing or wrong CSRF header) answers 403 `forbidden` with "You do not have permission to do this.".

**CSRF (AR-S-03).** One `CookieCsrfTokenRepository` bean, defined in `SecurityConfiguration` and used by the filter chain and by the login and logout handlers, with cookie name `vigil_csrf`, header name `X-Vigil-CSRF`, cookie path `/`, and a cookie customizer setting `HttpOnly` false, `SameSite=Strict` and `Secure` = `vigil.security.secure-cookies`; request handler `CsrfTokenRequestAttributeHandler` (plain token, compared as is) in a subclass whose `resolveCsrfTokenValue` reads only the header `X-Vigil-CSRF`, because the base class also accepts the request parameter `_csrf` and AR-S-03 requires the header. The CSRF protection matcher matches exactly the requests whose method is `POST`, `PUT` or `DELETE`, that the session filter authenticated (an active session), and that are not `POST /api/v1/session`, `/api/v1/installation/**` or `/api/v1/webhooks/**`. So a request without an active session is never refused for CSRF; it gets the 401 of the entry point (or passes, on a permitted path).

**Session cookie (AR-S-02, BP-A-02).** `ApiCookies` writes `Set-Cookie` with `ResponseCookie`: `vigil_session={token}` with `Path=/`, `HttpOnly`, `SameSite=Lax`, `Secure` when `vigil.security.secure-cookies` is `true`, and no `Max-Age` or `Expires`. Clearing writes `vigil_session=` with the same attributes and `Max-Age=0` (Spring also writes an `Expires` in the past).

**Access declaration (AR-I-07, PM-M23-02, PM-R-09).** The "logged in" operations need no permission (AR-I-07, AR §10.2; DM-E06-R1's "requires one of these" applies to operations whose Permission column names one). Three annotations in `vigil.api` for handler methods: `@Public` (permission "none"), `@LoggedIn` ("logged in"), and `@RequiresPermission(Permission[] value)` (any one of the listed permissions; AR-I-32 and AR-I-34 list two). Every handler method of every controller in `vigil.api` carries exactly one of them (Section 7, `EntryPointTest`). `AccessInterceptor`, a `HandlerInterceptor` registered for `/api/**`, runs before the handler. It applies its rules only to handler methods of controller classes in package `vigil.api`; every other handler (the static resource handler that answers an unmapped path with `not_found`, Spring MVC's own `OPTIONS` handler) passes unchanged. For a handler method of `vigil.api`: `@Public` → continue; `@LoggedIn` → continue when the request has an `ApiCaller`, otherwise `VigilError` `SESSION_ENDED` when the request carries a `vigil_session` cookie, else `NOT_SIGNED_IN` (the same 401 as the entry point; the security chain answers these cases first); `@RequiresPermission` → the same 401 when there is no `ApiCaller`, otherwise `IdentityService.hasPermission(tenant, user id, p)` for each listed permission in order until one is true, and `VigilError` `FORBIDDEN` (403, default text) when none is; a handler method without an annotation → `VigilError` `FORBIDDEN`. The permission is asked of `vigil-identity` on every request (a grant made inactive takes effect at the next request). Handlers receive the caller as an `ApiCaller` method parameter (argument resolver; without a caller it throws the same 401 `VigilError`).

### 6.6 Times (AR-I-01)

`ApiTimes.format(Instant)` writes `uuuu-MM-dd'T'HH:mm:ss.SSS'Z'` in UTC, truncating to milliseconds (Example: `2026-10-16T09:05:00.120Z`). Every timestamp that `vigil-api` writes uses it; in this package that is the `at` of a notice (Section 6.8). Later packages use it for their answers.

### 6.7 Operations (AR-I-10 to AR-I-16)

JSON objects of this section (field order as written):

- `TenantSettings`: `{"product_display_name": string, "customer_name": string, "has_logo": boolean, "environment_label": string or null}` from `TenantSettingsView`.
- `User`: `{"username": string, "display_name": string, "permissions": [keys], "team_keys": [keys]}` from `UserView`: `permissions` are the `key()`s of the user's permissions in the order of `Permission` (DM-E06-R1); `team_keys` in `Key` order (Unicode code points). The user id is not part of the answer.
- `LoginRequest`: `{"username": string, "password": string}` (the OpenAPI schema of the request; the handler reads it as AR-I-12 below says).

| ID | Operation | Access | Behaviour (complete) |
| --- | --- | --- | --- |
| AR-I-10 | `GET /api/v1/public/branding` | `@Public` | 200 `TenantSettings` of `TenantService.settings(tenant)`. |
| AR-I-11 | `GET /api/v1/public/logo` | `@Public` | `TenantService.logo(tenant)`: 200 with the bytes, `Content-Type` its media type (`image/png` or `image/svg+xml`) and `Cache-Control: no-cache` (the address is the same for every tenant); none → `VigilError` `NOT_FOUND` (404, default text). |

### 6.8 Live update stream (AR-I-04, AR-T-10, AR-TM-04, AR-R-33)

**Topics (the registry).** `LiveTopic` — record `(Kind kind, UUID id)` with nested `enum Kind` of exactly the topics of AR-I-04 in its order, each with `key()` and whether it takes an id (complete list): `INCIDENTS` `incidents`; `INCIDENT` `incident` (id); `RUN` `run` (id); `ALERTS` `alerts`; `SOURCES` `sources`; `APPROVAL` `approval` (id); `WORKFLOW` `workflow`; `TENANT` `tenant`; `TEST_REPLAY` `test-replay` (id). The canonical constructor throws `IllegalArgumentException` when `id` is set for a kind without id or missing for a kind with id. `text()` is the key, or `{key}:{id}` with the id in lower-case canonical form. `static LiveTopic parse(String)` accepts exactly the texts `text()` can produce (an id written as 8-4-4-4-12 lower-case hexadecimal digits) and throws `IllegalArgumentException` otherwise. The `topics` parameter is split at every `,`, keeping empty items (`split(",", -1)`); it is invalid when it is missing or empty, or when any item (an empty item too) does not parse; duplicate topics count once.

**Hub.** `LiveHub`, a bean implementing `SmartLifecycle` with the default phase (`SmartLifecycle.DEFAULT_PHASE`, so it stops before the web server's graceful shutdown):

- `void publish(TenantId tenantId, LiveTopic topic, UUID id, Instant at)` — callable from any thread, never blocks; every argument is required (`null` → `IllegalArgumentException`): it offers the notice to the queue of every open stream of that tenant whose topics contain `topic`. Each stream has a bounded queue of 1,000 notices; when a queue is full, that stream ends (it writes nothing more; the browser reconnects after 1 s and re-reads, AR-I-04).
- `int openStreams()` — the number of open streams (package-private, for tests).
- `stop()` ends every open stream within 1 s; a stream opened after `stop()` ends right after its `retry` line.

**Stream.** The handler of AR-I-16 runs on the request's thread, which is a virtual thread (`spring.threads.virtual.enabled=true`, P-02; AR-R-33), registers a stream with the hub and writes to the response itself (no `SseEmitter`, no servlet async). It holds no database connection while open. The stream is registered with the hub before step 1, so every notice published after the client has read the `retry` line is delivered. In order:

1. Status 200, `Content-Type: text/event-stream;charset=UTF-8`, `Cache-Control: no-cache`; writes `retry: 1000\n\n` and flushes.
2. Then, until it ends: each notice as `event: change\ndata: {"topic":"{topic text}","id":"{id}","at":"{ApiTimes.format(at)}"}\n\n` (exactly these bytes, no spaces, no `id:` line), flushed at once, in publish order; `: ping\n\n`, flushed, at `pingInterval` after the open and every `pingInterval` after that.
3. The stream ends at `maxOpen` after the open (no ping is written at that instant), when the hub ends it, or when a write fails (the client went away); it is then removed from the hub and the handler returns, which ends the response.

**Timings.** `LiveTimings` — record `(Duration pingInterval, Duration maxOpen)`, provided by a bean method `liveTimings()` with 15 s and 300 s (AR-TM-04). Tests that need shorter timings pass a source class with `@Bean @Primary LiveTimings testLiveTimings()` to `VigilTestApp` (a different bean name, as `MutableClock`, P-08 Section 6.6). Stream timing uses `System.nanoTime()`, not the `Clock` bean.

**Delivery path for producers.** A producer calls `LiveHub.publish` after the commit of the change it announces (P-25 adds the producers as listeners in `vigil.api`; AR-TM-04's 1 s counts from that commit). The hub adds no delay: a published notice is written by each stream's thread as soon as it takes it from its queue.
