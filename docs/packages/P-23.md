## 2. Goal

Build `vigil-recovery` (PM-M15): the recovery check definitions of seed part 13 (DM-E-61) with their key checks against the service map and the alert types; the Recovery check step (DM-S-07) that decides, from alert states and source health held by `vigil-intake` and never from action results, whether the service recovered: every condition and the source health guard must hold for the observation window, within the step's maximum wait (DM-R-34 to DM-R-38); the recovery verification (DM-E-62, DM-SM-13) with its last evaluation and the condition texts of DC-TX-03; the evidence entry whose `content` the Jira resolve comment of P-21 reads (CTX-D-069 (6)); and the resolve request to `vigil-incidents` (PM-M09-06). Build `vigil-reporting`'s module core (PM-M21): the baseline values of seed part 17 (DM-E-80) and the four dashboard metrics of DM-R-53 over the tenant's live incidents and its seeded past incidents (DM-R-52), so that the seeded starting state gives the values of DD-K-11.

### 6.1 General rules

- Every public type of `vigil-recovery` is in `vigil.recovery.api`, of `vigil-reporting` in `vigil.reporting.api` (AR-R-04); every other new class is package-private. The `@ApplicationModule` declarations stay as they are (`vigil-recovery`: `shared`, `intake :: api`, `incidents :: api`, `correlation :: api`, `servicemap :: api`, `audit :: api`; `vigil-reporting`: `shared`, `incidents :: api`, `intake :: api`, `knowledge :: api`, `tenancy :: api`, `audit :: api`).
- Persistence with `JdbcClient`; transactions with `TransactionTemplate`; ids from `Ids.newId()`; time from the `Clock` bean through `Timestamps.now(clock)`; every statement filtered by `tenant_id`; no `DELETE`. Requests to other modules inside a transaction join it (AR-R-10). JSON with a `static final JsonMapper` (Jackson 3).
- Neither module makes an external call: the Recovery check step reads only records of Vigil, so its `start` and `evaluate` run their work in transactions and do not call `TransactionGuard.assertNoTransaction()`; AR-Q-04 does not change.
- Lengths are Unicode code points; "cut to n" keeps the first n code points. Lists of names are joined by `, ` in ascending order of Unicode code points of the text shown, and an empty list is `none` (DC-TX-00 "Lists"), unless a rule says otherwise. Counts before a noun follow DC-TX-00 "Counts". Durations in stored texts use DC-U-07 rule (2) (`{s} s` under 120 s, else `{m} min` or `{m} min {s} s`); `vigil-recovery` holds its own copy of this helper (as P-22's `MessageTexts`, CTX-D-071). Instants in stored JSON are written with `Instant.toString()` (ISO 8601 in UTC, read back by `Instant.parse`, as P-21's `TicketTexts` reads them).
- `null` arguments of public requests: `IllegalArgumentException("a required argument is missing")`.
- Actors: requests of `vigil-recovery` use `Actor.module("vigil-recovery")`.
- Logging (complete list at `INFO` or above from `vigil.recovery` and `vigil.reporting`): none. A refused call throws; the engine logs it (AR-TM-05).
- Every list returned is unmodifiable. Texts named in this spec are exact.

### 6.5 The JSON forms (DM-E-62 as DC-A-12 amends it; CTX-D-069 (6), CTX-D-073 (8))

- **A condition** (in `conditions`, in the snapshot and in the last evaluation): `{"kind": "incident_alerts_resolved"}`, or `{"kind": "component_no_firing_alert", "component_key": k, "alert_types": [sorted keys]}`, keys in this order.
- **`definition_snapshot`**: `{"recovery_check_key": k, "name": n, "conditions": [conditions in the definition's order], "observation_window_seconds": integer}`.
- **`last_evaluation`**: `{"at": instant, "conditions": [{"condition": a condition, "held": boolean, "detail": text, "firing_count": integer}, … in the definition's order], "sources_healthy": boolean, "unhealthy_source_ids": [ids as strings, in the order of `IntakeService.sources`]}`; `sources_healthy` and `unhealthy_source_ids` describe the active sources' health now (what DC-S03-11 shows); a source that is healthy now but was not healthy during the window restarts the window (Section 6.7 step 5) and is not listed.
- **The evidence entry's `content`**: `{"definition_snapshot": the snapshot, "window_started_at": instant or null, "decided_at": instant, "last_evaluation": the last evaluation}`. Its key names and types are those P-21 reads (CTX-D-069 (6)): `definition_snapshot.observation_window_seconds` an integer, `window_started_at` and `decided_at` instants, `last_evaluation.conditions[].detail` the condition's text.

### 6.6 The texts (`RecoveryTexts`; DC-TX-03, DC-TX-10)

`{component name}` is the name of the component in the current service map generation (`ServiceMapService.component`), the key when it is not there; `{alert type display names joined by ' or '}` the display names (`IntakeService.alertTypes`; the key when not found) of the condition's `alert_types`, in ascending code point order of the names (DC-TX-00 "Lists"; only the joiner differs); `{f}` the condition's `firing_count`; `{check name}` the snapshot's `name`; `{observation window}` and `{max_wait}` durations by DC-U-07 rule (2) (`max_wait` = `max_wait_until` − `started_at`).

- **Condition texts** (the `detail` of each condition in the last evaluation, exactly as DC-TX-03 gives them): `incident_alerts_resolved` holding `Every alert of the incident is resolved at its source`, not holding `{f} {alert or alerts} of the incident {is or are} still firing`; `component_no_firing_alert` with empty `alert_types` holding `No alert of {component name} is firing`, not holding `{f} {alert or alerts} of {component name} {is or are} firing`; with `alert_types` holding `No {alert type display names joined by ' or '} alert of {component name} is firing`, not holding `{f} {alert type display names joined by ' or '} {alert or alerts} of {component name} {is or are} firing`. The requirement texts of `RecoveryCheckView` are the holding forms.
- **The source health guard** (DM-R-36): holding `Every monitoring source is healthy`; not holding `{source names} not healthy` (the `name`s of the unhealthy active sources, as a list).
- **Evidence summary** (DC-TX-03 row `recovery_verification`): recovered `Recovered: '{check name}' held for {observation window} with every monitoring source healthy.`; not recovered `Not recovered within {max_wait}: {texts not holding, joined by '; '}.`, where the texts not holding are the `detail` of each condition that does not hold, in the definition's order, followed by the guard's text when the guard does not hold now (DC-TX-03 lists the guard among the recovery condition texts; CTX-D-073 (4)); when every condition and the guard hold now (the window started but was not long enough), `Not recovered within {max_wait}: the conditions held for less than {observation window}.` (CTX-D-073 (4) adds this text to DC-TX-03). `vigil-incidents` cuts a summary longer than 200 (DM-E-38).
- **Evidence `source_system`**: `Monitoring: {active source names}` (the `name`s of the tenant's active sources, as a list, cut to 200).
- **Audit summary** (DC-TX-10 `recovery_verified`): `Recovered: '{check name}'.` or `Not recovered: '{check name}'.`

### 6.7 The Recovery check step (`RecoveryStep`, `Evaluation`; DM-S-07, PM-M15-02, PM-M15-03, DM-R-34 to DM-R-38, DM-R-64, DM-SM-13)

The engine calls `start` and `evaluate` on the run's virtual thread with no transaction open; a throw is a failed call, retried after 5 s, 15 s and 45 s (AR-TM-05). `start` and `evaluate` do the same (one call). Each call is, in order:

1. **Parameters.** A step type other than `RECOVERY_CHECK`, or parameters that are not an object with `max_wait` a JSON integer (`isIntegralNumber()` and `canConvertToLong()`, as `WorkflowPartCheck` checks a Duration) from 60 to 86,400 (the stored content holds `max_wait` in seconds without `_s`, P-41): `IllegalArgumentException("recovery check step parameters: max_wait")`.
2. **The verification** (one transaction for steps 2 to 5; the row read `FOR UPDATE`): the verification of the call's step execution (DM-R-64).
   - It exists and is `recovered` or `not_recovered`: the transaction ends with no change and the call answers by it (step 6).
   - It exists and is `cancelled`: `IllegalStateException("recovery verification {id} is cancelled")`.
   - It does not exist (DM-SM13-T1): **the definition** (DM-R-34, CTX-D-073 (3)) is the active definition with the call's `recoveryCheckKey` when the call has one, else the tenant's active default definition; none: `IllegalStateException("recovery check {key} not found")` or `IllegalStateException("no default recovery check")`. `max_wait` not greater than the definition's observation window (DM-R-38): `IllegalArgumentException("recovery check step parameters: max_wait must be greater than the observation window of {key}")`. A row `observing` with the run, step execution, incident, the key, the snapshot (Section 6.5), `started_at` now, `max_wait_until` now + `max_wait`, no window, and the evaluation of step 3 as its `last_evaluation`.
3. **Reading the conditions** (DM-R-35; at `now` = `Timestamps.now(clock)`, read once at the start of the call and used for every step of it; the conditions, the observation window and the check name come from the verification's `definition_snapshot`, not from the current definition):
   - `incident_alerts_resolved`: the alerts of the incident's active memberships (`IncidentService.members`), read with `IntakeService.alerts`; `firing_count` the number with status `firing`; holds when it is 0.
   - `component_no_firing_alert`: the alerts whose grouping decision matched the component (`CorrelationService.alertsOfComponent`), read with `IntakeService.alerts`, restricted to the condition's `alert_types` when not empty; `firing_count` the number with status `firing`; holds when it is 0.
   - `held` and `detail` per condition (Section 6.6).
4. **The guard now** (DM-R-36): the tenant's active sources (`IntakeService.sources`, `active`); a source is unhealthy now when its `health` is not `healthy`. `sources_healthy` is true when no active source is unhealthy now (also when the tenant has none); `unhealthy_source_ids` lists those that are.
5. **The window and the decision** (DM-R-37 with DM-E23-R1; CTX-D-073 (2)), with `all` = every condition held and `sources_healthy`, in this order:
   - `all` is false → `window_started_at` is cleared.
   - `all` is true and there is no window → `window_started_at` = now.
   - `all` is true, there is a window, and an active source was not `healthy` during the whole of it (`IntakeService.healthyThroughout(tenant, source, window_started_at, now)` is false, for a source that is healthy again now, Example: a source that turned stale between two evaluations and was tested again) → `window_started_at` = now (the window restarts; the step waits a full window again).
   - **Recovered** (DM-SM13-T2) when `window_started_at` is set and now ≥ `window_started_at` + observation window.
   - Otherwise **not recovered** (DM-SM13-T3) when now ≥ `max_wait_until`.
   - The row is updated: `last_evaluation` (Section 6.5, `at` now), `window_started_at`, and on a decision `state` and `decided_at` now. On a decision, in the same transaction and in this order: the audit event (Section 6.9); `IncidentService.addEvidence(tenant, Actor.module("vigil-recovery"), incident, RECOVERY_VERIFICATION, verification id, source_system, decided_at, summary, content, INCIDENT_RECORD)` (Sections 6.5, 6.6; PM-M15-03); and when recovered and the incident is `open` (read in this transaction), `IncidentService.resolve(tenant, Actor.module("vigil-recovery"), incident, verification id)` (PM-M09-06, DM-SM05-T4; `resolve` finds the evidence entry just added). An incident that is `resolved` is not resolved again (CTX-D-073 (5)). An incident that is `closed` or `merged` cannot get evidence (`addEvidence` refuses), so the call fails and its transaction is rolled back; this does not happen in a run, because `vigil-engine` cancels the run in the transaction that closes or merges its incident (AR-R-20) and the step is not called again.
6. **The answer**: `recovered` → `Completed(recovered, ResultRef("vigil-recovery", "RecoveryVerification", id))`; `not_recovered` → `Completed(not_recovered, the same ResultRef)`; still `observing` → `Waiting({ALERT_STATE_CHANGED, SOURCE_HEALTH_CHANGED}, due, null)` with `due` the earlier of `window_started_at` + observation window (when set) and `max_wait_until` (both later than now at that point, DM-R-37; the engine keeps no step state for this step, CTX-D-073 (8)).

**`cancel`** (DM-SM13-T4; joins the caller's transaction, AR-R-21): the verification of the step execution, when it is `observing`, becomes `cancelled` (no `decided_at`, no evidence, no audit event); any other state or none: nothing. Called twice it gives the same result.

### 6.10 The metrics (`Reporting`, `Metrics`; DM-R-52, DM-R-53, PM-M21-01, PM-M21-02, DM-E-79)

`dashboard(tenant)` reads, in one read-only transaction (CTX-D-073 (7)):

- **Counted live incidents**: `IncidentService.incidents(tenant, {OPEN, RESOLVED, CLOSED})` with a `number` (not `forming`, not `merged`). - Each metric with the tenant's baseline of the same key (`baselineValue`, `baselineLabel`), or `null` when none (PM-M21-02). `liveIncidents`, `pastIncidents` the two counts; `recordLabels` the distinct labels of the counted past incidents, sorted.
