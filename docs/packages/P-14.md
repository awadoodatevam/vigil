## 2. Goal

Build the module core of `vigil-incidents` (PM-M09): the incident (DM-E-32) with its lifecycle (DM-SM-05) and transition records (DM-E-33), alert memberships with their grouping reasons and merges (DM-E-34, DM-R-12), the title (DM-R-20, with the alert copy of BP-A-27), the acknowledgement with its atomic check (DM-E-35, DM-E35-R1, AR-R-12), escalation records (DM-E-36), notified teams (DM-E-37), the evidence register and its summary (DM-E-38, PM-M09-11), the timeline with the texts of DC-TX-04 (DM-E-39), the AI status (PM-M09-07), the incident settings (DM-E-40) as seed part 9, the closure of resolved incidents as scheduled work for active tenants (DM-R-23), the audit events `vigil-incidents` owns (DM-E08-R3) and the events AR-E-05 to AR-E-08. Each change is a request of the module named by DM-E-32 and PM-M09 (DM-E32-R1); the requesting modules (P-15, P-16, P-18 to P-24) and the API operations (P-25) come later. The package also builds, in `vigil-intake`, the U+0000 rule of DM-C-11 (BP-A-26, CTX-D-048).

### 6.1 General rules

- Every public type of `vigil-incidents` is in `vigil.incidents.api` (AR-R-04); every other class is package-private in `vigil.incidents`. The `@ApplicationModule(allowedDependencies = {"shared", "tenancy :: api", "identity :: api", "audit :: api"})` of `vigil.incidents` stays unchanged, and so do the declarations of `vigil.setup` and `vigil.api`. No public type of `vigil.incidents.api` names a type of another module's `api` package (types of `vigil.shared` such as `TenantId`, `Key` and `Actor` are used).
- Records are written with `JdbcClient`; every writing request is `@Transactional` (`REQUIRED`, AR-R-10) and, unless this spec says otherwise, first locks the incident row (`SELECT … FOR UPDATE`); reads have no transaction of their own.
- Time from the `Clock` bean through `Timestamps.now(clock)`, read once per request; ids from `Ids.newId()`; lengths in Unicode code points; "cut to n" as P-13 (the first n code points).
- `null` arguments: `IllegalArgumentException`, except where Section 6.4 or 6.6 allows them. A request for an incident id that the tenant does not have: `VigilError` `NOT_FOUND` (default message).
- **Requesting module (DM-E32-R1).** Every request except `acknowledge` takes the caller's `Actor`, which MUST be `Actor.module(m)` with `m` the module that Section 6.6 names for that request; any other actor (another module, or a user): `IllegalArgumentException` with the message `{request} is accepted only from {m}`, where `{request}` is the Java method name (Example: `addAlert is accepted only from vigil-correlation`). The actor is the actor of the request's transition records, timeline entries and audit events.
- **State guard.** A request made in a state that Section 6.6 does not allow for it: `IllegalStateException` with the message `{request} is not allowed in state {state key}`; nothing changes.
- **Order of checks** of every request: (1) its arguments (`null` where Sections 6.4 and 6.6 do not allow it, and every value rule of Sections 6.4 and 6.6, such as `ruleName` 1 to 100 characters, `level` ≥ 1, `timer` with the cause, `status` not `NOT_RUN`, `contentJson` a JSON object, `summary` not empty, `reason.decision`) and the requesting module (`IllegalArgumentException`); (2) the incident exists for the tenant (`NOT_FOUND`); (3) the state guard; (4) the request's own rules. `acknowledge`: (1) `null` arguments, (2) `NOT_FOUND`, then the checks of Section 6.7.
- A unique-constraint violation (Example: two concurrent memberships of one alert) is not translated; it cannot occur when `vigil-correlation` makes one decision at a time per tenant (DM-R-62), and an import is made once per tenant by `vigil-setup`.
- Logging: nothing at `INFO` or above per request, except one `INFO` line per state transition (tenant id, incident id, from, to).
- Every list returned is unmodifiable; JSON values returned are copies.
- No class has a `@Profile`, except the scheduled work and the listener of Section 6.9 (`@Profile("!migrate")`, as P-13).

### 6.6 Requests that change an incident

Every request below writes, in its transaction: the changes; the timeline entries (DM-E-39, texts of Section 6.8, `at` now, actor the request's actor, `ref_type`/`ref_id` as stated); the transition record (DM-E-33) of a state change (`transition_id` the DM-SM-05 ID, `reason` the state change's timeline text, for `DM-SM05-T1` the `created` text), with `state_changed_at` = now on the incident; the audit events of Section 6.8 (`AuditService.append`, `incident_id` the incident; `subject_type` `Incident` unless the request says otherwise; `ref_type` of timeline entries, where stated, one of `IncidentAlertMembership`, `IncidentEscalation`, `Acknowledgement`, `EvidenceEntry`, `NotifiedTeam`); and then publishes, in this order, `IncidentCreated` (creation only), `IncidentStateChanged` (each state change), `IncidentAcknowledged` (acknowledgement only) and one `IncidentChanged` per changed incident (DM-E32-R2), except `merge`, whose order is item 3's. A request that changes nothing writes and publishes nothing.

**Derived fields** (recomputed in every request that changes the active memberships, the hypothesis or the affected services): `alert_count` = the number of active memberships; `alert_types`, `alert_sources` = the sets of the active members' `alert_type` and `source_kind`; `first_alert_fired_at` = the earliest `fired_at` of every membership ever (active or ended) of the incident; `last_alert_joined_at` as each request states; `title` by DM-R-20 below. When `title` changes (and the request is not the creation), a `title_changed` entry is written after the request's other entries.

**Title (DM-R-20)**, over the active members: with a hypothesis, `{hypothesis_snapshot.name}: {primary alert type name}`, followed by ` — {n} services affected` when n = the number of `affected_services` is at least 2, ` — 1 service affected` when n = 1, nothing when 0; the primary alert type is the `alert_type` held by the most members whose `component_key` equals the hypothesis component (ties: the alert type key first in code point order), and when no member is on that component, the most frequent `alert_type` of all members (same tie rule); its name is the `alert_type_name` of any member with that type (they are equal; the first in member order is used). Without a hypothesis: `{v}: {name}`, where the earliest member is the one with the earliest `fired_at` (ties: `source_kind`, then `alert_key`, each in code point order), `v` its `first_identity_pair.value`, or its `title` when it has none, and `name` its `alert_type_name`. The title is cut to 200.

Requests (complete list; module, allowed states, effect):

1. `UUID create(TenantId, Actor, UUID groupingDecisionId, AlertCopy alert, GroupingReason reason)` — `vigil-correlation`; `reason.decision` `created_incident` (the other four fields `null`, DM-E-29). In one transaction, under `pg_advisory_xact_lock(hashtext('incidents.sequence'), hashtext(tenant id text))`: a new incident (`sequence` = highest + 1, or 1; `state` `forming`, `state_changed_at` now; `alert_count` 1; `last_alert_joined_at` now; `assignment_frozen` false; `escalation_level` 0; `ai_status` `not_run`; `reopen_count` 0; `informed_team_keys` and `affected_services` empty; the title) and its membership (`joined_at` now); transition `DM-SM05-T1` (`from_state` empty, `to_state` `forming`); timeline `created`; audit `incident_created` (subject `Incident`); events `IncidentCreated`, `IncidentChanged` (creation is not published as `IncidentStateChanged`). The alert MUST NOT have an active membership (DM-E34-R1), else `IllegalStateException` `alert {id} is already a member of an incident`. Returns the incident id.
2. `void addAlert(TenantId, Actor, UUID incidentId, UUID groupingDecisionId, AlertCopy alert, GroupingReason reason)` — `vigil-correlation`; states `forming`, `open`; `reason.decision` `joined`. A membership (`joined_at` now; in state `open` also `final_reason` = the reason's relation fields, DM-E-34); `last_alert_joined_at` now; derived fields; timeline `alert_joined` (ref the membership). Same DM-E34-R1 check.
3. `void merge(TenantId, Actor, UUID survivorId, List<UUID> absorbedIds)` — `vigil-correlation`; the survivor and every absorbed incident `forming`, at least one absorbed, none equal to the survivor or repeated (DM-R-12). Incident rows locked in ascending `sequence` order. For each absorbed incident, in the list's order: each active membership ends (`ended_at` now) and the survivor gets a new membership for the alert (`reason` `{"decision": "moved_by_merge", "from_incident_id": …, "original_reason": the old reason}`, `joined_at` now, the same `grouping_decision_id` and alert copy); the absorbed incident: `merged_into_incident_id`, `state` `merged`, transition `DM-SM05-T3`, timeline `state_changed`, audit `incident_state_changed`, `IncidentStateChanged`, `IncidentChanged`; its derived fields keep their last values. The survivor: `last_alert_joined_at` = the latest of its own and the absorbed incidents' values; derived fields; one timeline `merged_in` per absorbed incident (n = the memberships moved from it); `IncidentChanged`. Events in this order: for each absorbed incident in the list's order, its `IncidentStateChanged` and `IncidentChanged`; then the survivor's `IncidentChanged`.
4. `void setHypothesisAndImpact(TenantId, Actor, UUID incidentId, HypothesisCopy hypothesis, UUID hypothesisComputationId, List<AffectedServiceCopy> affectedServices)` — `vigil-correlation`; states `forming`, `open`; `hypothesis` and `hypothesisComputationId` MAY be `null` together (no hypothesis), `affectedServices` MAY be empty. A request that removes an existing hypothesis: `IllegalStateException` `the hypothesis cannot be removed` (DM-R-18 never loses a known component of the members). Stores `hypothesis_component_key`, `hypothesis_snapshot`, `hypothesis_computation_id` and `affected_services` (ordered by `service_key`); timeline `hypothesis_changed` when the component key changes; `impact_changed` when `affected_services` differ as JSON (keys, names, criticality or via keys); then the title. When only the computation id or the snapshot changed (BP-A-27): no timeline entry, `IncidentChanged` only.
5. `void open(TenantId, Actor, UUID incidentId, Map<UUID, FinalReason> finalReasons)` — `vigil-correlation`; state `forming`; the map's keys MUST be exactly the alert ids of the active members, else `IllegalArgumentException` (this check is step (4) of the order of checks, after the state guard). Under `pg_advisory_xact_lock(hashtext('incidents.number'), hashtext(tenant id text))`: `number` = highest number of the tenant + 1, or 1; `state` `open`, `stable_at` now, `assignment_frozen` true; each active membership's `final_reason`; transition `DM-SM05-T2`; timeline `state_changed`; audit `incident_state_changed`; events.
6. `void reopen(TenantId, Actor, UUID incidentId, UUID groupingDecisionId, AlertCopy alert, GroupingReason reason)` — `vigil-correlation`; state `resolved`; `reason.decision` `reopened`. The membership with `final_reason` = the reason's relation fields (DM-R-21); `reopen_count` + 1; `resolved_at`, `resolved_by_verification_id`, `acknowledged_at`, `acknowledged_by` cleared; `escalation_level` 0; `state` `open`; `last_alert_joined_at` now; derived fields; transition `DM-SM05-T5`; one timeline entry `state_changed` (its text names the alert; no `alert_joined`); audit `incident_state_changed`; events. The number and the frozen assignment are kept. Same DM-E34-R1 check.
7. `void setAssignment(TenantId, Actor, UUID incidentId, Severity severity, Key ownerTeamKey, Set<Key> informedTeamKeys, UUID routingEvaluationId, String ruleName)` — `vigil-routing` (PM-M09-03); state `forming` and `assignment_frozen` false (DM-R-16, DM-R-17); `ruleName` 1 to 100 characters (DC-A-10). Stores the assignment and `assignment_evaluation_id`; timeline `assignment_changed`; audit `assignment_changed` (subject `Incident`). Every applied evaluation is a change, also when its result equals the stored one (a new `assignment_evaluation_id`, with its entry and audit event); a request whose `routingEvaluationId` equals the stored one changes nothing.
8. `UUID recordEscalation(TenantId, Actor, UUID incidentId, long level, Set<Key> teamKeys, EscalationCause cause, Duration timer, long policyRevision)` — `vigil-routing`; state `open`; `level` ≥ 1; `timer` required for `ACKNOWLEDGEMENT_TIMEOUT` and `null` for `ESCALATE_NOW` (DC-A-10). A DM-E-36 record; `escalation_level` = `level`; timeline `escalated` (ref `IncidentEscalation`); audit `incident_escalated` (subject `IncidentEscalation`). Returns its id.
9. `void recordNotifiedTeam(TenantId, Actor, UUID incidentId, Key teamKey, NotifiedPurpose purpose)` — `vigil-notifications`; states `open`, `resolved`. When the incident has a record for the team: nothing (DM-E37-R1). Otherwise a DM-E-37 record (`first_notified_at` now); timeline `notified_team_added` (ref `NotifiedTeam`).
10. `UUID addEvidence(TenantId, Actor, UUID incidentId, EvidenceKind kind, UUID producerRecordId, String sourceSystem, Instant collectedAt, String summary, String contentJson, DataCategory dataCategory)` — the producer of the kind (complete list): `diagnostic_result` `vigil-diagnostics`; `ai_investigation` and `similarity_match` `vigil-investigation`; `approval` and `action_execution` `vigil-actions`; `recovery_verification` `vigil-recovery`; states `open`, `resolved`, and also `closed` for `ai_investigation` (a re-run is accepted on a closed incident, DM-E68-R2). `producer_module` is the actor's module. When the tenant has an entry for (`producer_module`, `producerRecordId`): returns its id, nothing changes (DM-R-65). Otherwise a DM-E-38 record: `summary` 1 or more characters, longer than 200 → its first 199 code points followed by `…` (DC-TX-03); `source_system` 1 to 200 (else `IllegalArgumentException`); `contentJson` a JSON object; `dataCategory` the category of its kind by DM-R-44 (`diagnostic_result` → `diagnostic_output`; `similarity_match` → `incident_history`; the other four → `incident_record`), else `IllegalArgumentException`; timeline `evidence_added` (ref `EvidenceEntry`). Returns the id.
11. `void setAiStatus(TenantId, Actor, UUID incidentId, AiStatus status, AiUnavailableReason reason, UUID requestGroupId)` — `vigil-investigation` (PM-M09-07); states `open`, `resolved`, `closed` (DM-E68-R2); `reason` required for `UNAVAILABLE`, `null` otherwise; `status` not `NOT_RUN`. When `status` or `reason` differs from the stored ones: sets them, `ai_last_request_group_id`, `ai_status_changed_at` now, timeline `ai_status_changed`; when only `requestGroupId` differs: sets `ai_last_request_group_id` and publishes only `IncidentChanged` (DC-A-13); when nothing differs: nothing.
12. `void resolve(TenantId, Actor, UUID incidentId, UUID verificationId)` — `vigil-recovery` (PM-M09-06); state `open`; the incident MUST have an evidence entry of kind `recovery_verification` produced by `vigil-recovery` with `producer_record_id` = `verificationId` (the verification belongs to this incident), else `IllegalStateException` `verification {id} is not evidence of this incident`; that it passed is the caller's check (`vigil-incidents` may not request `vigil-recovery`, AR-M-10). `state` `resolved`, `resolved_at` now, `resolved_by_verification_id`; transition `DM-SM05-T4`; timeline `state_changed`; audit `incident_state_changed`; events.

### 6.7 The acknowledgement (DM-E35-R1, DM-R-63, AR-R-12, PM-M09-04)
