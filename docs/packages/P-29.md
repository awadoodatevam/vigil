## 2. Goal

Build the incident workspace (DC-S03, SL-A4-03) at `/incidents/{incident id}`: the header, the read-only run canvas in a full-width band with follow mode, zoom, Fit and Expand (SL-WE-10, SL-A1-08), the main column with the hypothesis and customer impact, the grouped alerts with their reasons, the evidence, the AI investigation, Response and Recovery, and the side column with the run steps, the timeline and the notified teams. Every text is composed in `vigil-web` from the operations P-25 and P-43 built (AR-I-22 to AR-I-25, AR-I-27 to AR-I-31) with the wording of `40-demo-cut`, and kept current by the live topics and the recovery polling (DC-U-08). The look is `45-visual-design` v1.1 (VD-S-05). Playwright proves the workspace while the storm driver runs: the values of SB-S02 to SB-S08 (exact in the `demo` profile of the owner's Mac run), and the highlight following each step change within 2 s.

### 6.2 API client, route, reads and live topics

1. **Path parameters.** `web/src/api/client.ts`: `RequestOptions` gets `params?: Record<string, string>`; `send` replaces each `{name}` of the path with `encodeURIComponent(params[name])` before the query is added. `apiGet("/api/v1/incidents/{incident_id}/run", { params: { incident_id } })` is typed by the generated `paths` as before. Tested in `api/client.test.ts`.
2. **Route** (AR-W-01): `ROUTE_TABLE` adds `{ path: "/incidents/:incidentId", screen: "workspace" }` before `*`; the screen `workspace` renders `WorkspacePage`. Every other path keeps the not-found state of P-28.
3. **Reads** (`web/src/workspace/queries.ts`; complete list of the workspace's query keys, each `retry: false` as P-28's client sets):

   | Key | Operation | Part |
   | --- | --- | --- |
   | `["incident", id]` | AR-I-22 | Header, hypothesis and impact |
   | `["incident-alerts", id]` | AR-I-23 | Alerts |
   | `["incident", id, "evidence"]` | AR-I-24 | Evidence |
   | `["incident", id, "investigation"]` | AR-I-25 | AI investigation |
   | `["incident", id, "response"]` | AR-I-27 | Response |
   | `["incident", id, "recovery"]` | AR-I-28 | Recovery; polled every 1 s while any of its verifications is `observing` (AR-I-05; `refetchInterval` as a function of the last answer, `refetchIntervalInBackground: true`) |
   | `["incident", id, "run"]` | AR-I-29 | Run band, run steps |
   | `["incident", id, "timeline"]` | AR-I-30 | Timeline |
   | `["incident", id, "notified"]` | AR-I-31 | Notified |

4. **Live topics** (AR-I-04 row DC-S03): `incident:{incident_id}` once AR-I-22 has answered an incident (the answer's `incident_id`, not the address), `run:{run_id}` once AR-I-29 has answered a run (the topic changes when the latest live run changes), and `alerts`; plus `tenant` from `SignedInLayout`. When the topics change, `useLiveTopics` opens a new stream; a stream opened because the topics changed re-reads every query of its topics on its first `open` (P-28's first stream of a page still does not), so no notice of the gap is lost. `web/src/live/useLiveTopics.ts`: `TOPIC_QUERIES` becomes a function `topicQueries(topic)` that returns the query keys a topic re-reads (complete list): `tenant` → `["tenant"]`; `incidents` → `["incidents"]`; `alerts` → `["strip"]` and `["incident-alerts"]`; `sources` → `["strip"]`; `incident:{id}` → `["incident", id]` and `["incident-alerts", id]`; `run:{id}` → `["incident"]`; any other → none. Invalidation matches by key prefix (TanStack Query's default), so `["incident", id]` re-reads every part of that key, and `run:{id}` every open workspace part except the alerts. `queriesOf(topics)` keeps its meaning (the keys of the given topics, without duplicates). The interrupted line's "Last update {time}" (P-28 `InterruptedLine`) becomes the latest `dataUpdatedAt` of every query in the cache that matches one of those keys by prefix (`getQueryCache().findAll({ queryKey })`), so it also works for prefix keys. The re-read of each topic stays at most once per 500 ms (P-28 `LiveConnection`).
5. **Page** (`web/src/workspace/WorkspacePage.tsx`): `SignedInLayout` with `access="view"`, `topics` as item 4, `live`, and `screen` = "{number} {title}" once AR-I-22 has answered with an incident, else `null` (tab title "{number} {title} — {product}" (DC-U-15); `{product}` alone before that and on the error state). The page reads AR-I-22 and AR-I-29 itself (the same queries the header card and the band use) for the title and the run topic.

### 6.3 States of the page and of its parts (DC-U-09, DC-S03-01)

1. **AR-I-22 first.** While it has not answered: `Loading` in a card (VD-S-05). An answer `MergedIncident` (`merged_into_incident_id`) → `navigate("/incidents/{merged_into_incident_id}", { replace: true })` (DC-S03-01). A failure: 401 as P-28 (the layout opens the login screen); any other → `PageError` "Could not load this page. {reason}" with "Try again" (re-reads AR-I-22); a `forming` or unknown incident answers 404 `not_found`, so it shows "Could not load this page. Not found." (DC-S03-01). Nothing else of the workspace is shown in these states.
2. **Parts.** Once AR-I-22 has answered an incident, every other part shows its content from its own read: `Loading` in its place until its first answer; when its latest read failed, `PartError` "Could not load this part. {reason}" with "Try again" (re-reads that part) in place of its content, under its heading (P-28's reading: a failed re-read replaces the earlier content). A part never shows a partial value as final. A failed re-read of AR-I-22 after an answer shows `PageError` in place of the whole workspace.
3. **Parts that are shown only sometimes** (DC-S03-06, DC-S03-10, DC-S03-11; DC-U-09 "where a part has no empty text, the part is not shown"): the run band is shown while AR-I-29 loads for the first time (with `Loading`), when its latest answer has a run, and when its latest read failed; the Response section when the latest answer of AR-I-27 has `similar` not `null` (CTX-D-089 (6)) or when its latest read failed; the Recovery section when the latest answer of AR-I-28 has at least one verification or when its latest read failed. The anchor of a section is shown exactly when the section is.
4. **Live updates interrupted** (DC-U-08, DC-U-09): the line of P-28 under the header (`live`).
