## 2. Goal

Build the `jira_cloud` connector (AR-K-04, AR-K-14 to AR-K-16) and `vigil-ticketing` (PM-M19): the ticket link and the ticket sync record (DM-E-75, DM-E-76), the Ticket step (DM-S-10) that creates the Jira ticket of an incident with the content of DC-OUT-01, reopens it for a reopened incident (DC-OUT-04) and resolves it with the recovery evidence (DC-OUT-03), and the escalation comment that `vigil-routing` will ask for in P-22 (DC-OUT-02). Before a create that follows an earlier create attempt for the same incident (a stop between the Jira call and its record, or an attempt that ended without an answer), Jira is searched for the incident's label, so the issue found is linked instead of a second one being made (DM-E76-R2, CTX-D-069 (4)). The incident link of the ticket (AR-I-100) starts with the installation property `vigil.links.base` (BP-A-09), which `vigil-tenancy` now reads for every module that builds links.

### 6.1 General rules

- Every public type of `vigil-ticketing` is in `vigil.ticketing.api` (AR-R-04); every other new class is package-private. The `@ApplicationModule` declaration of `vigil-ticketing` stays as it is (`shared`, `connectors :: api`, `intake :: api`, `incidents :: api`, `investigation :: api`, `tenancy :: api`, `audit :: api`; AR-M-13); no other declaration changes.
- Persistence with `JdbcClient`; transactions with `TransactionTemplate`; ids from `Ids.newId()`; time from the `Clock` bean through `Timestamps.now(clock)`; every statement filtered by `tenant_id`; no `DELETE`. Requests to other modules inside a transaction join it (AR-R-10). JSON with a `static final JsonMapper` (Jackson 3); `jsonb` read back is compared as a tree.
- External calls (AR-R-09): `TicketingStepHandler.start` and `evaluate`, `TicketingService.recordEscalation` and every `TicketingConnector` method except `kind()` call `TransactionGuard.assertNoTransaction()` first. A sync record is stored `pending` in its own committed transaction before the first Jira call it covers (DM-E76-R2); every write that follows a Jira call happens in a transaction opened after the call returned.
- Lengths are Unicode code points; "cut to n" keeps the first n code points. "Comma-separated" means joined with `, `. Lists of names are in alphabetical order, which is ascending order of Unicode code points (DC-TX-00 "Lists"; the convention of `20-domain-model` DM-C-01 and P-20's `IncidentTexts.CODE_POINTS`), unless a rule says otherwise. Times in outbound texts use the outbound time format of DC-TX-01, `YYYY-MM-DD HH:MM:SS UTC` (the instant in UTC, truncated to the second); durations use DC-U-07 rule (2): less than 120 s `{s} s`, otherwise whole minutes `{m} min`, otherwise `{m} min {s} s`.
- `null` arguments of public requests: `IllegalArgumentException("a required argument is missing")`.
- Actors: requests of `vigil-ticketing` to other modules and its audit events use `Actor.module("vigil-ticketing")`.
- Logging (complete list at `INFO` or above from `vigil.ticketing` and from the Jira connector): `WARN` `ticket {operation key} for incident {incident id} of tenant {tenant id} failed: {error}` once per sync record finished `failed`. (The `WARN` that `FileSecrets.readNamed` already writes for a secret it cannot read stays.) No ticket content, secret or answer body is logged.
- Every list returned is unmodifiable. Texts named in this spec are exact.

### 6.5 The Jira connector (`JiraConnector`; PM-K-04, AR-K-04, AR-K-14, AR-K-15)

A Spring bean implementing `TicketingConnector`, `kind()` `JIRA_CLOUD`, built like the AI connectors (P-19 Section 6.6): `ConnectorRecords`, `FileSecrets`, `ConnectorHttp`, `ConnectorTimings`. Each method, in order: `TransactionGuard.assertNoTransaction()`; `null` arguments as Section 6.1; an instance of another kind: `IllegalArgumentException("connector instance {id} is not jira_cloud")`; then the checks below, each giving `Failed` with its reason and no call:

1. The base address: the instance's `address` without trailing `/`; a request address that `HttpSourceConnector.address` refuses: `The address is not a valid http or https address.`
2. The credential (AR-K-04, BP-A-29): no credential reference: `No credential is set.`; its secret not readable (`FileSecrets.readNamed`): `Secret {name} is not available.`; a secret that is not a JSON object with the non-empty strings `email` and `api_token`: `Secret {name} is not valid.` Only `email` and `api_token` are read; `expires_on` is ignored.
3. The settings `project_key`, `issue_type`, `resolved_status`, `reopened_status`, `label_prefix` are read as strings where a call needs them (a missing one is an `IllegalStateException`, as `AiConnector.setting`).

**Every request** (AR-K-14): `Authorization: Basic {base64 of email:api_token}`, `Accept: application/json`, and `Content-Type: application/json` on `POST`s; timeout `timings.jira()` (15 s; connect 5 s through `ConnectorHttp`). A call that does not get an answer: `Failed` with `FailureReasons.of(failure, uri, timings, timings.jira(), hidden)`, `hidden` the `api_token`, the `email` and the base64 text. An answer outside 200 to 299: `Failed` `HTTP {status}` (the P-19 form). A 2xx answer that is not the JSON object a method needs: `Failed` with the reason the method names. A value read from an answer is never part of a reason.

**ADF** (`Adf.document(List<TicketLine> lines)`, AR-K-15): `{"type":"doc","version":1,"content":[…]}` with one `paragraph` per line in order; a line without a link is `{"type":"paragraph","content":[{"type":"text","text": text}]}`; a line with a link has the text before the link as one `text` node (left out when it is empty) and the link as a second `text` node with `"marks":[{"type":"link","attrs":{"href": link}}]`; a line whose text is empty is `{"type":"paragraph"}`. Key order as written.

**Methods** (complete list of calls; paths after the base address):

- `create`: `POST /rest/api/3/issue` with `{"fields":{"project":{"key": project_key},"issuetype":{"name": issue_type},"summary": title,"description": Adf.document(description),"labels":[label]}}` (key order as written). 201 or another 2xx with a non-empty string `key`: `Done(key, {base}/browse/{key}, null)`; without one: `Failed` `The answer has no issue key.`
- `addComment`: `POST /rest/api/3/issue/{key}/comment` with `{"body": Adf.document(lines)}`; any 2xx: `Done(key, null, null)`.
- `status`: `GET /rest/api/3/issue/{key}?fields=status`; a 2xx with a string `fields.status.name`: `Done(key, null, name)`; otherwise `Failed` `The answer has no status.`
- `transition`: `GET /rest/api/3/issue/{key}/transitions`; the first entry of `transitions` whose `to.name` equals `statusName` exactly; none (or no `transitions` array): `Failed` `No transition to status '{statusName}'.` Then `POST /rest/api/3/issue/{key}/transitions` with `{"transition":{"id": id}}` (`id` as the answer gives it, a string); any 2xx (Jira answers 204): `Done(key, null, statusName)`.
- `findByLabel`: one search, `GET /rest/api/3/search/jql?jql={jql}&fields=status` with `jql` = `project={project_key} AND labels="{label}"`, encoded with `URLEncoder.encode(…, UTF_8)` and every `+` then written `%20` (the form of the P-06 recording `jira/0003-search-1.json`). A 2xx with an `issues` array: the first issue's string `key` gives `Done(key, {base}/browse/{key}, its fields.status.name or null)`; an empty array gives `Done(null, null, null)` (none); no array: `Failed` `The answer has no issues.` The repetition of AR-K-14 is `vigil-ticketing`'s (Section 6.7).

### 6.6 The texts (`TicketTexts`; DC-OUT-00 to DC-OUT-04, DM-E02-R2, DC-TX-00, DC-TX-01)

`{number}` is `INC-` and the incident `number` padded with zeros to 4 digits (DC-TX-01); `{product}` the tenant setting `productDisplayName`; `{label}` the tenant setting `environmentLabel`.

#### 6.6.1 Create (DC-OUT-01)

- **Title** (DM-E02-R2): `{label} - {title}` when `environmentLabel` is not empty, else `{title}`; cut to 255, Jira's limit for `summary` (CTX-D-069 (5); the demo title has 88 characters).
- **Description**, exactly these lines in this order:
  1. `Incident: {title}`
  2. `Alerts: {alert_count} {alert or alerts}. Types: {alert type display names}.` — `alert` when the count is 1 (DC-TX-00 "Counts"); the display names of the incident's `alert_types`, alphabetical, comma-separated; a type's display name is the `alertTypeName` of the first active member (`IncidentService.members`, by `joined_at`, then id) whose alert has that type, or the type's key when none has it (as P-20's template summary).
  3. `Customer impact: {service names}.` — the `name`s of `affected_services`, sorted by code point, comma-separated; `none identified` when there is none.
  4. `Root-cause hypothesis: {component name} ({component key}). A hypothesis from the service map, not a confirmed cause.` from the incident's `hypothesis` copy, or `Root-cause hypothesis: none.` when it has none.
  5. `AI summary: {text}` when the summary of `InvestigationService.summaryForMessage` has source `ai`, otherwise `Summary (template): {text}`.
  6. `Evidence:`, then one line `- {summary}` per entry of `IncidentService.evidenceSummary` (its order, `collected_at`), or the one line `- none yet` when there is none.
  7. `Open {number} in {product}: {link}`, the link `{publicBaseAddress}/incidents/{incident id}` (AR-I-100) as the line's `link`.
- **Label** (DM-E76-R2, AR-K-14): `{label_prefix}{incident id}` (the id in its lower-case text form).

#### 6.6.2 Reopen (DC-OUT-04)

One line: `Reopened by alert '{title}' ({source kind}) received at {first_received_at}.` The reopening alert is the alert of the membership (`IncidentService.memberships`) with the latest `joined_at` (then the highest id) whose `reasonJson` has `decision` `reopened` (DM-E-34, DM-R-21); `{title}`, `{source kind}` and `{first_received_at}` are its `IntakeService.alert` values (PM-I-48, AR-A-22): `title`, the source kind name of DC-TX-01 (`zabbix` "Zabbix", `alertmanager` "Alertmanager"), and `firstReceivedAt` in the outbound time format. No such membership, or no such alert in `vigil-intake`: no reopening alert (Section 6.7).

#### 6.6.3 Resolve (DC-OUT-03) and the recovery evidence (CTX-D-069 (6))

The recovery evidence is the incident's evidence entry of kind `recovery_verification` whose `producerRecordId` equals the incident's `resolvedByVerificationId` (DM-SM14-T2). Its `content` is the object of DM-E-62 (DC-A-12): the definition snapshot, `window_started_at`, `decided_at` and the last evaluation. The keys `vigil-ticketing` reads (complete list; CTX-D-069 (6) names them, and P-23 MUST write them so): `definition_snapshot.observation_window_seconds`, an integer of at least 1; `window_started_at` and `decided_at`, instants as ISO 8601 text; `last_evaluation.conditions`, an array of objects each with a string `detail` (the condition's DC-TX-03 text for its state, DC-A-12). Lines, exactly, in order:

1. `Resolved: recovery verified.`
2. The entry's `summary`.
3. `Conditions:`, then one line `- {detail}: held` per element of `last_evaluation.conditions`, in the array's order, then `- Every monitoring source is healthy: held`.
4. `Observation window: {observation window}, from {window_started_at} to {decided_at}.` (the window by DC-U-07 rule 2, the times in the outbound time format).
5. `Source: {source_system}` (the entry's `source_system`).

No such entry, or content without these keys in these types: no recovery evidence (Section 6.7).

#### 6.6.4 Record escalation (DC-OUT-02)

`Escalated to level {n}: {team names} ({escalation cause}).` (`{n}` the `level` given; `{team names}` the names given by `vigil-routing`, alphabetical, comma-separated, `none` when the list is empty (DC-TX-00 "Lists"); the cause by DC-TX-01 from the cause and timer given (DC-A-10): `acknowledgement_timeout` `not acknowledged within {timer}` with the timer by DC-U-07 rule 2, `escalate_now` `workflow escalation step`); then `Evidence:`; then one line `- {summary}` per entry of `IncidentService.evidenceSummary`, and no further line when there is none (DC-OUT-02 names no other text; CTX-D-069 (7)).

#### 6.6.5 Content sent and audit texts

- `content_sent` (CTX-D-069 (8)): `create` `{"title", "description": [line texts], "labels": [label]}`; `reopen` and `resolve` `{"comment": [line texts], "transition_to": status name}`; `record_escalation` `{"comment": [line texts]}`; a record that fails before its content is built (Section 6.7) `{}`.
- Audit summary (DC-TX-10 `ticket_changed`): `Jira {key}: {operation} {outcome}.` with `{key}` the link's `external_key`, or `no ticket` when the record has no link; `{operation}` `create`, `reopen`, `resolve` or `record escalation`; `{outcome}` `done` or `failed`.

### 6.7 The Ticket step (`TicketStep`; DM-S-10, PM-M19-01 to PM-M19-04, DM-E76-R1, DM-E76-R2, DM-SM-14, AR-K-16)

The engine calls `start` and `evaluate` on the run's virtual thread with no transaction open; a throw is a failed call, retried after 5 s, 15 s and 45 s (AR-TM-05). `start` and `evaluate` do the same (the step never answers `Waiting`); `cancel` does nothing, every time. The answer is `Completed(output, resultRef)` with `output` `done` or `failed` and `resultRef` `ResultRef("vigil-ticketing", "TicketSyncRecord", record id)` when the step finished a sync record, else `null`.

**Records.** Every record this step stores has `requested_by` `workflow_step` and this `step_execution_id`; `at` is when it was stored; `ticket_link_id` is the incident's link whenever the incident has one, except on a `create` record that is not finished `done`, which has none (DM-E-76 "empty for a failed create", CTX-D-069 (3)). A record that needs a Jira call is stored `pending` in its own committed transaction before the first call (DM-E76-R2). A record that fails before any call ("fails at once" below) is stored directly as `failed`, with `content_sent` `{}` unless stated, `finished_at` = `at`, and its audit event, in one transaction (CTX-D-069 (9)). **Finishing** a record happens in one transaction opened after the calls: `outcome`, `error` (cut to 500), `finished_at` now, `ticket_link_id` where set, the link change, and the audit event (Section 6.9).

1. `TransactionGuard.assertNoTransaction()`. A step type other than `TICKET`, or parameters that are not an object whose `operation` is `create` or `resolve`: `IllegalArgumentException("ticket step parameters: operation create or resolve")`.
2. The incident (`IncidentService.incident`); none: `IllegalStateException("incident {id} not found")`.
3. **The step's own record** (the record with this `step_execution_id`): `done` or `failed` → answer that outcome with that record and call nothing (a call made again after a stop between the record and the engine's answer). `pending` → finish it by the restart rules (step 6). None → go on.
4. **`create`**, by the incident's ticket link (DM-E76-R1):
   - link `open`: `done`, no record, no call (CTX-D-069 (9)).
   - link `resolved` (a reopened incident): **reopen**. The link's instance (below); the line of Section 6.6.2 — no reopening alert: a record `reopen` fails at once with `no reopening alert`. Otherwise a record (`reopen`, `pending`, `content_sent` `{"comment", "transition_to"}`); `addComment`, then `transition` to the instance's `reopened_status` (AR-K-16); both `Done`: the link `open` (DM-SM14-T3) and the record `done`; else the record `failed` with the first `Failed` reason.
   - no link: **create**. The instance: the first of `ConnectorService.activeInstances(tenant, JIRA_CLOUD)`; none: a record `create` fails at once with `no active Jira connector instance`. The link base `TenantService.publicBaseAddress`; empty: a record `create` fails at once with `the tenant has no public address for links`. The content of Section 6.6.1 (`summaryForMessage` in its own transaction first); a record (`create`, `pending`, `content_sent` `{"title", "description", "labels"}`). Then, when the incident has any other `create` record whose outcome is `pending`, or `failed` with a `content_sent` other than `{}` (an earlier attempt that called Jira and may have made the issue; CTX-D-069 (4)), the label search (below): an issue found is linked instead of created; a failed search finishes the record `failed` with its reason. Otherwise, and when the search found none, `create`. `Done` (created or found): in one transaction the link (`open`, the instance, `external_key`, `url` the answer's `address`; DM-SM14-T1), the record `done` with the link, and every other `pending` `create` record of the incident finished `failed` with the error `superseded by {this record id}` and no link (each with its audit event, `Jira no ticket: create failed.`); a `Failed` create: the record `failed` with its reason.
5. **`resolve`**, by the link:
   - no link: a record `resolve` fails at once with `no ticket` (DM-E76-R1).
   - link `resolved`: `done`, no record, no call (DM-SM14-T2, CTX-D-069 (9)).
   - link `open`: the link's instance (below); the recovery evidence (Section 6.6.3); none: a record `resolve` fails at once with `no recovery evidence`. Otherwise a record (`resolve`, `pending`, `content_sent` `{"comment", "transition_to"}`), then `addComment`, then `transition` to the instance's `resolved_status` (AR-K-16); both `Done`: the link `resolved` and the record `done`; else the record `failed` with the first `Failed` reason.
6. **Restart rules** (the step's own record is `pending`, DM-E76-R2). The content is built again as in steps 4 and 5 and replaces the record's `content_sent` only when it is sent again (a create, comment or transition made now); otherwise the stored `content_sent` stays. A condition that now fails at once (no instance, no link base, no evidence, no reopening alert) finishes the record `failed` with that reason and the stored content.
   - `create`: the label search; found: link it and finish as a `Done` create; not found: `create`, then as in step 4. A failed search: the record `failed` with its reason.
   - `reopen` or `resolve`: `status` of the link's key first; equal to the target status: the link takes the target state and the record `done`, with no comment and no transition; otherwise the comment and the transition as in steps 4 and 5 (a second comment may result; accepted, as DM-E76-R2 accepts it for escalations; CTX-D-069 (9)). A failed `status`: the record `failed` with its reason.

- **The link's instance** (CTX-D-069 (2)): the link's `connector_instance_id` (`ConnectorService.instance`); none or inactive: a record (of the operation) fails at once with `the Jira connector instance is not active`.
- **Settings**: `label_prefix`, `reopened_status` and `resolved_status` are read from the instance's settings before any record is stored (the seed import guarantees them through the kind's settings schema; a missing one is an `IllegalStateException`, a failed call). The connector is the `TicketingConnector` bean whose `kind()` is the instance's kind (`JiraInstances`).
- **The label search** (AR-K-14 as CTX-D-060 (6) reads it): `findByLabel` at once, then, while it finds none, again 5 s after the previous answer, at most 4 searches in all (`Thread.sleep` on the step's virtual thread, no transaction open). A `Failed` search ends the search with that reason.
- Any `vigil-incidents`, `vigil-intake`, `vigil-investigation`, `vigil-connectors` or `vigil-tenancy` request that throws is thrown (a failed call).
- Two Ticket steps of one incident never run at the same time (one live run per incident and episode, DM-E50-R1; one evaluation at a time, DM-R-67); a second link for an incident is refused by the unique index of Section 6.3, which makes it a failed call.

### 6.8 The escalation comment (`Ticketing.recordEscalation`; PM-M19-01, PM-M19-03, DC-OUT-02, DM-E76-R2, DC-A-10, CTX-D-069 (7))

`SyncOutcome recordEscalation(TenantId tenantId, UUID incidentId, UUID escalationId, long level, List<String> teamNames, EscalationCause cause, Duration timer)`, called by `vigil-routing` (P-22) with no transaction open, after the escalation is committed in `vigil-incidents` (`TransactionGuard.assertNoTransaction()` first; `null` arguments as Section 6.1, except `timer`, which is required for `acknowledgement_timeout` and MUST be `null` for `escalate_now`, else `IllegalArgumentException("timer: required for acknowledgement_timeout only")`; `teamNames` may be empty). `vigil-routing` passes the level, cause and timer with the request, as PM-I-14 (DC-A-10) says; `vigil-ticketing` does not read the escalation. The incident must exist (`IllegalStateException` otherwise).

1. The record of this `escalation_id`: `done` or `failed` → return its outcome, no call; `pending` → send again (DM-E76-R2) and finish it; none → go on.
2. No ticket link: a record (`record_escalation`, `requested_by` `routing`, the escalation id) fails at once with `no ticket` (DM-E76-R1); returns `FAILED`.
3. The link's instance as in Section 6.7 (inactive: the record fails at once). Otherwise the lines of Section 6.6.4; the record `pending` with `content_sent` `{"comment"}` (when new; a `pending` record gets the lines built again); `addComment` on the link's key; `Done`: `done`; else `failed` with the reason. The link's state does not change. Returns the outcome.

### 6.9 Audit (DM-E08-R1, DM-E08-R3)

Each sync record that becomes `done` or `failed` gets exactly one `AuditService.append` in the transaction that finishes it: `occurredAt` now, actor `Actor.module("vigil-ticketing")`, `ticket_changed`, subject type `TicketSyncRecord` and the record's id, the incident id, the summary of Section 6.6.5, details `{"operation": operation key, "outcome": "done" or "failed"}`. A record superseded in Section 6.7 step 4 gets its event too. The cases that create no record create no event.
