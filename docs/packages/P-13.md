## 2. Goal

Build the module core of `vigil-intake` (PM-M06): monitoring sources, alert type definitions and alert type mappings (DM-E-15 to DM-E-17) imported as seed part 6; the webhook operation AR-I-90, which checks the source's own token (DM-E18-R1), stores every call and alert entry unchanged (DM-E-18, DM-E-19), normalises each entry through the source's monitoring connector and the alert type mappings (DM-E-20, DM-E17-R1), and applies it to the alerts (DM-E-21, DM-E-22, DM-E21-R1, DM-E21-R2) with a gap-free `sequence` per tenant in the order of AR-R-16; the events AR-E-01 to AR-E-03; source health (DM-R-39 to DM-R-41, DM-SM-03, DM-E-23) with its scheduled connection tests and 1 s evaluation for active tenants, started at restart step (6) and by an AR-E-14 listener, and the connection test on request (PM-M06-07); and the questions later modules ask of intake (the alerts after a sequence number, an alert, the sources, whether a source was healthy throughout an interval, the alert types).

### 6.1 General rules

- Every public type of `vigil-intake` is in `vigil.intake.api` (AR-R-04); every other class is package-private in `vigil.intake`. The `@ApplicationModule(allowedDependencies = {"shared", "tenancy :: api", "connectors :: api", "audit :: api"})` of `vigil.intake` stays unchanged (this package uses no `audit` request), and so do the declarations of `vigil.setup` and `vigil.api`. No public type of `vigil.intake.api` names a type of another module's `api` package, because the modules that read intake (`vigil-correlation`, `vigil-recovery`, `vigil-engine`, `vigil-reporting`, `vigil-ticketing`) may not depend on `vigil-connectors` (AR-M-15 to AR-M-21).
- Records are written with `JdbcClient`; every writing operation is `@Transactional` (`REQUIRED`, AR-R-10) except where Section 6.6 or 6.7 says it opens its own transactions; reads have no transaction of their own.
- Time from the `Clock` bean through `Timestamps.now(clock)` (milliseconds); ids from `Ids.newId()`; lengths in Unicode code points, as `varchar(n)` counts them. "Cut to n" means: the first n code points when the text is longer, otherwise unchanged (DM-C-11 as amended by BP-A-25; no `*_truncated` field is added).
- `null` arguments: `IllegalArgumentException`, except where Section 6.4 says otherwise.
- Logging (AR-S-11): never a token, an `Authorization` header, a request body or a payload. Nothing at `INFO` or above per webhook call or per question. One `INFO` line per source health change (tenant id, source key, from, to, cause); one `WARN` line per call whose body the connector cannot read (tenant id, source key, the connector's reason); one `WARN` line when a scheduled connection test throws (tenant id, source key, the exception's class name).
- Every list returned is unmodifiable.
- No class of `vigil.intake` or `vigil.setup` that this package adds has a `@Profile`, except the scheduled work and the listener of Section 6.8, which are `@Profile("!migrate")` as P-08's `SessionSweeps` and `TenantAliasListener`. The connection test of Section 6.7 is in a package-private class `SourceTests` without a profile, used by `startFirstTests`, `testSource` and the scheduled work, so the `migrate` context still starts (`MigrateIT`).
- Package-private pure functions, used by the module and tested without a database (names binding): `AlertTypeRule.classify(MonitoringKind kind, List<mapping> mappings, Map<String, String> mappingFields)` → the alert type (DM-E17-R1); `HealthRule.evaluate(source row values, Instant now)` → the health and, when it differs from the stored health, the cause (DM-R-40).
- `vigil.intake.api.AlertStatus` and `IdentityPair` have the same simple names as types of `vigil.connectors.api`; the module's code converts between them and writes one of the two fully qualified. A `MonitoringKind` is passed to `ConnectorService` as `ConnectorKind.fromKey(kind.key()).orElseThrow()`.
- Lists ordered "in code point order" are sorted in SQL with `COLLATE "C"`.

### 6.6 The webhook (AR-I-90, AR-R-16, DM-E-18 to DM-E-22, DM-E17-R1, DM-E21-R1)

**`vigil-api`.** A handler `POST /api/v1/webhooks/{sourceKey}` in a package-private `WebhookController` (`@Profile("!migrate")`, like the other controllers of `vigil.api`) with a new access annotation `@WebhookToken` (package-private, method level, runtime, like `@InstallationToken`): `AccessInterceptor` lets it pass without a session and without a check of its own (the token is checked by `vigil-intake`, the one caller of `Secrets.verify` besides `vigil-connectors`, AR-S-04); `EntryPointTest` accepts exactly one of the five annotations. The handler takes the request's tenant (`HostTenantFilter`, as today: a host with no alias answers `unknown_host`), and:

1. Reads the body from the request's input stream (`HttpServletRequest.getInputStream()`, so no message converter reads it), at most 5,242,881 bytes; when it has more than 5,242,880 bytes, answers 413 `too_large` (AR-TM-02) and reads no further (whether or not the request has a `Content-Length`; Tomcat's default `max-swallow-size` of 2 MiB is left unchanged).
2. Takes the presented token from `Authorization`: the word `Bearer` (any case), one space, then a token with no space (as `@InstallationToken`); a missing or malformed header gives `null`.
3. Calls `IntakeService.receiveWebhook(tenant, sourceKey, token, the Content-Type header or null, body)` and answers 200 `{"entries": n}` with its result; a `VigilError` is answered by `ApiErrors` as usual.

Nothing is stored and nothing changes for a call refused in step 1 or by `receiveWebhook`'s checks. The OpenAPI file adds the operation (request body: any media type, binary; answers 200 with `{"entries": integer}`, 401, 404, 413 with the error body; `security: [{webhook: []}]`) and the security scheme `webhook` (`type: http`, `scheme: bearer`). `ContractIT`: its security check also compares the set of operations with `[{webhook: []}]` with the `@WebhookToken` handlers (as it compares the public and installation sets); in `@BeforeAll`, after the demo bundle's import into its ready tenant, it sets the alias `hooks.test` to that tenant with `TenantService.setAlias`, it creates its secrets folder with `TestSecrets.create` from the same values as `InstallationIT.secrets(database)` plus `webhook-zabbix` and `webhook-alertmanager` (`randomToken()`) (`InstallationIT` stays unchanged), and it gets scenarios for 200 (a Zabbix body like `0001-zabbix-lab.json`'s, written in the test, with the right token), 401 (no `Authorization`), 404 (source key `nope`) and 413 (5,242,881 bytes) on `hooks.test` (BP-R-13).

**`receiveWebhook`** (AR-R-16 steps 2 to 5):

1. The active source of the tenant with that `source_key` (a key that is not a valid `Key` finds none); none or inactive: `VigilError` `NOT_FOUND` (default message).
2. `presentedToken` `null`: `VigilError` `NOT_SIGNED_IN`; `Secrets.verify(tenantId, webhook_token_ref_id, presentedToken)` false: `VigilError` `BAD_TOKEN` (DM-E18-R1, AR-S-05; default messages).
3. `ConnectorService.parse(ConnectorKind.fromKey(the source's kind key).orElseThrow(), body, contentType)` (no network call, before the transaction).
4. In one transaction: lock the counter row (`SELECT … FOR UPDATE` on `intake.alert_counter`, held until commit); now = `Timestamps.now(clock)`, read after the lock, is `received_at` of the call, its raw alerts and its state changes (DM-R-03: calls of one tenant, and so of one source, get `received_at` in commit order); lock the source row (`SELECT … FOR UPDATE`); store the webhook call (`content_type` the header cut to 100, the empty text when `null`; `body` the bytes as received; `entry_count` the number of parsed entries, 0 when the parse failed; `parse_outcome`); for a failed parse, the `WARN` line of Section 6.1 and no raw or normalised alert (the contact below is made all the same: the call was authenticated, DM-R-39); otherwise, for each entry in `entry_index` order: a raw alert (`payload` the entry's `payload()` exactly), then its normalised alert and its application as below; then the counter row's `last_sequence`; then the contact: `last_contact_at` = now and the health evaluation of Section 6.7; the events are published in this transaction, in the order they arise.
5. Returns `entry_count`.

**Normalised alert of an entry** (DM-E-20; DM-C-11 as amended by BP-A-25): a `Failed` entry → `outcome` `failed`, `failure_reason` the connector's reason cut to 300, `application` `not_applied`, every other field empty; a `Normalised` entry whose alert key has more than 200 characters → the same with the reason `the alert key is longer than 200 characters`; otherwise `outcome` `normalised`, `alert_key`, `reported_status`, `title` cut to 300 (`NULL` when the connector gives none), `source_time` (milliseconds), `source_severity` cut to 50, `identity_pairs` in the connector's order with each value cut to 200, `alert_type` by DM-E17-R1.

**Fields (DM-E-17 `field`, complete list per kind, AR §12.3 and §12.4).** `zabbix`: `event_name`, `host`, `severity`, and `tag.{name}`; `alertmanager`: `label.{name}` and `annotation.{name}`; where `{name}` is any text of at least 1 character; the whole field at most 200 characters. A mapping's comparison reads the entry's `mappingFields()` value of its field.

**DM-E17-R1.** The alert type is the `alert_type` of the first mapping of the source's kind, in ascending `order`, whose comparison is true: `equals` — the value equals the field's value; `starts_with` — the field's value starts with the value; `contains` — the field's value contains the value; compared code point by code point, case-sensitive; a field the entry does not have makes the comparison false. When none is true: `unclassified`.

**Application (DM-E21-R1, DM-SM-04), for a `normalised` entry**, looking for the alert of the same source and `alert_key` with status `firing` (DM-E21-R2; the counter lock serialises the tenant's calls, and the partial unique index backs the rule, AR-R-12):

- (a) `firing`, none firing → a new alert: `sequence` = `last_sequence` + 1 (then `last_sequence` is that value), `source_kind`, `alert_key`, `alert_type`, `identity_pairs` and `title` of the entry (the empty text `''` when the entry has no title, because DM-E-21 `title` is required), `status` `firing`, `fired_at` = the entry's `source_time` or, when it has none, `received_at`, `first_received_at` = `received_at`, `entry_count` 1; an `alert_state_change` (`from_status` empty, `to_status` `firing`, `at` = `received_at`, `source_time`, `raw_alert_id`); `application` `created_alert`, `applied_to_alert_id` the new alert; publish `AlertReceived(tenant, alert id, sequence)` then `AlertStateChanged(tenant, alert id, FIRING)`.
- (b) `firing`, one firing → its `entry_count` + 1 and `updated_at`; `application` `repeat_firing`, `applied_to_alert_id` that alert; no state change, no event.
- (c) `resolved`, one firing → `status` `resolved`, `resolved_at` = the entry's `source_time` or `received_at`, `resolve_received_at` = `received_at`, `entry_count` + 1, `updated_at`; an `alert_state_change` (`firing` → `resolved`); `application` `resolved_alert`, `applied_to_alert_id` that alert; publish `AlertStateChanged(tenant, alert id, RESOLVED)`.
- (d) `resolved`, none firing → `application` `orphan_resolved`, `applied_to_alert_id` empty; nothing else.

### 6.7 Source health (DM-R-39, DM-R-40, DM-SM-03, DM-E-23, PM-M06-07)

**The rule (DM-R-40), as a function of the source row and now:** `disconnected` when `last_contact_at` is empty; else `disconnected` when `last_test_outcome` is `failed` and `last_contact_at` is not later than `last_test_at`; else `disconnected` when now − `last_contact_at` > `disconnected_after`; else `stale` when now − `last_contact_at` > `stale_after`; else `healthy`. **Evaluation:** in a transaction that holds the source row's lock, compute the rule; when the result differs from `health`: set `health`, `health_changed_at` = now and `updated_at`; append a `source_health_change` (`from_health` the old, `to_health` the new, `at` now, `cause`: to `healthy` — `contact`; to `stale` — `contact_age`; to `disconnected` — `test_failed` when the second clause gave it, else `contact_age`); publish `SourceHealthChanged(tenant, source id, new health)`; log the `INFO` line of Section 6.1. Evaluation runs (complete list): in the webhook transaction after the contact (Section 6.6); in the transaction that records a connection test; on the 1 s tick of Section 6.8 for each active source of an active tenant.

**Connection test (DM-R-39, PM-M06-07).** With no transaction open (AR-R-09): `ConnectorService.testConnection(tenantId, the source's connector_instance_id)`; then, in one transaction that locks the source row: `last_test_at` = now, `last_test_outcome`, `last_test_reason` (the connector's reason, at most 500 characters, P-10; empty when passed), `updated_at`; when passed, `last_contact_at` = now; then the evaluation above. `testSource(tenantId, sourceKey)` does this for the active source with that key (none or inactive: `VigilError` `NOT_FOUND`) and returns the result and the health after it; an exception of `testConnection` propagates and nothing is recorded. The scheduled tests (Section 6.8) and `startFirstTests` (Section 6.5) do the same and, when `testConnection` throws, log the `WARN` line of Section 6.1 and record nothing.

**`healthyThroughout(tenantId, sourceId, from, to)` (DM-E23-R1):** `from` later than `to`, or `to` later than now: `IllegalArgumentException`; a source not found: `false`; otherwise `true` exactly when the source's latest `source_health_change` with `at` at or before `from` (latest by `at`, then by `id`: ids from `Ids.newId()` increase within the process, so two changes at one instant keep their order) exists and has `to_health` `healthy`, and no `source_health_change` of the source has `at` later than `from` and at or before `to`.
